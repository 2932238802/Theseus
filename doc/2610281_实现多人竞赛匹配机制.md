# 多人竞赛匹配机制（v1）

## 1. 目标与范围

第一版实现实时匹配的 4 人排位赛：用户进入匹配队列，系统凑齐 4 名合格用户后立即创建一场比赛，并向四人返回同一组题目。每位参赛者独立提交代码，比赛结束时统一结算并通过站内通知发送个人成绩。

本版本包含：

- 实时匹配队列与 4 人成局；
- 共享题目集、独立提交、比赛倒计时；
- 参赛者提前提交并离场；
- 时间到或 4 人全部完成时结算；
- 摄像头授权、切屏、粘贴事件记录；
- 结算结果写入通知中心；
- 学校/官方赛事在论坛中置顶展示。

本版本不包含：段位和赛季、代码相似度判定、摄像头 AI 判定、实时视频流、申诉复核和 WebSocket 推送。这些功能需要在基础比赛数据稳定后单独设计。

## 2. 用户流程

### 2.1 进入匹配

1. 用户点击“开始排位赛”。客户端先请求摄像头授权，再请求屏幕共享，并上报两个授权结果；任一未通过时前端阻止继续，服务端也会拒绝未带 `granted` 的匹配请求并返回 400。
2. 服务端校验用户已登录、邮箱已验证、没有正在进行的比赛且不在匹配队列中，然后加入排队队列。
3. 队列按进入时间 FIFO。凑齐 4 人后原子地取出 4 人创建比赛，状态从 `matching` 变为 `running`。等待超时后允许 3 人/2 人降级。
4. 如果用户主动取消匹配，只能移除自己的排队记录；比赛成局后不能取消。

### 2.2 比赛过程

- 一场比赛默认 60 分钟、4 道题；时长和题目数量作为比赛配置保存，不能依赖客户端参数。
- 四人看到相同题目顺序和相同测试数据；每个人拥有独立的提交记录。
- 提交仍复用现有判题系统。只有比赛开始后提交且题目属于本场比赛的记录，才计入比赛成绩。
- 参赛者可以点击“完成并离场”。离场只改变自己的 `finished` 状态，不提前结束整场比赛；其他人继续作答。
- 比赛在以下任一条件满足时进入结算：到达 `ends_at`，或四名参赛者均为 `finished`。结算任务必须幂等，重复触发不能生成重复成绩或重复通知。

## 3. 状态机

### 3.1 比赛状态

`matching -> running -> settling -> finished`

异常情况下允许 `matching/running -> cancelled`，例如题目配置失效或系统管理员取消。`finished/cancelled` 为终态。

### 3.2 参赛者状态

`queued -> active -> finished`

用户掉线不自动判定为完成；服务端以比赛截止时间结算。重新进入页面时通过比赛查询接口恢复状态。

## 4. 初版计分方案

计分先采用可配置的透明公式，权重写入比赛配置，后续可以在不改历史成绩的前提下调整新比赛的默认值。

### 4.1 单题分数

- 通过题目：基础分 100；未通过：0 分。
- 同一题只按首次通过时间计时，后续提交用于判题但不重复加分。
- 通过题目的时间分 `time_score = 100 * (1 - elapsed_seconds / duration_seconds)`，限制在 0 到 100；未通过题目为 0。

### 4.2 总分

默认权重：通过题数 60%，完成速度 25%，代码书写 15%。

- 通过题数：`accepted_count / problem_count * 100`；
- 完成速度：所有已通过题目的平均 `time_score`，没有通过题目时为 0；
- 代码书写：先使用可解释的提交行为分，满分 100。默认从 100 分开始，对每道题的编译错误、运行错误、答案错误分别扣 2、3、1 分，最低 0 分；不评价代码风格，也不做代码相似度判断。
- 总分：`0.60 * solved_score + 0.25 * speed_score + 0.15 * coding_score`，四舍五入到两位小数。

排名按总分降序；同分时依次比较通过题数、最后一道通过题的时间、最早完成时间，仍相同则按用户 ID 稳定排序。该公式是 v1 默认方案，正式上线前应通过小规模测试调整权重。

## 5. 防作弊事件、人工复核与信誉分

客户端在比赛期间记录以下事件，并批量上传到服务端：

- `camera_permission`: `granted` / `denied` / `unavailable`；
- `screen_permission`: `granted` / `denied` / `unavailable`；
- `visibility_hidden` / `visibility_visible`：页面切到后台或恢复；
- `paste`：发生粘贴操作，只记录次数和时间，不记录剪贴板内容；
- `paste_suspicious`：编辑器内粘贴内容达到 80 字符、看起来像代码，且与当前代码、题目描述/示例/代码模板的词元重合度分别低于 32% 和 15% 时记录。payload 只保存长度、行数、两项重合度、语言和前 200 个字符片段，不保存完整剪贴板内容

事件字段至少包括比赛 ID、参赛者 ID、事件类型、客户端时间、服务端接收时间和页面会话 ID。服务端不信任客户端时间，也不因为单个事件直接扣分；比赛结束后保留事件供管理员查看。摄像头视频和屏幕画面都不上传、不存储。

粘贴初筛只在比赛编辑器内本地完成，不安装全局剪贴板监听。疑似事件不会自动定罪：系统按「待复核数量最少」自动分配给在线管理员，管理员可以滞后审批；管理员在「粘贴复核」页逐条标记「确认作弊」或「排除」，结论写入 `contest_event_reviews`，并记录复核人、复核时间、备注和处罚时间。

确认作弊后执行以下处罚，同一事件只执行一次：

- 固定扣除 25 信誉分；
- 取消该用户本场成绩；若比赛已结算，立即重新排名，其余选手按新名次重新计算段位分；
- 段位分只应用新旧结果的差额（多还少补），不覆盖用户在后续比赛中已经发生的变化；
- 信誉分 `70 < 分数 < 100` 发送站内消息提醒；`40 < 分数 <= 70` 再次发送站内消息提醒；`0 < 分数 < 40` 禁止参与排位赛、赛事报名/进入和论坛发言；`分数 < 0` 账号封禁、当前会话失效、邮箱加入黑名单，除非管理员恢复否则保持封禁；
- 不做公开论坛通报。

信誉分默认 100，每日签到恢复 0.1 分（上限 100），已被封禁的账号无法登录签到。除签到外只能由管理员定量恢复：管理员输入恢复后的分数和原因，恢复到 0 分以上时自动解除账号与邮箱封禁。已确认作弊的记录不能改回排除，避免重复处罚或撤销已经发生的排名变化。

客户端需要在比赛页面卸载前尽力发送未上传事件；服务端接口应支持幂等事件 ID，避免重试造成重复记录。

## 6. 数据模型建议

新增迁移（名称待实现时确定）：

- `contests`：`id`、`status`、`duration_seconds`、`problem_count`、`starts_at`、`ends_at`、`finished_at`、计分权重、题目快照；
- `contest_problems`：比赛题目顺序、题目 ID、分值快照；
- `contest_participants`：比赛 ID、用户 ID、状态、加入/完成时间、总分、排名；用户和比赛联合唯一；
- `contest_queue`：用户 ID、加入时间，用户联合唯一；
- `contest_submissions`：比赛 ID 与现有提交 ID 的关联、首次通过时间和错误分类快照；
- `contest_events`：上述防作弊事件，事件 ID 联合唯一；
- `contest_results`：若不直接放在参赛者表，保存结算明细和公式版本，保证历史成绩可追溯。

题目必须在比赛创建时快照，避免比赛过程中题目被编辑导致同场用户看到不同内容。提交判题完成后通过现有判题结果更新比赛统计；结算时再从提交事实重算一次，避免异步消息丢失。

## 7. API 草案

需要登录且邮箱已验证的接口：

- `POST /api/contests/match`：加入匹配队列，返回 `queued` 或已成局的比赛概要；
- `DELETE /api/contests/match`：取消自己的匹配；
- `GET /api/contests/current`：查询当前排队或进行中的比赛；
- `POST /api/contests/{id}/events`：批量上传防作弊事件；
- `POST /api/contests/{id}/finish`：标记本人完成并离场；
- `GET /api/contests/{id}`：比赛题目、时间、参赛者完成状态；
- `GET /api/contests/{id}/result`：比赛结束后的排名和本人得分明细。

提交接口增加可选 `contest_id`，服务端校验用户是该比赛参赛者、比赛仍在 `running` 且题目属于题目快照。客户端轮询即可完成第一版，WebSocket 作为后续优化。

## 8. 通知

结算成功后为每位参赛者创建一条 `contest_result` 站内通知：标题包含比赛结束和名次，正文包含总分、通过题数、用时和各项得分，链接指向比赛结果页。通知写入必须和结算结果处于同一可重试流程；重复结算通过业务唯一键避免重复通知。

## 9. 官方赛事与论坛置顶

学校或官方组织的赛事不是排位匹配场次，而是独立的 `official_event` 记录，包含标题、主办方、报名/开始/结束时间、说明、报名链接和状态。管理员或具备赛事发布权限的组织者可以把赛事同步为论坛公告帖，并设置 `is_pinned` 与置顶截止时间。

论坛列表按“有效置顶赛事 → 其他置顶帖 → 原有排序”展示。赛事结束或置顶截止后自动取消置顶，但帖子和报名记录保留。第一版复用现有论坛置顶能力，不把赛事报名强行建模为普通评论。

## 10. 实施顺序与验收

1. 数据库迁移、模型和服务端状态机；
2. 匹配/取消/当前比赛/完成/结果接口；
3. 将比赛 ID 接入提交与判题统计；
4. 结算任务与 `contest_result` 通知；
5. 前端匹配页、比赛页、结果页和事件采集；
6. 官方赛事与论坛置顶字段/接口；
7. 补充真实 API 冒烟脚本。

验收标准：四名用户并发加入只生成一场比赛；四人看到同一题目快照；任一用户可提前离场且不会影响他人；时间到或四人完成只结算一次；成绩通知每人只收到一次；拒绝摄像头、切屏和粘贴事件均可在比赛记录中查询；官方赛事可以在论坛置顶并按截止时间失效。

## 12. 当前实现（2026-10-29）

- 匹配：必须同时获得摄像头与屏幕共享授权；4 人房优先，等待 3 分钟后允许段位分相近的 3 人房，等待 5 分钟后允许 2 人房，房内按名次调整段位分。
- 结算：默认 `ends_at + 20s` 后结算一次；排位赛无人可提交时提前结算，全员断线超时则取消对局。结果站内通知，赛事比赛不改变排位分。
- 断线重连：比赛页每 10 秒心跳；30 秒无心跳标记 `disconnected`，距最后一次心跳 120 秒变为 `timed_out` 并冻结成绩；赛事比赛不因全员断线取消。详见 `doc/2610294_短线重连实现方案.md`。
- 官方赛事：`official_events` 保存赛事信息，`official_event_registrations` 保存报名，`official_event_followers` 保存关注，`official_event_problems` 保存题目与顺序。
- 赛事比赛：首次有报名选手进入时按 `official_event_problems` 冻结题目快照并创建 `contests.official_event_id` 关联的比赛；报名但未进入的选手保持 `queued`，不参与结算。
- 论坛置顶：管理员可把已发布赛事同步为校园墙帖子并置顶，赛事结束或取消后后台任务自动取消置顶。
- 粘贴初筛与复核：编辑器读取本次粘贴文本，与当前代码、题目内容做本地词元重合度比较；疑似记录 `paste_suspicious`，按待复核负载自动分配给管理员。管理员确认后固定扣 25 信誉分、取消本场成绩；已结束的比赛重新排名并按差额修正段位分。
- 信誉分：默认 100，每日签到 +0.1；低于 40 禁止排位、赛事和论坛；低于 0 自动封号并加入邮箱黑名单。管理员可按申诉定量恢复，恢复到 0 分以上自动解封。
- 实时推送：通知与匹配成局已通过 WebSocket 推送（`doc/2610295_实时推送设计方案.md`）；匹配命令仍走 REST，判题状态与断线事件重放未接入。
- 仍未实现：赛季、赛事申诉与成绩导出、代码相似度判定。
