# 性能压测与索引收口

> 日期：2026-11-05
> 状态：v1 已实现（压测脚本、慢查询采集、索引迁移）
> 关联：`2611012_架构与性能收口.md`、`2611051_可观测性落地方案.md`、`2611031_服务器部署方案.md`

## 1. 目标

`2611012` 已补上 HTTP 指标、连接池上限与首页查询并行，但缺少三项可验证的性能基础：

- 没有可重复的负载脚本，容量只能靠主观感受；
- 没有慢 SQL 采集，数据库侧的瓶颈只能靠猜；
- 提交记录、通知等列表查询缺少与排序完全匹配的复合索引。

本次补齐这三点，不改变任何接口行为，也不调整业务逻辑。压测覆盖读路径；判题吞吐仍由独立 Worker 与沙箱决定，不在本次范围内。

## 2. 新增与修改文件

| 文件 | 作用 |

## 3. 压测设计

### 3.1 场景

| 场景 | 默认并发 | 请求 |
|---|---|---|
| `browse` | 10 VU | 题库列表、难度筛选、随机题目详情 |
| `read` | 8 VU | 首页概览、`/auth/me`、通知列表与未读数、论坛列表/详情、个人提交记录、排行榜 |
| `submit` | 1 VU，默认关闭 | `POST /api/submissions`，每次提交后等待 10 秒 |

`setup()` 只登录一次并把 JWT 放进 VU 共享数据。单设备登录下，同一账号重复登录会让先前的 token 失效，因此读场景不能在 VU 内自行登录；`submit` 场景为每个 VU 分配独立账号，同样在 `setup()` 中顺序登录。

### 3.2 安全约定

- 使用专用压测账号，脚本不打印账号、密码或 token；
- 真实提交默认关闭，启用后写入提交记录、占用判题队列与沙箱；
- 不在比赛、作业截止与判题高峰期运行；
- 文档与脚本不写入真实凭据，运行参数由环境变量传入。

### 3.3 阈值

默认阈值面向 2 核 4 GB 单机：失败率 < 1%、检查通过率 > 99%、全局 P95 < 800 ms、P99 < 2000 ms，主要列表接口 P95 < 500 ms。换机器或调大并发后应重新校准，不能为了跑绿而直接放宽。

请求统一使用无空格的 `name` 标签（如 `problems-list`），避免查询参数把时间序列拆散，也便于按接口设置阈值。

## 4. 慢查询采集

### 4.1 PostgreSQL 配置

`deploy/compose.yaml` 为 `postgres` 增加：

```yaml
command:
  - postgres
  - -c
  - shared_preload_libraries=pg_stat_statements
  - -c
  - pg_stat_statements.max=1000
  - -c
  - pg_stat_statements.track=all
```

`shared_preload_libraries` 只能在启动时生效，升级后首次 `docker compose up -d` 会重建 postgres 容器；这是本版本唯一一次数据库进程重启。

扩展本身不放进迁移：本地开发使用宿主机 PostgreSQL，可能没有安装 contrib 或没有配置预加载，迁移失败会阻塞整个启动流程。因此改为一次性脚本：

```bash
cd deploy
./scripts/pg_stats.sh enable
./scripts/pg_stats.sh reset --yes   # 清空历史，开始新一轮采样
./scripts/pg_stats.sh --limit 30    # 按累计执行时间查看 Top SQL
```

脚本会先检查 `current_setting('shared_preload_libraries')`，未生效时提示重建容器，不会静默执行失败。`theseus` 是 Compose 初始化的超级用户，可以执行 `CREATE EXTENSION`。

### 4.2 输出字段

| 字段 | 含义 |
|---|---|
| `total_ms` / `mean_ms` | 累计与平均执行时间 |
| `calls` | 调用次数，用于区分“慢但少”和“快但多” |
| `rows` | 返回或影响的行数 |
| `cache_hit_pct` | 共享缓冲区命中率，偏低说明工作集超出内存 |
| `query` | 归一化后的 SQL（参数显示为 `$1`），截断到 150 字符 |

SQL 使用绑定参数，`query` 中不包含用户密码、邮箱或源码。

## 5. 索引收口

### 5.1 提交记录

`GET /api/submissions` 有两种排序查询：

```sql
WHERE user_id = $1 ORDER BY submitted_at DESC, id DESC
WHERE user_id = $1 AND problem_id = $2 ORDER BY submitted_at DESC, id DESC
```

原有索引：

- `idx_submissions_user_id (user_id)`：只能定位用户，无法提供排序；
- `idx_submissions_user_time (user_id, submitted_at DESC)`：能按时间取数，但缺少 `id` 稳定次序，按题筛选时还要回表过滤 `problem_id`；
- `idx_submissions_problem_id (problem_id)`：题目维度，不适合个人列表。

`0045` 新增：

```sql
CREATE INDEX idx_submissions_user_recent
    ON submissions (user_id, submitted_at DESC, id DESC);
CREATE INDEX idx_submissions_user_problem_recent
    ON submissions (user_id, problem_id, submitted_at DESC, id DESC);
```

同时删除 `idx_submissions_user_time`（被前者覆盖）与 `idx_submissions_user_id`（新索引的最左前缀），避免同能力索引重复维护。

### 5.2 通知列表

`GET /api/notifications` 的排序是 `ORDER BY created_at DESC, id DESC`，而原索引 `idx_notifications_user (user_id, read_at, created_at DESC)` 把 `read_at` 放在第二列：

- “仅未读”查询可以按索引顺序取数；
- 全部通知列表必须先取出该用户全部行再排序。

新增 `idx_notifications_user_recent (user_id, created_at DESC, id DESC)` 服务全部通知列表；原索引保留，继续服务未读筛选与未读计数。

### 5.3 论坛帖子流

`0032_forum_interview_board.sql` 已创建 `idx_forum_posts_board_feed (board, status, is_pinned DESC, created_at DESC)`，与 `GET /api/forum/posts` 的过滤和排序基本一致。本次不重复创建索引；`id DESC` 只在 `created_at` 完全相同时才影响顺序，收益不足以重建现有索引。

### 5.4 迁移注意

- 普通 `CREATE INDEX` 会短暂阻塞写入，建议低峰期升级；数据量很大时可先手工 `CREATE INDEX CONCURRENTLY`，迁移中的 `IF NOT EXISTS` 会跳过已存在的索引；
- `DROP INDEX` 只删除被覆盖的索引，不涉及数据；
- 迁移不包含 `CREATE EXTENSION`，原因见 4.1。

## 6. 本地验证

### 6.1 方法

在本地开发库的事务中插入合成数据并执行 `EXPLAIN (ANALYZE, BUFFERS)`，结束时 `ROLLBACK`，不修改迁移状态、不留下测试数据：

- 100,000 条提交记录，分布在 27 个现有用户与 100 道题；
- 50,000 条通知，分布在 27 个用户；
- 手工执行与 `0045` 相同的 DDL，并删除被覆盖的旧索引；
- 每条查询执行一次，记录 `Execution Time`。

### 6.2 结果

| 查询 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 个人提交列表（`user_id`，取 20 条） | 0.087 ms，`idx_submissions_user_time` + 小排序 | 0.078 ms，`idx_submissions_user_recent` 顺序扫描 | 基本持平，去掉排序步骤 |
| 个人某题提交列表 | 0.361 ms，`user_id` / `problem_id` 位图交集 + top-N 排序 | 0.064 ms，`idx_submissions_user_problem_recent` | 约 5.6 倍 |
| 个人某题提交计数 | 0.313 ms，位图交集 | 0.053 ms，复合索引位图扫描 | 约 5.9 倍 |
| 通知列表（取 20 条） | 1.336 ms，取全部 3708 条后 top-N 排序 | 0.032 ms，`idx_notifications_user_recent` 顺序扫描 | 约 42 倍 |

个人提交列表本身已有按时间排序的旧索引，因此提升有限；按题筛选与通知列表才是主要收益。结果说明执行计划已从“过滤 + 排序”变为“按索引顺序取前 N 行”。

这些数字来自本地合成数据，只用于确认索引被正确使用，不代表线上吞吐。不同数据分布、缓存命中率与硬件会得到不同绝对值；上线后应按第 7 节重新采集。

## 7. 上线后的对比流程

```bash
cd /opt/theseus
git pull
./update.sh                 # 应用 0045，并重建 postgres 以加载 pg_stat_statements

cd deploy
./scripts/pg_stats.sh enable
./scripts/pg_stats.sh reset --yes

K6_USERNAME='loadtest-user' K6_PASSWORD='<密码>' \
  K6_SUMMARY_OUT=/tmp/k6-after.json \
  k6 run load/k6-theseus.js

./scripts/pg_stats.sh --limit 30 | tee /tmp/pg-after.txt
```

若需要“优化前”数据，可先在旧版本、旧索引与同一份数据上执行相同命令；已有生产数据无法回退时，以 `pg_stat_statements` 的 `mean_ms` 与 `EXPLAIN` 计划变化作为主要依据。

## 8. 结果解读

- 失败率上升、延迟不变：先查认证与提交限流、`DB_MAX_CONNECTIONS`；
- 延迟随并发线性上升但 CPU 未满：多为连接池排队或锁等待，查 `pg_stat_activity`；
- 队列长度持续增长：`submit` 场景超过 Worker 处理能力，降低提交并发或增加 Worker；
- 单个接口 P95 偏高：用 `pg_stats.sh` 找到 SQL，再用 `EXPLAIN (ANALYZE, BUFFERS)` 确认索引与实际行数；
- 通知或提交列表再次变慢：先确认统计信息是否过期，必要时 `ANALYZE`，再评估是否需要新增索引。

## 9. 已知限制

- 压测脚本覆盖 HTTP 读路径与提交入队，不测量编译、运行与判题耗时；
- 合成数据只用于验证计划，不能替代真实数据分布下的容量结论；
- `pg_stat_statements` 有少量固定开销，且统计在重启后清空；需要长期对比时应定期导出；
- 未引入 k6 分布式执行、火焰图与数据库自动索引建议；
- 论坛全文搜索仍走 `ILIKE`，本次未引入 `pg_trgm`，大表搜索仍可能成为瓶颈；
- 只覆盖单机单实例，多实例下的连接池与队列指标需要另行聚合。
