# 服务器部署方案（Docker Compose 单机）

> 日期：2026-10-30
> 状态：v1 已实现（构建文件、健康检查、备份/恢复脚本）；实际上线需在目标服务器执行
> 关联：`2610241_运行代码功能设计方案.md`、`2610303_审计中心设计方案.md`

## 1. 目标与拓扑

面向一台 Linux 服务器的单机部署：PostgreSQL、Redis、API、判题 Worker、防作弊 Worker、语义补全网关与前端 Nginx 由 Compose 编排；判题 Worker 通过挂载宿主机的 `docker.sock` 启动 gVisor 沙箱。API 与两个 Worker 共用同一镜像，靠 `command` 区分；语义补全网关使用独立镜像（内置 clangd 与 pyright）。

```text
                 ┌──────────────────────────────┐
  用户 ── HTTPS ──▶ 宿主机 Nginx / Caddy（TLS）   │
                 └──────────────┬───────────────┘
                                │ 127.0.0.1:8080
                 ┌──────────────▼───────────────┐
                 │ frontend（Nginx 容器）        │
                 │ 静态资源 + /api、/uploads 反代 │
                 └──────────────┬───────────────┘
                                │ backend:3000
        ┌───────────────────────┼────────────────────────┐
        │                       │                        │
   backend（API）         judge-worker            anticheat-worker
        │                       │                        │
        ├──────────┬────────────┴───────────┬────────────┘
        ▼          ▼                        ▼
   postgres     redis                宿主机 Docker + runsc
   (volume)     (volume)              runner-{python,node,cpp,java}
```

- 只有前端端口对外（默认 `8080`）；PostgreSQL、Redis、API、语义补全网关均不发布端口。
- 上传文件保存在 `theseus_uploads` 卷；数据库与 Redis 各自独立卷。
- 前端与 API 同源，避免 CORS；`/api/ws` 与 `/api/lsp/ws` 由前端 Nginx 升级为 WebSocket，后者反代到 `lsp:3001`。

## 2. 新增文件

| 文件 | 作用 |
| --- | --- |
| `backend-rust/Dockerfile` | 多阶段构建 API / judge_worker / anticheat_worker，运行镜像内置 docker CLI；另有 `lsp` 阶段构建语义补全镜像 |
| `backend-rust/.dockerignore` | 排除 `target/`、`.env`、上传目录 |
| `frontend-vue/Dockerfile` | Node 构建 + Nginx 托管 |
| `frontend-vue/nginx.conf` | SPA 回退、`/api` 与 `/uploads` 反代、WebSocket（含 `/api/lsp/ws`）、缓存与上传大小 |
| `deploy/compose.yaml` | 七个服务、健康检查、日志轮转、卷 |
| `deploy/.env.example` | 生产环境变量模板 |
| `deploy/scripts/backup.sh` | 数据库 + uploads 备份，按天保留 |
| `deploy/scripts/restore.sh` | 停止应用、恢复数据库与 uploads、重新启动 |
| `deploy/scripts/promote-admin.sh` | 把已注册用户提升为管理员 |
| `update.sh` | 服务器增量更新：更新前备份、构建镜像、先迁移数据库、再启动全部服务并核对健康状态 |

API 新增 `GET /healthz`（仅进程存活）与 `GET /readyz`（检查 PostgreSQL；启用判题时检查 Redis），供 Compose 健康检查与外部探活使用。

语义补全网关 `lsp` 使用独立镜像，内置 clangd、g++、python3 与 pyright；不发布端口，仅由前端 Nginx 反代 `/api/lsp/ws`。每个在线会话启动一个语言服务器进程，`LSP_MAX_SESSIONS`（默认 4）限制并发，内存紧张的服务器可调低到 2。补全开关由用户手动开启，比赛模式下前端禁用；`LSP_ENABLED=false` 时 API 不再签发票据。

## 3. 服务器准备

最低建议：2 核 4 GB、40 GB 磁盘；2 核 2 GB 也可运行，但需按 3.4 开启 swap 并降低编译/判题并发。判题并发高时按 CPU 增加 `RUN_WORKER_CONCURRENCY` 或另设评测机。

可以在服务器仓库根目录执行：

```bash
./build_env.sh runtime
```

脚本只搭建运行环境：安装 Docker 与 Compose、在内存小于 8 GB 时创建 4 GB swap、构建 judge runner 镜像、生成带随机密码与 JWT 密钥的 `deploy/.env`，不会安装 Rust / Node / PostgreSQL / Redis，也不会启动服务。gVisor（runsc）仍需按 3.2 手动安装；脚本检测不到 runsc 时会给出提示。

以下为手动步骤。

### 3.1 Docker 与 Compose

```bash
# Ubuntu 24.04 仓库版本
sudo apt update
sudo apt install -y docker.io docker-compose-v2
sudo systemctl enable --now docker

docker --version
docker compose version
```

如果发行版没有 `docker-compose-v2`，按 Docker 官方文档安装 Compose 插件。要求 Compose v2（`docker compose` 子命令），不支持旧的 `docker-compose`。

### 3.2 gVisor（runsc）

生产环境必须使用 `runsc`；代码默认拒绝回退到 `runc`。安装方式以 gVisor 官方文档为准，常见步骤如下：

```bash
curl -fsSL https://gvisor.dev/archive.key \
  | sudo gpg --dearmor -o /usr/share/keyrings/gvisor-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/gvisor-archive-keyring.gpg] \
https://storage.googleapis.com/gvisor/releases release main" \
  | sudo tee /etc/apt/sources.list.d/gvisor.list
sudo apt update && sudo apt install -y runsc
sudo runsc install
sudo systemctl restart docker

# 验证
docker run --rm --runtime=runsc hello-world
```

仅做本机联调时可临时使用 `RUN_SANDBOX_RUNTIME=runc` 与 `RUN_SANDBOX_ALLOW_RUNC=true`，不要用于公网环境。

### 3.3 判题运行镜像

Worker 通过宿主机 Docker 启动沙箱，因此运行镜像要构建在宿主机上：

```bash
cd /opt/theseus
sudo bash backend-rust/scripts/build_runtime_images.sh
```

脚本会构建 `theseus/runner-python:dev`、`runner-node:dev`、`runner-cpp:dev`、`runner-java:dev`。生产环境建议改为固定 digest 的镜像并推到私有仓库，再修改 `deploy/.env` 的 `RUN_IMAGE_*`。

### 3.4 低配服务器（2 核 2 GB）

2 核 2 GB 可以跑完整服务，但要避免构建阶段 OOM：

- **swap**：`./build_env.sh runtime` 会在内存小于 8 GB 且未启用 swap 时自动创建 4 GB `/swapfile` 并写入 `/etc/fstab`。确认：`free -h`、`swapon --show`。
- **编译并发**：后端镜像默认 `CARGO_BUILD_JOBS=1`（`deploy/.env` 可调）。首次 `docker compose build` 可能需要 20–40 分钟，属正常。
- **判题并发**：`RUN_WORKER_CONCURRENCY=1`，避免 Java 等运行时同时占用过多内存。
- **磁盘**：至少 40 GB；4 个 runner 镜像加判题沙箱占用明显，可用 `docker system df` 查看。
- **CPU**：经济型 e 实例为共享 CPU，判题延迟会有波动；对延迟敏感时另设评测机。
- **可选**：在本地或 CI 构建 `theseus/backend`、`theseus/frontend` 并推到 ACR，服务器只 `docker compose pull`，可完全避开 2 GB 上的编译。

**中国大陆网络**：官方 Debian/Ubuntu 软件源、GitHub 与 Maven Central 可能超时，构建前指定镜像：

```bash
export APT_MIRROR=mirrors.aliyun.com
export JSON_URL=https://cdn.jsdelivr.net/gh/nlohmann/json@v3.11.3/single_include/nlohmann/json.hpp
export GSON_URL=https://maven.aliyun.com/repository/public/com/google/code/gson/gson/2.11.0/gson-2.11.0.jar
./build_env.sh runtime
```

运行镜像构建完成后，在 `deploy/.env` 中设置 `APT_MIRROR=mirrors.aliyun.com`、`CARGO_MIRROR=https://rsproxy.cn/index/`、`NPM_REGISTRY=https://registry.npmmirror.com`，`docker compose build` 会把这些参数透传给后端与前端镜像。

构建被 `Killed`（退出码 137）几乎都是内存不足：`dmesg -T | grep -i oom` 确认，再检查 swap 是否生效或改用外部构建。

## 4. 首次部署

私有仓库需要先为服务器配置只读 Deploy Key（仓库 Settings → Deploy keys，添加服务器的 `~/.ssh/id_ed25519.pub` 或专用部署公钥，不要勾选写入权限），否则 `git clone` 会停在认证。

```bash
sudo mkdir -p /opt/theseus && sudo chown "$USER" /opt/theseus
git clone <repository> /opt/theseus
cd /opt/theseus/deploy

cp --no-clobber .env.example .env
chmod 600 .env
# 编辑 .env：
#   POSTGRES_PASSWORD   强随机密码
#   JWT_SECRET          openssl rand -base64 48
#   FRONTEND_BASE_URL   对外访问地址，如 https://oj.example.com
#   EMAIL_*             生产 SMTP
#   HTTP_PORT           前端监听端口，默认 8080
#   VITE_SUBMIT_JUDGE_ENABLED  前端提交按钮开关，修改后需重建前端镜像
```

构建并启动：

```bash
docker compose build
docker compose up -d
docker compose ps
```

验证：

```bash
docker compose ps
docker compose exec -T backend curl -fsS http://127.0.0.1:3000/readyz
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
docker compose logs -f backend
```

`readyz` 返回 `{"status":"ok","database":"ok","redis":"ok"}` 即依赖正常；`503` 时看 `database` / `redis` 字段。`/healthz` 与 `/readyz` 只监听容器内部，不通过前端 Nginx 对外暴露。

### 4.1 初始化管理员

生产环境没有默认管理员，`seed_admin.sql` 仅供本地测试。流程：

1. 在前端注册一个账号并完成邮箱验证；
2. 在服务器执行：

```bash
cd /opt/theseus/deploy
./scripts/promote-admin.sh <用户名>
```

3. 用该账号登录，进入管理端。

题目可由管理员在管理端创建或审核；`seed_problems_15.sql` 只用于演示，不建议导入生产库。

### 4.2 迁移

API 启动时会执行 `sqlx` 迁移（`db::migrate`），Compose 首次启动即完成建表。升级前先备份：

```bash
./scripts/backup.sh
```

## 5. HTTPS 与反向代理

Compose 内的前端 Nginx 只负责 HTTP。公网部署建议在宿主机再放一层 Nginx/Caddy 终止 TLS，并把上游指向 `127.0.0.1:8080`。可把 `HTTP_PORT` 设为 `127.0.0.1:8080`，避免 8080 直接暴露。

宿主机 Nginx 示例：

```nginx
server {
    listen 443 ssl http2;
    server_name oj.example.com;

    ssl_certificate     /etc/letsencrypt/live/oj.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/oj.example.com/privkey.pem;

    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 300s;
    }
}

server {
    listen 80;
    server_name oj.example.com;
    return 301 https://$host$request_uri;
}
```

证书可用 Certbot；也可直接用 Caddy 自动签发。记得在云厂商安全组/防火墙只放行 22、80、443。

## 6. 备份与恢复

### 6.1 备份

```bash
cd /opt/theseus/deploy
./scripts/backup.sh
```

生成 `deploy/backups/db-<时间>.dump` 与 `uploads-<时间>.tar.gz`，默认保留 14 天（`KEEP_DAYS` 可调）。建议加入 cron，并把备份同步到另一台机器或对象存储：

```cron
15 3 * * * cd /opt/theseus/deploy && ./scripts/backup.sh >> /var/log/theseus-backup.log 2>&1
```

### 6.2 恢复

```bash
cd /opt/theseus/deploy
./scripts/restore.sh backups/db-20261030-031500.dump backups/uploads-20261030-031500.tar.gz
```

脚本会先停止 API 与两个 Worker，恢复数据库与上传卷后再启动。恢复是不可逆操作，执行前确认备份文件与目标环境。

## 7. 日常运维

```bash
cd /opt/theseus/deploy

docker compose ps                 # 服务状态
docker compose logs -f backend    # API 日志
docker compose logs -f judge-worker
docker compose restart backend    # 只重启 API

docker stats                      # 资源占用
docker system df                  # 镜像/卷占用
```

日志使用 `json-file` 驱动并限制为 10 MB × 3，避免磁盘被写满。

### 7.1 升级

```bash
cd /opt/theseus
git pull
./update.sh
```

`update.sh` 会依次：

1. 记录数据库已应用的迁移，并对比 `backend-rust/migrations/` 列出待应用项；
2. 调用 `deploy/scripts/backup.sh` 备份数据库与 uploads；
3. 构建新镜像；
4. 停止 backend 与两个 Worker，仅启动新 backend 应用增量迁移；
5. 迁移成功后启动全部服务；
6. 核对新增迁移、失败迁移与 `/readyz` 健康状态，并打印前端响应。

常用选项：`--skip-build` 使用现有镜像，`--no-backup` 跳过备份（不推荐）。

后端镜像内嵌 `migrations`，API 启动时自动执行；脚本把迁移拆成独立一步，迁移失败时不会启动 Worker 和前端，并打印 `restore.sh` 回滚命令。恢复会回到更新前备份，更新期间的写入会丢失，需人工确认后再执行。

手动升级方式仍可参考：

```bash
cd /opt/theseus
git pull
cd deploy
./scripts/backup.sh
docker compose build
docker compose up -d
docker compose ps
```

API 启动时自动跑迁移。若迁移失败，容器会退出，先看 `docker compose logs backend`，用备份回滚。

### 7.2 常见问题

| 现象 | 排查 |
| --- | --- |
| 前端 502 | `docker compose ps` 看 backend 是否 healthy；`curl 127.0.0.1:3000/readyz`（容器内） |
| `readyz` 返回 503 | 看 `database` / `redis` 字段；检查 postgres/redis 容器与密码 |
| 提交返回 503 | 没有 judge worker 心跳；看 `judge-worker` 日志与 Redis 连接 |
| 判题报 runsc 错误 | 宿主机未安装/未注册 runsc，或 `RUN_SANDBOX_RUNTIME` 与宿主机不一致 |
| 判题报镜像不存在 | 未执行 `build_runtime_images.sh`，或 `RUN_IMAGE_*` 指向了不存在的 tag |
| 邮件链接指向 localhost | `FRONTEND_BASE_URL` 未改成对外地址 |
| 头像上传失败 | uploads 卷权限或 `client_max_body_size` 过小 |
| 磁盘占满 | 清理旧镜像、日志与备份；检查 `/var/lib/docker` |

## 8. 安全清单

- [ ] `POSTGRES_PASSWORD`、`JWT_SECRET` 均为随机值，`.env` 权限 600，且未提交到 Git；
- [ ] `EMAIL_MODE=smtp`，`FRONTEND_BASE_URL` 为 HTTPS 地址；
- [ ] 只暴露 80/443（或反代端口），5432/6379/3000 不对公网开放；
- [ ] 判题机使用 `runsc`，`RUN_SANDBOX_ALLOW_RUNC=false`；
- [ ] 挂载 `docker.sock` 的 Worker 视为高权限组件，评测机不要跑其他业务；
- [ ] 开启系统防火墙与自动安全更新；
- [ ] 备份文件异地保存，定期做恢复演练；
- [ ] 管理员使用强密码；当前未实现 2FA，公网部署需评估风险。
- [ ] 容器默认以 root 运行（Worker 需要访问 `docker.sock`，API 需要写 uploads 卷）；后续可拆分非 root 运行与卷权限。

## 9. 已知限制

- Compose 方案面向单机，不包含多实例与负载均衡；WebSocket 实时推送与 API 进程绑定，横向扩容需要额外的 Pub/Sub。
- 未包含 Prometheus/Grafana 指标与告警，目前只有健康检查、结构化日志与审计日志；指标属于下一步「可观测性」。
- 未包含 CI/CD；升级依赖人工 `git pull + compose build`。
- 前端 Nginx 只提供 HTTP，TLS 由宿主机反代终止。
