# 提交代码功能设计方案

- 日期：2026-10-25
- 关联文档：[2610241_运行代码功能设计方案](./2610241_运行代码功能设计方案.md)、[2610252_编译超时的原因](./2610252_编译超时的原因.md)、[2610253_前端现状及其修复方案](./2610253_前端现状及其修复方案.md)
- 涉及代码：`backend-rust/src/handlers/submission_handler.rs`、`backend-rust/src/services/judge_service.rs`、`backend-rust/src/bin/judge_worker.rs`、`backend-rust/src/judge/*`、`frontend-vue/src/store/submissions.ts`

## 0. 结论速览

「提交代码」目前是**桩实现**：`POST /api/submissions` 在 API 进程里 `tokio::spawn` 一个假判题，睡 10ms 后直接把提交写成 `runtime_error`（`src/services/judge_service.rs`），既不进沙箱，也没有用例、没有编译、没有并发控制。

本方案把提交判题接到已经跑通的运行（Run）流水线上，并做四点关键决策：

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 隐藏用例存储 | 新增 `problems.judge_cases` JSONB 列，结构与 `run_config.public_cases` 一致；**不放进 `run_config`**（题目详情会原样返回 `run_config`） |
| 2 | 队列形态 | 同一 `judge_worker` 进程，新增独立 stream `theseus:judge:submissions` + 独立消费组；与运行队列互不挤占 |
| 3 | 结果展示 | 通过数 `X / Y` + **第一个失败用例**的输入/期望/实际；其余隐藏用例不返回 |
| 4 | 配额 | 提交独立限流与并发锁：每用户 1 并发、10 次/分钟，不占运行名额 |

判题集合 = `run_config.public_cases`（公开，运行也在用）+ `problems.judge_cases`（隐藏）。用例顺序公开在前、隐藏在后，遇到第一个不通过的用例即停止。

## 1. 现状盘点

### 1.1 现在的提交链路

```text
POST /api/submissions
  └─ submission_handler::create
       ├─ 校验 problem_id / language / code 非空（≤512KB）
       ├─ SELECT jsonb_array_length(problems.test_cases)   // 仅用于总数
       ├─ INSERT submissions (status='pending')
       ├─ UPSERT user_problem_status (attempted)
       └─ tokio::spawn(judge_service.judge_submission)
            ├─ UPDATE submissions SET status='judging'
            ├─ sleep(10ms)
            └─ UPDATE submissions SET status='runtime_error',
                 error_message='评测器尚未配置，请稍后重试'
```

前端 `store/submissions.ts` 每 1s 轮询 `GET /api/submissions/{id}`，60s 超时；`OjPage.vue` 的「提交代码」按钮与运行结果共用右侧输出面板。

### 1.2 可以直接复用的运行链路

运行功能（2610241）已经把判题需要的基础设施全部建好：

| 能力 | 现有实现 |
|---|---|
| 沙箱 | `judge/runner.rs::SandboxSession`：一容器一次任务、只读根、tmpfs、uid 65534、断网、CPU/内存/PID 限制、编译独立预算 |
| 代码注入与产物读取 | `write_to_container` / `read_from_container`（`docker exec`，避开 `docker cp` 与 tmpfs 的不兼容） |
| 语言 harness | `judge/harness/{python,javascript,cpp,java}.rs`，按 `run_config` 生成 runner |
| 输入/比较 | `run_config::validate_input`、`normalize_for_compare`；`compare::values_match`（exact / double 容差） |
| 队列 | `judge/queue.rs`：XADD / XREADGROUP / XACK / XAUTOCLAIM / 死信 / 心跳 / 状态缓存 |
| 幂等终态 | `run_service::finish_run` 的条件 UPDATE：终态不可覆盖 |
| 重试 | `attempt_count` + `RUN_MAX_DELIVERIES` + 死信流 + 锁释放 |
| 限流/并发锁 | `INCR` 分钟桶 + `SET NX EX` 用户锁 + Lua CAS 释放，TTL 按任务实际预算推导 |
| 过期回收 | API 侧 `reaper_loop`：queued 超时 / running 卡死 → `internal_error` 并释放锁 |

### 1.3 现有缺口

| 缺口 | 说明 |
|---|---|
| 没有判题执行 | 不创建沙箱、不编译、不用例比较 |
| 用例格式不兼容 | `problems.test_cases` 是 `{"input": "[1,3]\n[2]", "output": "2.0"}` 字符串，harness 需要结构化 `args` / `expected` |
| 无快照 | 判题过程中题目被改，结果就不可复现（`submissions` 没有 `run_config_snapshot`） |
| 无重试/回收 | 只有进程内 spawn，API 重启即丢；无死信 |
| 无队列隔离 | 提交和运行共用 API 进程，无法限流与背压 |
| 状态缺项 | `submissions.status` 的 CHECK 里没有 `internal_error` |
| 结果粒度不足 | 只有通过数，无法看到具体失败用例；也没有 `compile_output` |
| 提交无独立的并发/限流 | 目前完全不受控，可被刷接口 |
| 轮询负载重 | 前端每 1s 拉整条提交详情（含 `code`） |

## 2. 目标与非目标

### 2.1 目标

1. 提交异步判题：API 只做校验、配额、落库、入队；执行全部在 `judge_worker`。
2. 复用运行沙箱与四语言 harness，不为提交另写一套执行器。
3. 判题依据可复现：入库时冻结 `run_config` 与隐藏用例快照。
4. 结果可信：编译错误、超时、OOM、运行时错误分别映射；`accepted` 才更新通过率。
5. 隐藏用例不外泄：不进入 Redis 消息、不进日志、API 只返回首个失败用例。
6. 提交与运行互不影响：独立队列、独立配额、独立监控。
7. 可靠性对齐运行：幂等终态、超时回收、重试上限、死信、锁必然释放。

### 2.2 非目标（本期不做）

- 排行榜、反作弊、代码查重、相似度检测；
- 部分分/权重/子任务、Special Judge、交互题、多返回值；
- 提交代码 diff、失败用例下载；
- 管理端 `judge_cases` 可视化编辑器（本期只提供 API，暂无后台页面）；
- 跨机调度与独立扩缩容。

## 3. 总体架构与流程

### 3.1 组件职责

```text
┌────────────┐   POST /api/submissions    ┌───────────────────────┐
│  frontend  │ ─────────────────────────► │  API (Axum)           │
│  Vue 3     │ ◄───────────────────────── │  submit_service       │
└────────────┘   GET .../status / detail  └───────┬───────────────┘
                                                │ XADD submission_id
                                                ▼
                                      theseus:judge:submissions
                                                │ XREADGROUP
                                                ▼
                                      ┌───────────────────────┐
                                      │ judge_worker          │
                                      │  submission_consumer  │
                                      │  submission_claimer   │
                                      │  SandboxSession       │
                                      └───────┬───────────────┘
                                              │ UPDATE submissions / problems
                                              ▼
                                        PostgreSQL
```

- API 进程**不执行任何用户代码**，也不读隐藏用例（只做存在性/数量校验）。
- 隐藏用例只在 Worker 消费时从数据库读取，并冻结进 `submissions.judge_cases_snapshot`。
- 运行与提交共用同一个 worker 进程、同一批沙箱配置、同一套镜像与编译预算。

### 3.2 提交流程（API 侧）

```text
authenticate
  → 功能开关 SUBMIT_JUDGE_ENABLED（关闭返回 503）
  → 校验请求：problem_id / language / code 非空且 ≤64KB
  → 查题目：必须 approved，且 run_config、judge_cases 可用
  → has_live_submit_worker（SCAN 心跳键，缺失返回 503）
  → 提交限流：theseus:submit:rate:{user}:{minute}，10 次/分钟（超限 429）
  → 并发锁：SET theseus:submit:concurrency:{user} = token NX EX ttl
  → INSERT submissions（status='pending'，含两份快照）
  → 锁 token 换成 submission_id（防 XADD 失败时误释放）
  → XADD {stream} {submission_id}
      ├─ 成功：写状态缓存，返回 { submission_id, status: 'pending' }
      └─ 失败：条件更新 internal_error + 释放锁 + 返回 503
```

与 `run_service::create` 保持一致的关键点：

- 消息体**只有 `submission_id`**，不带代码/输入/用例。
- 题目必须在 `pending` 之外的 `approved` 状态；`judge_cases` 为空但 `public_cases` 可用也允许判题（判题集合 = 公开 + 隐藏）。
- 并发锁的 TTL 用同一套推导：`排队 + 编译 + 判题总预算 + 30s`。

### 3.3 判题流程（Worker 侧）

```text
读消息 → fetch_submission_row
  ├─ 终态 → 直接 ACK，跳过
  ├─ 语言无沙箱 / 快照无效 → 条件更新 internal_error，ACK
  ├─ claim：UPDATE submissions SET status='judging', started_at=now
  │          WHERE id=$1 AND status='pending'   // 0 行表示已被别人领走
  ├─ 写状态缓存 judging
  ├─ program_for(language, code, run_config_snapshot)
  ├─ SandboxSession::start（含编译，使用 60s / 1024MB 编译预算）
  │    └─ 编译失败 → compile_error + compile_output
  ├─ 按 [公开用例..., 隐藏用例...] 顺序逐个 run_case
  │    ├─ 每个用例 timeout = min(2s, 判题总预算剩余)
  │    ├─ 第一个不通过 → 记录并停止（剩余标记 unrun）
  │    └─ 每跑完一个更新状态缓存（已通过数 / 总数）
  ├─ shutdown 容器
  └─ 聚合 verdict → 单事务写终态：
       UPDATE submissions ... WHERE id=$1 AND status IN ('pending','judging')
       ├─ 1 行：更新 problems 计数 + user_problem_status，写缓存，释放锁，ACK
       └─ 0 行：已被终态/回收处理，释放锁，ACK
```

### 3.4 端到端时序

```text
用户点击提交
  → POST /api/submissions           201 { submission_id, status: pending }
  → 前端每 800ms GET /submissions/{id}/status
  → Worker 消费：pending → judging
  → Worker 写终态（accepted / wrong_answer / ...）
  → 前端看到终态：GET /submissions/{id} 拉详情（首个失败用例 / 编译输出）
  → 输出面板展示，个人中心列表同步出现新记录
```

## 4. 数据模型

### 4.1 隐藏用例 `problems.judge_cases`

```json
[
  {"args": [[3, 2, 4], 6], "expected": [1, 2]},
  {"args": [[3, 3], 6], "expected": [0, 1]}
]
```

- 格式与 `run_config.public_cases` 完全一致，直接复用 `value_matches_type` 校验。
- 保存题目时校验：
  - `args` 长度与 `params` 一致、每个参数类型匹配；
  - `expected` 与 `return_type` 匹配；
  - 隐藏用例 ≤ 50 条，与公开用例合计 ≤ 50 条；
  - 序列化后 ≤ 256KB。
- `run_config` 为空时不允许配置 `judge_cases`（没有签名无法判题）。
- **不出现在任何用户接口**：题目详情沿用现有 `ProblemResponse`（本来就不含 `test_cases`），本次也不加 `judge_cases`。

### 4.2 `submissions` 变更（migration `0003_submission_judge.sql`）

```sql
ALTER TABLE problems ADD COLUMN IF NOT EXISTS judge_cases JSONB;

ALTER TABLE submissions
    ADD COLUMN IF NOT EXISTS run_config_snapshot JSONB,
    ADD COLUMN IF NOT EXISTS judge_cases_snapshot JSONB,
    ADD COLUMN IF NOT EXISTS cases JSONB NOT NULL DEFAULT '[]'::jsonb,
    ADD COLUMN IF NOT EXISTS compile_output TEXT,
    ADD COLUMN IF NOT EXISTS attempt_count INTEGER NOT NULL DEFAULT 0,
    ADD COLUMN IF NOT EXISTS started_at TIMESTAMPTZ,
    ADD COLUMN IF NOT EXISTS finished_at TIMESTAMPTZ;

ALTER TABLE submissions DROP CONSTRAINT IF EXISTS submissions_status_check;
ALTER TABLE submissions ADD CONSTRAINT submissions_status_check
    CHECK (status IN (
        'pending', 'judging', 'accepted', 'wrong_answer',
        'time_limit_exceeded', 'memory_limit_exceeded',
        'runtime_error', 'compile_error', 'internal_error'
    ));
```

说明：

- `run_config_snapshot` / `judge_cases_snapshot` 在创建提交时写入；之后管理员改题不影响已排队/已完成的提交。
- `cases` 存执行过的用例结果（结构同 `RunCaseResult`），用于管理端排障；用户接口按 §5.3 的策略过滤。
- `runtime` / `memory` 沿用现有 INTEGER 列（毫秒 / KB），不改名，避免前端类型大改。
- `total_test_cases` 在创建时写入判题集合大小（公开 + 隐藏），不是旧 `test_cases` 的长度。
- 旧列 `problems.test_cases` 保留但**停止使用**（格式不兼容 harness），后续可单独清理。
- 不修改 `submissions.problem_id` 的外键：已确认题目删除时提交历史一起删除（`ON DELETE CASCADE`），详见 §10。

### 4.3 状态机

```text
pending ──► judging ──┬──► accepted
                      ├──► wrong_answer
                      ├──► time_limit_exceeded
                      ├──► memory_limit_exceeded
                      ├──► runtime_error
                      ├──► compile_error
                      └──► internal_error（重试耗尽 / 回收 / 快照损坏）

pending ──► internal_error（排队超时回收）
```

- 所有终态写入都用 `WHERE status IN ('pending','judging')` 条件更新，终态不可覆盖。
- `internal_error` 不计入用户错误，也不更新 `problems` 计数。
- `judging` 阶段若 Worker 崩溃，消息留在 PEL，`XAUTOCLAIM` 120s 后重新投递（`attempt_count + 1`）。

## 5. 接口设计

### 5.1 创建提交 `POST /api/submissions`

请求体不变：

```json
{"problem_id": 1001, "language": "cpp", "code": "class Solution { ... }"}
```

响应不变（前端无需改解析）：

```json
{"submission_id": 12, "status": "pending", "message": "提交成功，正在评测中"}
```

新增错误：

| 场景 | 状态码 | 文案 |
|---|---|---|
| 开关关闭 / 无存活 Worker / 入队失败 | 503 | 评测服务暂不可用，请稍后再试 |
| 题目未审核 / 无 `run_config` / 无任何用例 | 400 | 该题暂不支持提交评测 |
| 限流 | 429 | 每分钟最多提交 10 次，请稍后再试（`Retry-After`） |
| 已有评测中的提交 | 429 | 有提交正在评测中，请稍后再试 |

行为变更：

- 代码上限从 512KB 收紧到 **64KB**（与运行一致；正常题解远小于此）。
- 删除 `tokio::spawn(judge_service)`，改为入队。
- 创建时的 `user_problem_status` 更新保留（`attempted`），`accepted` 由判题终态写入。
- `total_test_cases` 由判题集合大小决定。

### 5.2 轮询状态 `GET /api/submissions/{id}/status`（新增）

轻量接口，前端轮询专用（不再每 1s 拉整条详情，包括 `code`）：

```json
{
  "id": 12,
  "status": "judging",
  "test_cases_passed": 2,
  "total_test_cases": 6,
  "error_message": null,
  "updated_at": "2026-10-25T14:02:11Z"
}
```

- 权限：本人或管理员；非本人返回 403，不存在返回 404。
- 优先读 Redis `theseus:submission:status:{id}`（TTL 3600），未命中查库并回填。
- 与运行的 `/status` 保持同一形态，便于前端复用轮询逻辑。

### 5.3 提交详情 `GET /api/submissions/{id}`

在现有字段上追加：

```json
{
  "id": 12,
  "problem_id": 1001,
  "problem_title": "两数之和",
  "language": "cpp",
  "code": "class Solution { ... }",
  "status": "wrong_answer",
  "test_cases_passed": 2,
  "total_test_cases": 4,
  "runtime": 12,
  "memory": 3120,
  "compile_output": null,
  "error_message": "输出与预期结果不一致",
  "failed_case": {
    "index": 2,
    "args": [[3, 3], 6],
    "expected": [0, 1],
    "actual": [1, 0],
    "stdout": "",
    "stderr": "",
    "status": "failed"
  },
  "submitted_at": "2026-10-25T14:02:01Z",
  "finished_at": "2026-10-25T14:02:03Z"
}
```

`failed_case` 规则：

- 只返回**执行到的第一个非通过用例**；
- `expected` 仅在 `wrong_answer` 时返回；`time_limit_exceeded` / `memory_limit_exceeded` / `runtime_error` 只返回 `args` 与 `stderr`；
- `accepted` / `compile_error` / `pending` / `judging` 时为 `null`；
- 其余隐藏用例的输入与期望永远不出现在任何用户接口中。

其它约定：

- `code` 仅本人或管理员可见（现有逻辑）。
- 列表接口 `GET /api/submissions` 不再返回 `code`（当前每条都带完整代码，响应很重）；详情保留。

### 5.4 管理端

- `POST /api/admin/problems`、`PUT /api/admin/problems/{id}` 请求体新增 `judge_cases`。
- 校验规则见 §4.1；校验失败返回 400，并在文案中指出第几条用例的哪个字段。
- 新增 `GET /api/admin/problems/{id}`：返回完整题目（含 `test_cases`、`judge_cases`），否则管理员编辑题目时拿不到用例，PUT 会把它们清空（现有 PUT 对 `test_cases` 就是覆盖式写入）。
- `PUT` 对 `judge_cases` 采用「未提供则保持原值」，避免误清空。

### 5.5 配置

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `SUBMIT_JUDGE_ENABLED` | `false` | 提交评测总开关（关闭时创建接口 503） |
| `SUBMIT_STREAM` | `theseus:judge:submissions` | 提交队列 |
| `SUBMIT_CONSUMER_GROUP` | `judge-submit-workers` | 消费组 |
| `SUBMIT_DEAD_STREAM` | `theseus:judge:submissions:dead` | 死信流 |
| `SUBMIT_MAX_DELIVERIES` | `3` | 最大投递次数 |
| `SUBMIT_QUEUE_TIMEOUT_SECS` | `90` | 排队超时（回收） |
| `SUBMIT_STALE_TIMEOUT_SECS` | `300` | judging 卡死回收 |
| `SUBMIT_RUN_TIMEOUT_SECS` | `60` | 判题执行总预算（不含编译） |
| `SUBMIT_MAX_CASES` | `50` | 单题判题用例上限 |

复用现有 `RUN_SANDBOX_*`、`RUN_IMAGE_*`、`RUN_COMPILE_TIMEOUT_SECS`、`RUN_COMPILE_MEMORY_MB`、`RUN_WORKER_NAME`、`RUN_WORKER_CONCURRENCY`。
前端新增 `VITE_SUBMIT_JUDGE_ENABLED`（默认 `false`，仅控制入口提示，后端为准）。

## 6. 队列与 Worker

### 6.1 Redis Streams

`judge/queue.rs` 的函数都是 stream 参数化的，可直接复用：

- `ensure_group`：Worker 启动时对提交流建组（`MKSTREAM` 幂等）；
- `enqueue(stream, id)`：消息体只有 `submission_id`；
- `read_one` / `ack`：消费循环与运行一致；
- `claim_stale`：`XAUTOCLAIM`，`min_idle = 120s`；
- `enqueue_dead`：超过 `SUBMIT_MAX_DELIVERIES` 写死信。

新增键：

| Key | 类型 | 说明 |
|---|---|---|
| `theseus:submit:rate:{user_id}:{minute}` | string | 分钟桶限流，TTL 120s |
| `theseus:submit:concurrency:{user_id}` | string | 用户并发锁，值为 submission_id |
| `theseus:submission:status:{id}` | string(JSON) | 状态缓存，TTL 3600s |
| `theseus:submit:worker:{name}` | string | 提交 Worker 心跳，TTL 30s |

### 6.2 幂等

- 创建：先 `SET NX EX` 锁，再插库，再入队；入队失败时条件更新 `internal_error` 并释放锁。
- 消费：先查终态，终态直接 ACK；再 `claim`（`pending → judging`）；只有 `claim` 成功的 Worker 执行。
- 终态：条件 `UPDATE ... WHERE status IN ('pending','judging')`，返回 0 行说明已被处理，不重复计数。
- 计数：`problems` 与 `user_problem_status` 的更新放在**同一事务**里，且只在终态更新命中 1 行时执行。

### 6.3 重试与死信

与运行完全一致：

```text
沙箱启动失败 / 读取容器异常 → 不改状态，直接返回（消息留在 PEL）
  → 120s 后 XAUTOCLAIM 重新投递
  → 每次领取 attempt_count + 1
  → attempt_count > SUBMIT_MAX_DELIVERIES
       → 写死信流 + internal_error + 状态缓存 + 释放锁 + ACK
用户代码导致的失败（编译错误、WA、TLE、OOM、RE）→ 正常终态，不重试
```

### 6.4 并发模型

`judge_worker` 当前按 `RUN_WORKER_CONCURRENCY` 起 N 个运行消费者。如果提交再起 N 个，最坏会同时开 2N 个容器，把 CPU/内存吃满（编译阶段单个容器可到 1GB）。

方案：**全进程共享一个 `tokio::Semaphore`**：

```text
RUN_WORKER_CONCURRENCY = 2   // 同时最多 2 个沙箱（运行 + 提交共享）
```

- 运行消费循环与提交消费循环在 `SandboxSession::start` 前 `acquire()`，结束后自动释放；
- 排队等待发生在 Worker 内部，消息仍留在 PEL，不影响回收；
- 如果暂时不想改运行循环，也可以先给提交循环单独限 1 个并发，但共享信号量更干净，推荐一起改。

### 6.5 心跳与 503

- 心跳循环同时刷新 `theseus:run:worker:{name}` 与 `theseus:submit:worker:{name}`。
- 创建提交时 `SCAN theseus:submit:worker:*`，没有存活键返回 503——避免「API 正常但没人消费」时用户提交后一直排队。
- 发布顺序必须是 **先升级 Worker，再开 `SUBMIT_JUDGE_ENABLED`**，否则新 Worker 还没跑起来时心跳检查会直接挡住（这是期望行为，不是故障）。

## 7. 判题与结果

### 7.1 用例构建

```text
judge_set = run_config_snapshot.public_cases（公开）
          + judge_cases_snapshot（隐藏）
```

- 公开在前：常见错误（空实现、示例都过不了）会在前几个用例就失败，隐藏用例只执行必要的部分。
- 任一侧都为空，或合计为 0 → 创建阶段就拒绝（400）。
- 每条用例在消费时再用 `value_matches_type` 校验一次（防止历史数据不合法），失败则 `internal_error`。

### 7.2 执行预算

| 阶段 | 预算 | 来源 |
|---|---|---|
| 编译 | 60s / 1024MB | 复用 `RUN_COMPILE_*`，与运行一致 |
| 单用例 | 2s | 与运行一致 |
| 判题总执行 | 60s（`SUBMIT_RUN_TIMEOUT_SECS`） | 提交比运行更宽松，容纳多用例 |
| 排队 | 90s | `SUBMIT_QUEUE_TIMEOUT_SECS` |
| judging 卡死 | 300s | `SUBMIT_STALE_TIMEOUT_SECS` |

执行逻辑：

```text
deadline = now + SUBMIT_RUN_TIMEOUT_SECS
for case in judge_set:
    remaining = deadline - now
    if remaining <= 0: 剩余用例记为 unrun；verdict = time_limit_exceeded；break
    outcome = session.run_case(args, min(2s, remaining))
    if outcome.timed_out: verdict = time_limit_exceeded; break
    if outcome.oom:        verdict = memory_limit_exceeded; break
    if outcome 无 result.json: verdict = runtime_error; break
    if 比较不通过:         verdict = wrong_answer; break
    passed += 1
    if passed == total: verdict = accepted
```

> 注意：每个用例都是新进程（`docker exec` 重新执行），用户代码无法在用例间保留状态，这与运行行为一致。

### 7.3 判定映射

| 场景 | status | error_message |
|---|---|---|
| 编译失败 | `compile_error` | g++/javac 输出（截断 64KB） |
| 用例超时 | `time_limit_exceeded` | 第 N 个用例执行超过 2 秒 |
| 总预算耗尽 | `time_limit_exceeded` | 判题总时长超过 60 秒，剩余用例未执行 |
| OOM | `memory_limit_exceeded` | 第 N 个用例内存超过限制 |
| 运行时异常 / 无结果 | `runtime_error` | harness 返回的错误信息 |
| 输出不一致 | `wrong_answer` | 第 N 个用例输出与预期不一致 |
| 全部通过 | `accepted` | 无 |

`runtime` 取所有已执行用例的**最大值**，`memory` 取最大值（与 LeetCode 展示口径一致）。

### 7.4 首错展示策略

- `cases` 列完整保存执行过的用例（含 `args/expected/actual/stdout/stderr/status`），供管理员排障。
- 用户接口只取第一个 `status != "passed"` 的用例，按 §5.3 的字段规则裁剪。
- 后续如果产品要求「失败用例可下载」，再单独做管理员/题目作者权限的接口，不要放开给普通用户。

### 7.5 计数与做题状态

终态写入命中时，在**同一事务**内执行：

```sql
-- 通过：提交数 +1、通过数 +1、重算通过率
UPDATE problems
SET submit_count = submit_count + 1,
    accept_count = accept_count + 1,
    acceptance_rate = ((accept_count + 1)::double precision / (submit_count + 1)) * 100
WHERE id = $1;

-- 未通过：只加提交数
UPDATE problems
SET submit_count = submit_count + 1,
    acceptance_rate = (accept_count::double precision / (submit_count + 1)) * 100
WHERE id = $1;

-- 做题状态：已 accepted 的不会被降级
INSERT INTO user_problem_status (user_id, problem_id, status, last_submission_id)
VALUES ($1, $2, $3, $4)
ON CONFLICT (user_id, problem_id) DO UPDATE
SET status = CASE
        WHEN user_problem_status.status = 'accepted' THEN 'accepted'
        ELSE EXCLUDED.status
    END,
    last_submission_id = EXCLUDED.last_submission_id,
    updated_at = CURRENT_TIMESTAMP;
```

约定：

- `internal_error` **不**计入 `submit_count` / `accept_count`；
- `accepted` 才把 `user_problem_status` 置为 `accepted`；
- 数据库 `submissions` 写入与计数更新在同一事务，避免「状态成功但计数丢失」；
- 终态更新返回 0 行时（重复投递、回收竞争）跳过计数。

## 8. 限流、配额与锁

| 项 | 值 | 键 |
|---|---|---|
| 限流 | 10 次/分钟 | `theseus:submit:rate:{user}:{minute}` |
| 并发 | 1 | `theseus:submit:concurrency:{user}` |
| 锁 TTL | `queue + compile + run + 30s`（默认 90+60+60+30 = 240s） | 同上 |

- 与运行的键完全分开，调试运行不占提交名额。
- 锁释放使用与运行相同的 Lua CAS：只有值等于自己的 `submission_id` 才删除。
- 回收任务（排队超时 / judging 卡死）也负责释放锁；锁 TTL 只是兜底，不依赖它。
- 429 返回 `Retry-After`，与运行限流一致。

## 10. 安全与数据治理

| 项 | 设计 |
|---|---|
| 隐藏用例 | 不入 Redis 消息、不进日志、不进用户接口；只在 Worker 内读取并快照 |
| 代码/输入 | 日志只记 `submission_id`、状态、耗时，不打印代码与用例 |
| 沙箱 | 与运行相同：runsc（生产）、只读根、tmpfs、非 root、无网络、能力全丢、PID/CPU/内存限制 |
| 输出 | 每个输出 64KB 截断并标记；编译输出同样截断 |
| 权限 | 详情/状态本人或管理员；列表仅本人（管理员可指定 `user_id`）；无删除提交接口 |
| 数据保留 | 代码与结果随账号删除级联清理；**题目删除时提交历史一并删除**（`submissions.problem_id` 为 `ON DELETE CASCADE`，已确认） |
| 供应链 | 沿用运行镜像与 digest 要求；新增代码不引入新镜像 |
| 刷接口 | 独立限流 + 并发锁 + 队列背压（心跳缺失时快速 503） |

> 已确认（2026-10-25）：题目删除时提交记录**一起删除**，保持现有 `ON DELETE CASCADE`，不改为 `SET NULL`。
> 这与运行记录（`code_runs.problem_id` 为 `SET NULL`，题目删除后历史仍可读）是刻意不同的：运行是调试产物，提交是题目的一部分，题目不存在后提交失去上下文。
> 影响：① 无需改表结构；② 查询提交详情/列表继续 `JOIN problems`，不会出现悬挂记录；③ 管理员删除题目会不可逆地删除所有用户在该题下的提交，管理端删除确认文案必须明确提示「同时删除 N 条提交记录」。

## 15. 风险与待确认

1. **判题总预算**：60s 覆盖 50 个用例 × 2s 是够的，但慢机器上编译本身可能接近 60s。若实测偏紧，改为「编译预算与执行预算分开计时」（当前已分开，锁 TTL 也分开计算）。
2. **共享信号量**：需要改动已经稳定的运行消费循环。若担心回归，可以先让提交循环单独限 1 并发，验证后再合并信号量。
3. **公开用例重复执行**：判题集合包含公开用例，同一条用例在「运行」和「提交」各跑一次，属于预期成本；不做缓存，避免正确性风险。
4. **题目删除**：已确认（2026-10-25）**提交历史与题目一起删除**，沿用 `submissions.problem_id ON DELETE CASCADE`，不改为 `SET NULL`。实施时注意：管理端删除题目需在确认文案里提示「将同时删除该题下的提交记录」；删除前可用 `SELECT COUNT(*) FROM submissions WHERE problem_id = $1` 展示数量。
5. **旧 `test_cases` 数据**：字符串格式无法自动转成结构化用例，本期不迁移；管理员需要为新题配置 `judge_cases` 后才能真正判题。
6. **管理端无页面**：`judge_cases` 只能通过 API 配置；若近期要运营多题，建议补一个简单的管理页（本期非目标）。
7. **前端 `SubmissionStatus` 联合类型**：新增 `internal_error` 需要同步 `adapters.ts` 与 `types/oj.ts`，否则会被归一化成 `runtime_error`，展示文案不准确。
8. **限流与队列深度**：10 次/分钟 × 1 并发下，单 Worker 顺序判题足够；多题上线后再评估是否需要提高 Worker 并发或独立扩容。

### 16.4 与运行功能的差异对照

| 维度 | 运行（Run） | 提交（Submission） |
|---|---|---|
| 用例 | 公开示例或自定义输入 | 公开示例 + 隐藏用例 |
| 队列 | `theseus:judge:runs` | `theseus:judge:submissions` |
| 状态 | `queued/compiling/running/...` | `pending/judging/...` |
| 结果 | 每个用例都返回 | 通过数 + 首个失败用例 |
| 执行预算 | 10s | 60s |
| 计数 | 不计入通过率 | 计入 `submit_count`，AC 计入 `accept_count` |
| 配额 | 1 并发 + 10 次/分钟 | 独立 1 并发 + 10 次/分钟 |
| 删除 | 支持（终态） | 不支持 |
| 快照 | `run_config_snapshot` | `run_config_snapshot` + `judge_cases_snapshot` |

### 16.5 一句话总结

提交判题不再另起炉灶：**把提交当成「带隐藏用例、需要计分、独立队列」的特殊运行**，复用沙箱、harness、重试与回收机制；隐藏用例单独存 `problems.judge_cases`，结果只暴露首个失败用例，配额与运行分离。
