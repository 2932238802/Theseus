## 2. P1：合并前必须修复

### P1-1 评论全部加载完后误显示“还没有评论”

**位置：** `frontend-vue/src/views/ForumPostPage.vue:514-525`

**现象：** 只要根评论全部加载完成且至少有一条评论，评论列表下面会额外出现“还没有评论，来坐第一个沙发”。

**原因：** 空状态的 `v-else-if` 挂在“加载更多评论”按钮的 `v-if` 上，而不是挂在评论列表上：

```vue
<button v-if="forumStore.comments.length < forumStore.commentsTotal" ...>
  加载更多评论
</button>
<div v-else-if="!forumStore.commentsLoading" class="empty-state">
  还没有评论，来坐第一个沙发。
</div>
```

当 `comments.length === commentsTotal` 时，`v-else-if` 立即成立，无论评论是否为空。

**修复建议：**

```vue
<div
  v-else-if="!forumStore.commentsLoading && forumStore.comments.length === 0"
  class="empty-state"
>
  <p>还没有评论，来坐第一个沙发。</p>
</div>
```

**回归用例：**

- 0 条评论：显示空状态。
- 1 条评论：显示评论，不显示空状态。
- 20 条评论且已全部加载：显示评论，不显示空状态。
- 25 条评论、已加载 20 条：显示“加载更多”，不显示空状态。

### P1-2 发帖/评论/举报限流可被并发绕过（TOCTOU）

**位置：** `backend-rust/src/services/forum_service.rs:204-297`  
**调用点：** `create_post`（469）、`create_comment`（965）、`create_report`（1294）

**现象：** 同一用户并发发起多个请求，可以超过冷却时间和每日上限。

**原因：** 三个 `ensure_*_limits` 都在 `pool.begin()` 之前用普通 `SELECT` 查询计数，检查与插入不在同一事务内。并发请求会同时看到旧计数，全部通过检查后再各自插入。`ensure_not_muted` 同样在事务外，禁言生效瞬间也存在竞态窗口。

**影响：** 60 秒发帖冷却、10 秒评论冷却、每日发帖/评论/举报上限失效，刷屏和举报轰炸防护可被绕过。

**修复建议：**

1. 把限流检查和插入放入同一事务。
2. 检查前按用户加事务级 advisory lock，例如：

```sql
SELECT pg_advisory_xact_lock($1, $2);
```

其中 `$1` 是固定整数命名空间（例如 1=发帖、2=评论、3=举报），`$2` 是 `user_id`；也可以使用 `SELECT id FROM users WHERE id = $1 FOR UPDATE`，但会与用户资料更新产生更多争用。
3. 将 `ensure_not_muted` 一并移入事务，在锁之后执行。
4. 补一个并发测试：同一账号并行发送 N 个发帖/评论/举报请求，断言最终成功数不超过上限。

**修复后验证：**

- 单请求冷却返回 429，并带 `Retry-After`。
- 并发请求只有 1 个成功（冷却大于 0 时）。
- 每日上限在并发下不会被突破。

### P1-3 分页越界时 `total` 变成 0，前后端会卡在空列表

**位置：**

- 帖子列表：`backend-rust/src/services/forum_service.rs:316/408`
- 评论列表：`forum_service.rs:805-806/854`
- 回复列表：`forum_service.rs:907-936`
- 管理端帖子：`forum_service.rs:1435/1504`
- 管理端举报：`forum_service.rs:2049/2072`
- 管理端审计：`forum_service.rs:2580/2607`
- 通知列表：`backend-rust/src/services/notification_service.rs:116/133`

**现象：** 请求超出最后一页时，接口返回 `total = 0`，而不是真实总数。

**原因：** 这些查询依赖 `COUNT(*) OVER() AS total`，窗口函数只对返回行求值。`OFFSET` 超出范围时没有返回行，`rows.first()` 为 `None`，`unwrap_or(0)` 就把 `total` 写成 0。

**影响：**

- 管理员处理完当前页最后一条举报后重载，会显示“没有待处理举报”，但前面的页仍有数据。
- 公共帖子列表会隐藏分页控件，用户无法回到前面的页。
- 前端 `store/forum.ts:55` 和 `AdminForumPage.vue:118` 的“越界回退”逻辑都要求 `result.total > 0`，因此无法恢复。

**修复建议：**

- 方案 A（推荐）：使用与列表查询相同筛选条件的独立 `SELECT COUNT(*)`，再执行分页查询；两条查询允许存在轻微的并发快照差异。
- 方案 B：保留窗口计数；当返回 0 行且 `page > 1` 时，查询真实总数并回退到最后一页或第 1 页，返回真实 `total`。
- 方案 C：前端识别“空页 + page > 1”时无条件回退，不依赖 `total > 0`；但接口契约仍然应该修正。

**回归用例：**

- `page=999` 请求有数据的列表，返回真实 `total`，前端可回退。
- 删除/隐藏当前页最后一条内容后重载，自动回到有内容的页。
- 管理端举报、内容列表和审计列表同样验证。

### P1-4 禁言时长可导致 panic

**位置：** `backend-rust/src/services/forum_service.rs:2441-2448`

**现象：** 管理员提交超大 `duration_hours` 时，请求返回 500 或连接中断。

**原因：** 只校验了 `hours <= 0`，随后直接执行：

```rust
Utc::now() + Duration::hours(hours)
```

`Duration::hours` 对超出范围的 `i64` 会 panic；即使时长本身合法，`DateTime + Duration` 溢出也会 panic。

**影响：** 管理端出现无明确提示的失败；当前默认 `panic = "unwind"` 下不会拖垮进程，但不能依赖该行为，未来若开启 `panic = "abort"` 会影响进程稳定性。

**修复建议：**

- 设置合理上限，例如 8760 小时（1 年）；永久禁言继续使用 `duration_hours = null`。
- 使用 `TimeDelta::try_hours` 和 `checked_add_signed`，失败返回 400：

```rust
let max = TimeDelta::try_hours(MAX_MUTE_HOURS)
    .ok_or_else(|| AppError::BadRequest("禁言时长上限配置无效".to_owned()))?;
let duration = TimeDelta::try_hours(hours)
    .filter(|value| *value <= max)
    .ok_or_else(|| AppError::BadRequest("禁言时长无效".to_owned()))?;
let ends_at = Utc::now()
    .checked_add_signed(duration)
    .ok_or_else(|| AppError::BadRequest("禁言时长无效".to_owned()))?;
```

**回归用例：**

- `duration_hours = 0`、负数：400。
- `duration_hours = 8760`：成功。
- `duration_hours = i64::MAX`、`5_000_000_000`：400，不 panic。
- `duration_hours = null`：永久禁言。

## 3. P2：建议本轮修复

### P2-1 编辑评论存在“隐藏后仍被改”的竞态

**位置：** `backend-rust/src/services/forum_service.rs:1108-1133`

**现象：** 管理员隐藏/删除评论与作者编辑评论并发时，作者可能仍然修改成功。

**原因：** `update_comment` 用普通 `SELECT` 读取 `author_id, status`，检查通过后执行无状态条件的 `UPDATE ... WHERE id = $1`，中间没有事务和行锁。管理员在这两步之间改变状态，更新仍会落到已隐藏/已删除的行上。

**修复建议：** 参考 `update_post`：

1. `pool.begin()`。
2. `SELECT author_id, status FROM forum_comments WHERE id = $1 FOR UPDATE`。
3. 在事务内检查 `deleted` / `hidden` / 作者权限。
4. `UPDATE ... WHERE id = $1 AND status = 'published'`，并检查 `rows_affected`。
5. 提交事务。

**回归用例：** 在编辑请求处理过程中并发隐藏评论，最终状态应为隐藏，正文不被修改。

### P2-2 作者删除内容后 `pending_report_count` 不清零

**位置：**

- `delete_post`：`forum_service.rs:600-610`
- `delete_comment`：`forum_service.rs:1164-1175`

**现象：** 作者删除带有待处理举报的帖子/评论后，管理端内容卡片和详情仍显示“有 N 条待处理举报”。

**原因：** 两条路径调用了 `resolve_pending_reports`，把举报状态改为 `resolved`，但没有同步把 `pending_report_count` 置 0。管理端的隐藏/恢复/删除路径已经正确清零。

**修复建议：** 在 `resolve_pending_reports` 之后调用现成的 `clear_pending_count(&mut tx, "post"/"comment", target_id)`。删除路径持有内容行锁，新举报会被状态检查拒绝，因此直接置 0 是安全的。

**回归用例：** 举报帖子/评论 → 作者删除 → 管理端待处理计数为 0；举报列表不再出现该内容。

### P2-3 评论列表 N+1 查询

**位置：** `backend-rust/src/services/forum_service.rs:856-864`

**现象：** 每加载一页评论，会为每个根评论单独执行一次回复查询。

**原因：** `list_comments` 在根评论循环中调用 `load_replies(pool, root.id, ...)`。默认 20 条根评论产生 22+ 次数据库往返，页大小 50 时产生 52+ 次。

**影响：** 帖子详情页是论坛最热接口，数据库延迟和连接池占用会被放大。

**修复建议：**

- 一次查询取回所有根评论的回复：`WHERE c.parent_id = ANY($1)`。
- 使用 `ROW_NUMBER() OVER (PARTITION BY c.parent_id ORDER BY c.created_at, c.id)` 截断每根评论的展示条数。
- 使用 `COUNT(*) OVER (PARTITION BY c.parent_id)` 计算 `reply_total`。
- 在内存中按 `parent_id` 分组后组装。

**回归用例：** 20 条根评论、每条 3 条回复时，根/回复查询从 21 次降到 2 次，总查询约 3 次（含帖子可见性检查）；回复截断和“加载更多回复”分页行为不变。

### P2-4 `admin_decide_report` 加锁顺序可能死锁

**位置：** `backend-rust/src/services/forum_service.rs:2110-2124`、`2145-2158`

**现象：** 两个管理员同时处理同一内容的不同举报时，其中一个请求可能因数据库死锁失败。

**原因：** 当前顺序是先锁举报行，再锁内容行；隐藏分支在持有内容锁时，还会更新同一内容的其他 pending 举报行。两个事务分别持有不同举报行并互相等待时形成环：

- 事务 A：持有举报 A → 等待内容锁。
- 事务 B：持有内容锁 → 等待更新举报 A（被事务 A 持有）。

**影响：** 概率较低，但管理端会偶发 500；PostgreSQL 会中止其中一个事务，当前没有自动重试。

**修复建议：**

- 所有处理举报的路径统一锁顺序：先按 `(target_type, target_id)` 加 advisory lock 或先锁内容，再锁举报行并复查状态。
- 或者在统一事务入口对内容加 `pg_advisory_xact_lock`，避免依赖行锁顺序。

**回归用例：** 两个举报、两个并发管理请求处理同一帖子；至少一个成功，另一个得到可重试的冲突/成功，而不是死锁错误。

### P2-5 搜索词未转义 ILIKE 通配符

**位置：** `forum_service.rs:380-385`（公共搜索）、`1481-1492`（管理端标题/正文/作者搜索）

**现象：** 搜索 `%` 会匹配全部帖子；搜索 `_` 会匹配任意单字符；管理端作者筛选 `_` 会列出所有作者。

**原因：** 用户输入直接拼进 `format!("%{search}%")`，`%` 和 `_` 被当作 SQL `LIKE` 通配符。参数是绑定的，不存在 SQL 注入，但语义错误。

**修复建议：**

- 先转义 `\`、`%`、`_`，例如：

```rust
fn escape_like(value: &str) -> String {
    value
        .replace('\\', "\\\\")
        .replace('%', "\\%")
        .replace('_', "\\_")
}
```

- SQL 中显式声明转义字符：`ILIKE $n ESCAPE '\'`。
- 公共搜索和管理端作者搜索复用同一个 helper。

**回归用例：** 搜索 `%`、`_`、`a_b`、`100%` 时只匹配字面量；普通中文和英文搜索不受影响。

### P2-6 管理端“定位内容”对评论举报无效

**位置：** `frontend-vue/src/views/AdminForumPage.vue:318-327`

**现象：** 点击评论举报的“定位内容”后，只把内容列表的搜索词设为父帖标题并重载，没有打开帖子，也没有定位到被举报评论。

**原因：** 评论举报的 `targetPreview.title` 是父帖标题，不是评论内容，也不包含父帖 ID；当前实现只做了文本筛选。

**修复建议：**

- 后端在举报 preview 中补充 `post_id`（举报查询已经 join 到父帖，可直接带出字段）。
- 前端对评论举报执行 `openDetail(post_id)`，并在详情加载后滚动到 `comment-{targetId}`。
- 如果暂不扩展 DTO，则把按钮改名为“按标题筛选”，避免误导管理员。

**回归用例：** 帖子举报和评论举报分别点击“定位内容”，都能直接看到被举报对象。

### P2-7 评论计数在并发下存在覆盖风险（待验证）

**位置：**

- `delete_comment`：`forum_service.rs:1174`
- `admin_change_comment_status`：`forum_service.rs:1792`
- `create_comment`：`forum_service.rs:1038`

**现象：** 评论创建与删除/隐藏并发时，父帖的 `comment_count` 可能出现少算或多算。

**原因：** `create_comment` 会先对父帖 `FOR UPDATE`，但 `delete_comment` 和管理端评论状态变更只锁评论行，不锁父帖，随后调用 `recompute_comment_count`。两条路径的锁协议不一致，READ COMMITTED 下存在旧快照覆盖新计数的可能。

**修复建议：** 所有会改变评论可见状态的路径，统一先锁父帖行（或使用按帖 advisory lock），再修改评论状态并重算计数。该条需要并发测试确认实际影响，但统一锁顺序成本很低。

## 4. P3：打磨、防御性加固与设计确认

### P3-1 管理端“待处理”徽标只统计当前页

`frontend-vue/src/views/AdminForumPage.vue:101-105`

当举报筛选不是 `pending` 时，`pendingCount` 只统计当前页返回的 pending 项，徽标数字会偏小。建议增加独立的 pending 总数接口/字段，或固定请求一次 `status=pending&size=1` 获取 `total`。

### P3-2 异步请求竞态

- `AdminForumPage` 的 `loadDetail` 没有请求序号，快速打开两个详情时可能显示旧响应。
- `ForumComposePage` 的题目搜索没有请求序号，慢请求可能覆盖新结果。
- `notificationStore.loadNotifications` 的 load-more 使用 offset 追加，新通知插入时可能重复一条。

建议统一增加 sequence guard；通知列表后续可改为 cursor 分页。

### P3-3 隐藏/删除后的作者体验

自己的隐藏帖仍显示点赞、评论、举报按钮，但后端会分别返回 404/409；编辑页对隐藏帖提示“只有作者本人可以编辑已发布的帖子”，实际原因是“已隐藏不可编辑”。建议前端按 `post.status` 禁用不可用操作，并给出准确文案。

### P3-4 题目引用查询未过滤审核状态

`forum_service.rs:316-319`、`1438` 的 `LEFT JOIN problems` 没有 `review_status = 'approved'` 条件。当前没有把 approved 改回其它状态的接口，因此不是现网漏洞；作为防御性查询，建议在列表和详情 join 中补上。

### P3-5 `FORUM_ENABLED` 只作用于公共接口

公共论坛接口在关闭时返回 503，管理端接口仍可使用。如果设计意图是“关闭期间允许管理员清理内容”，这是合理的；建议在 `2610257` 或运维说明中明确写出来，避免被当成遗漏。

### P3-6 审计接口没有前端入口

`frontend-vue/src/api/forum.ts:520` 的 `fetchAdminActions` 和 `AdminAction` 类型目前没有任何页面使用。首期如果不做审计页，建议删除这段死代码；否则补一个只读审计列表。

### P3-7 `rebuild_forum_counters.sql` 的“在线安全”声明过强

`backend-rust/scripts/rebuild_forum_counters.sql:3-5`

脚本头部写“API 在线时安全”，但重建期间并发写入仍可能被覆盖。建议改为“低峰期执行”或“停写执行”，并说明执行后会丢失并发窗口内的计数更新。

### P3-8 重复实现与管理端逻辑重复

- `frontend-vue/src/api/forum.ts:35-46` 与 `notifications.ts:11-20` 重复实现 adapter helpers；可收敛到共享模块。
- `admin_change_post_status`、`admin_change_comment_status`、`admin_decide_report` 三处重复“锁内容 → 改状态 → 清计数 → 写审计 → 发通知”的流程，后续可提取 helper，降低漏改风险。

这些不是功能缺陷，建议在 P1/P2 修复后一并整理。

### 设计确认：教师不自动获得论坛治理权

当前实现仍以 `users.role` 的 `user/admin` 判定，论坛审核和禁言仅 `admin`。这与 `2610257` 的“论坛治理权限仅 admin”一致，但与总体设计中的 `student ⊂ teacher ⊂ admin` 角色模型尚未打通。属于后续 RBAC 阶段的工作，不是本次实现的回归。

## 5. 已确认无问题的部分

- **匿名隔离**：`PublicAuthor` 是公开响应唯一的作者构造入口；匿名内容只显示“匿名同学”，公开响应不包含 `author_id`、`username`、`email`。`reply_to` 对匿名/隐藏目标做了脱敏，通知 API 不返回 actor 私有字段。
- **XSS**：`frontend-vue/src/components/MarkdownBody.vue` 使用 `marked` + `DOMPurify`，标签、属性、URI 白名单明确；清洗后才给链接加 `target/rel`，未发现明显绕过路径。
- **权限边界**：所有管理端 handler 都经过 `require_admin`；公开 DTO 与管理端 DTO 分离。
- **举报闭环**：重复举报唯一约束、自动隐藏阈值、处理时互斥、审计写入与设计基本一致。
- **设计对齐**：固定标签、两级评论、匿名不可编辑、隐藏/删除墓碑、通知优先级等行为与 `2610257_论坛功能设计方案.md` 基本一致。
