# 编译超时的原因

- 日期：2026-10-25
- 关联文档：[2610241_运行代码功能设计方案](./2610241_运行代码功能设计方案.md)、[2610251_提交运行示例会卡住原因?](./2610251_提交运行示例会卡住原因?.md)
- 涉及代码：`backend-rust/src/judge/runner.rs`、`backend-rust/src/judge/harness/cpp.rs`、`backend-rust/src/bin/judge_worker.rs`、`backend-rust/src/config.rs`

## 0. 结论速览

「编译超时」不是偶发，也不是沙箱或 Docker 的问题，而是**编译预算与 C++ harness 的实际编译成本不匹配**：

1. 生成的 C++ 代码会 `#include <bits/stdc++.h>` 和 `nlohmann/json.hpp`，这是最重的翻译单元；
2. 实测单核编译峰值内存约 **342 MB**、耗时 2.5–3s（本机 g++ 15，容器内为 g++ 12）；
3. 但沙箱容器的编译限额是 **256 MB / 10s**，内存在编译完成前就触顶，编译无法在 10s 内结束；
4. Worker 的 `exec_capture` 一到 10s 就返回 `编译超时（10 秒）`，写进 `compile_output`，任务状态变成 `compile_error`。

修复方向：**给编译阶段单独的预算（60s / 1024MB），编译完成后把内存限额降回运行限额**，这样既能让编译通过，也不放松对用户代码的运行期内存限制。

## 1. 现象

2026-10-25 13:24–13:26，两次 cpp 运行（run 5、run 6）都在约 11 秒后失败：

| id | language | status | compile_output | created_at | finished_at |
|---|---|---|---|---|---|
| 5 | cpp | compile_error | `编译超时（10 秒）` | 13:24:35 | 13:24:46 |
| 6 | cpp | compile_error | `编译超时（10 秒）` | 13:25:52 | 13:26:03 |

前端展示为「编译失败」，数据库与 Worker 日志记录的是编译超时。两次都是 10 秒整，说明**不是编译报错，而是预算耗尽**。

## 2. 代码路径

```
judge_worker::process_run
  └─ SandboxSession::start
       ├─ start_container(...)        // --memory=256m --cpus=1
       ├─ write_to_container(...)     // docker exec cat > /workspace/main.cpp
       └─ exec_capture(container, COMPILE, COMPILE_TIMEOUT)
            └─ tokio::time::timeout(10s, docker exec g++ ...)
                 ├─ 完成 → (success, output)
                 └─ 超时 → Ok((false, "编译超时（10 秒）"))
```

超时文案来自 `judge/runner.rs::exec_capture`，不是 g++ 的输出。

## 3. 根因分析

### 3.1 编译的到底是什么

`judge/harness/cpp.rs` 生成的 `main.cpp` 开头是：

```cpp
#include <bits/stdc++.h>
#include <sys/resource.h>
#include "json.hpp"
```

- `bits/stdc++.h` 会把整个标准库拉进来（仅解析就要约 **196 MB** 内存）；
- `nlohmann/json.hpp` 是一个约 **900 KB、2.5 万行**的模板库，`json` 的实例化 + `-O2` 代码生成会再抬高约 **150 MB**；
- harness 里还用了 `std::ifstream`、`std::chrono`、`getrusage`、`nlohmann::json` 的序列化，模板实例化量很大。

这是「竞赛题里方便」和「编译成本」之间的取舍，原来的 10s/256MB 预算是按简单 TU 估的，没有覆盖这种情况。

### 3.2 实测编译成本（本机，单核 `taskset -c 0`，g++ 15.2，`-O2 -std=c++17`）

| 翻译单元 | 耗时 | 峰值内存 |
|---|---|---|
| `#include <bits/stdc++.h>` + `int main(){}` | 0.73–0.96 s | 200,596 KB ≈ **196 MB** |
| 再加 `nlohmann/json.hpp` 并实例化 `json` | 2.54–3.01 s | 350,648 KB ≈ **342 MB** |
| 完整 harness（含 `Solution` / 参数准备） | ≈ 3 s+ | ≥ 342 MB |

宿主机的测量命令：

```bash
taskset -c 0 /usr/bin/time -f '%e s  %M KB' \
  g++ -O2 -std=c++17 -pipe -I. -o b b.cpp
```

### 3.3 与容器限额对比

`judge_worker.rs` 中 cpp 的运行内存限额是 `256` MB：

```rust
cpp: sandbox_config(&config, &config.run_image_cpp, 256),
```

容器启动参数：

```
--memory=256m --memory-swap=256m --cpus=1
```

也就是说：**编译峰值内存（342 MB）比容器上限（256 MB）高约 34%**，而且 `--memory-swap` 与 `--memory` 相等（无 swap）。编译在完成前就会撞上限额。

### 3.4 为什么表现为「超时」而不是「内存超限」

cgroup 内存到顶后有两种结局：

1. 内核先回收 page cache → 编译被拖慢，10s 预算先到 → 表现为**超时**（本次）；
2. 回收不动 → OOM killer 杀掉 `cc1plus` → g++ 报 `internal compiler error: Killed`，退出码 137 → 表现为**编译失败**。

两者根因相同（内存不够），本次是第一种。由于 256 MB 连「只 include `bits/stdc++.h`」的 196 MB 都很紧张，再加上 json.hpp 的模板实例化，必然触发其中之一。

另外，容器只有 1 核（`--cpus=1`），宿主机单核已经要 2.5–3s；在内存受限、page cache 反复回收的情况下，实际耗时会被进一步拉长，10s 本身也已经偏紧。

### 3.5 哪些语言会受影响

| 语言 | 编译步骤 | 影响 |
|---|---|---|
| cpp | `g++ -O2 ...` | **直接命中**：峰值 342MB > 256MB |
| java | `javac`（编译到 `/workspace/classes`） | 同样受 512MB / 10s 限制，javac 启动 + 编译通常需要 2–5s，内存 300MB 左右，属于「勉强够用」，慢机器上也会超时 |
| python / javascript | 无编译 | 不受影响 |

## 4. 修复

### 4.1 编译阶段独立预算

新增两个配置（`config.rs`，默认值写进 `.env.example`，不配置也能工作）：

| 环境变量 | 默认值 | 下限 | 说明 |
|---|---|---|---|
| `RUN_COMPILE_TIMEOUT_SECS` | 60 | 10 | 编译阶段超时 |
| `RUN_COMPILE_MEMORY_MB` | 1024 | 256 | 编译阶段内存预算 |

`SandboxConfig` 增加 `compile_timeout` 与 `compile_memory_mb`。

### 4.2 有编译步骤时先用大限额，编译后再收紧

`runner.rs::start_inner`：

```rust
start_container(sandbox, container, program.compile.is_some()).await?;
...
if let Some(compile) = program.compile.as_ref() {
    let (success, output) = exec_capture(container, compile, sandbox.compile_timeout).await?;
    if !success {
        return Ok(SandboxStart::CompileError { output });
    }
    // 编译是唯一需要大预算的阶段，运行前恢复严格限额
    apply_memory_limit(container, run_memory_mb(sandbox)).await;
}
```

- 容器启动时，若有编译步骤，`--memory` 取 `max(编译预算, 运行限额)`（默认 1024MB）；
- 编译成功后执行 `docker update --memory=256m --memory-swap=256m <ctr>`，把限额降回运行值；
- `docker update` 失败只记 `WARN`，不会让任务失败（代价是运行期限额停留在编译预算，仍是有界值）；
- 没有编译步骤的语言（python / js）直接用运行限额，不受影响。

这样 **用户代码运行时的内存限制仍然是 256MB（Java 512MB）**，只有编译进程能用到更大的预算。

### 4.3 并发锁 TTL 同步覆盖编译时间

`run_service.rs::concurrency_ttl` 原来只算了「排队 + 运行 + 用例预算」，编译预算加大后可能先于任务结束而到期，导致同一用户可以并发再提交。现在改为：

```rust
queue_timeout + compile_timeout + RUN_TIMEOUT + cases × CASE_TIMEOUT + 30s
```

默认值下（90 + 60 + 10 + 3×2 + 30 = 196s），覆盖了最坏情况。

### 4.4 不需要改 `.env`

新配置有默认值；`.env.example` 已补注释说明。已有 `.env` 无需改动，除非想调小/调大预算。

### 5.2 容器内实测（需要 docker 权限）

```bash
# 256MB：预期超时/被 OOM kill
docker run --rm --memory=256m --memory-swap=256m --cpus=1 --user 65534:65534 \

    printf "#include <bits/stdc++.h>\n#include \"/opt/harness/json.hpp\"\nint main(){}\n" > /tmp/t.cpp

docker run --rm --memory=1024m --memory-swap=1024m --cpus=1 --user 65534:65534 \

    printf "#include <bits/stdc++.h>\n#include \"/opt/harness/json.hpp\"\nint main(){}\n" > /tmp/t.cpp
```

### 5.3 端到端

重启 `dev.sh` 后提交一次 cpp 运行，预期：

- Worker 日志不再出现 `run failed to compile`；
- 编译耗时明显超过 10s 也不影响（预算 60s），随后正常执行用例；
- 数据库 `compile_output` 为空，状态进入 `completed` / `wrong_answer` 等；
- Worker 日志中不再出现 `failed to lower sandbox memory limit after compile`；
- 故意写一段编译错误（例如缺少分号）仍然得到 `compile_error`，文案为 g++ 的真实输出。

## 6. 后续优化（非本次必需）

1. **预编译头（PCH）**：在 runner 镜像构建时把 `bits/stdc++.h + json.hpp` 预编译成 `/opt/harness/harness.hpp.gch`，用户 TU 只 include 这个头。可把编译时间从数秒降到亚秒级，同时降低内存峰值。
2. **换掉 nlohmann/json**：harness 只需要解析 `case.json` 和输出 `result.json`，可以用更轻的解析器或手写序列化，减少模板实例化。
3. **编译与运行分容器**：编译放在单独的一次性容器（大内存），产物再注入运行沙箱，运行沙箱可以维持更严格的内存上限；这是生产环境更干净的方案。
4. **按语言配置预算**：C++ / Java 的编译成本差异大，可以分别配置超时与内存。

## 7. 一句话总结

C++ harness 为了写题方便引入了 `bits/stdc++.h` + `nlohmann/json`，单核编译需要约 **342 MB / 3s**；而沙箱按 `256 MB / 10s` 给编译留预算，编译还没跑完就被判定为超时。现在编译阶段使用 `1024 MB / 60s` 的独立预算，编译结束后再降回运行限额，既解决问题，也不放松对用户代码的限制。
