## 0. 结论速览

| 决策项 | 本期选择 |
|---|---|
| 产品形态 | 单一校园墙信息流 + 标签筛选，不做多板块 |
| 首期范围 | 发帖、编辑、软删除、两级评论、引用题目、点赞、收藏、举报、管理员治理、禁言、站内通知 |
| 匿名 | 发帖和评论均可选匿名；前台不暴露身份，后台保留真实作者，仅管理端可见 |
| 内容格式 | Markdown 子集 + 代码块；禁止原始 HTML、图片、iframe，前端 DOMPurify 清洗 |
| 审核模式 | 先发后审；举报达到阈值自动隐藏，管理员复核；管理员也可直接隐藏/恢复/删除 |
| 评论结构 | 两级：顶层评论 + 一层回复；回复回复时归一到根评论，额外记录被回复人 |
| 通知 | 首期只做站内信；回复、@、审核结果、禁言入库；邮件留到统一通知系统 |
| 标签 | 固定标签：综合、求助、题解、讨论、公告；公告仅管理员可用 |
| 搜索排序 | 标题/正文 `ILIKE` + 标签过滤；最新、热门两种排序；中文分词后续升级 |
| 治理权限 | 论坛审核与禁言仅 `admin`；教师不自动获得论坛治理权 |
| 题目引用 | 每帖最多引用 1 道已通过审核的题目，结构化外键 + 卡片展示 |

**一句话总结：** 先把「发帖 → 评论/回复 → 题目引用 → 举报/治理 → 站内通知」做成完整闭环，复用现有认证、题目和管理员能力，不引入新服务、不做富文本和图片。

## 1. 目标与非目标

### 1.1 目标

1. 学生和教师可以在校园墙发帖、讨论题目、互相回复。
2. 帖子可以结构化引用一道题目，点击卡片跳转到题目页。
3. 匿名发帖/评论可用，但管理员在治理时能看到真实作者。
4. 举报、自动隐藏、管理员复核、禁言、审计形成治理闭环。
5. 回复、@、审核结果能产生站内通知，导航栏有未读数。
6. 前端有完整的列表、详情、发帖、通知和管理端页面。
7. 数据结构为后续作业通知、系统广播、邮件 outbox 留出扩展空间。
8. 实现不依赖 WebSocket；通知用轮询即可，保持部署简单。

### 1.2 非目标

- 不做多板块、课程论坛、私信、关注作者、作者动态。
- 不做图片/附件上传、富文本编辑器、视频嵌入。
- 不做无限嵌套评论。
- 不做发帖先审；匿名帖也不进入待审队列。
- 不做邮件发送、短信、微信推送；本期只落 `notifications` 表。
- 不做中文全文检索、搜索引擎、推荐算法。
- 不做帖子编辑历史、版本对比。
- 不做帖子置顶以外的运营位（横幅、分区公告等）。
- 不做 AI 内容审核；敏感词只预留接口，不在首期实现。

### 1.3 首期验收标准

- [ ] 登录用户可发帖，至少选择一个标签，可引用一道已审核题目。
- [ ] 未登录用户可浏览帖子、评论和题目卡片，但不能写入。
- [ ] 匿名帖在列表、详情、评论、通知中都不泄露用户名、用户 id、邮箱。
- [ ] 管理员在管理端可以看到匿名帖的真实作者。
- [ ] 两级评论可创建、回复、编辑、软删除；回复通知能正确到达。
- [ ] 点赞、收藏可切换，计数准确且重复请求幂等。
- [ ] 举报重复提交返回 409；达到阈值后内容自动隐藏。
- [ ] 管理员可隐藏/恢复/删除帖子或评论，可禁言用户，操作写入审计表。
- [ ] `@用户名` 能产生站内通知；匿名作者显示为“匿名同学”。
- [ ] Markdown 中的 `<script>`、事件属性、`javascript:` 链接不会被执行。
- [ ] 冒烟脚本覆盖「发帖 → 评论 → 点赞 → 举报 → 管理员处理 → 通知」主链路。

## 3. 角色、权限与匿名

### 3.1 权限模型

首期沿用当前 `users.role`：

| 能力 | 游客 | 登录用户 | 管理员 |
|---|---:|---:|---:|
| 浏览帖子/评论/题目卡片 | ✓ | ✓ | ✓ |
| 搜索、标签筛选 | ✓ | ✓ | ✓ |
| 发帖、评论、回复 | — | ✓ | ✓ |
| 编辑/删除自己的内容 | — | ✓ | ✓ |
| 点赞、收藏 | — | ✓ | ✓ |
| 举报 | — | ✓ | ✓ |
| 隐藏/恢复/删除任意内容 | — | — | ✓ |
| 处理举报 | — | — | ✓ |
| 禁言/解除禁言 | — | — | ✓ |
| 置顶帖子 | — | — | ✓ |
| 查看匿名作者真实身份 | — | — | ✓（仅管理端） |

说明：

- 教师当前只有 `user` / `admin` 两种值；本期不新增 `teacher` 判断。后续 RBAC 落地时，论坛治理权限只授予 `admin`，教师不自动获得。
- 管理员不能因为能治理论坛就绕过内容可见性；管理端接口单独返回真实作者和全部状态。
- 作者只能编辑/删除自己的内容；管理员删除是软删除，不是物理删除。

### 3.2 匿名规则

1. `forum_posts.is_anonymous` 和 `forum_comments.is_anonymous` 在创建时确定，发布后不可修改。
2. 公开接口对匿名内容的作者统一返回：

```json
{
  "display_name": "匿名同学",
  "is_anonymous": true,
  "is_self": false
}
```

3. 公开接口**永不返回**匿名内容的 `author_id`、`username`、`email`。
4. 作者本人通过 `is_self: true` 得知这是自己的内容；这不泄露身份。
5. 管理员治理接口返回真实作者：

```json
{
  "id": 7,
  "username": "alice",
  "email": "alice@example.edu",
  "role": "user"
}
```

6. 通知文案不泄露匿名身份：
   - 实名作者：“Alice 回复了你的帖子”；
   - 匿名作者：“匿名同学回复了你的帖子”。
7. 禁言、频率限制、举报去重都按真实 `user_id` 计算，匿名不提供额外豁免。
8. 匿名帖仍然参与最新/热门/搜索；排序不使用作者信息。

### 3.3 内容可见性矩阵

| 内容状态 | 游客/其他用户 | 作者 | 管理员公开接口 | 管理员治理接口 |
|---|---|---|---|---|
| `published` 帖子 | 可见 | 可见 | 可见 | 可见 |
| `hidden` 帖子 | 404 | 可见，带隐藏提示，不可编辑 | 404 | 可见 |
| `deleted` 帖子 | 404 | 404 | 404 | 可见（带删除标记） |
| `published` 评论 | 可见 | 可见 | 可见 | 可见 |
| `hidden` 评论 | 不返回正文 | 不返回正文 | 不返回正文 | 可见 |
| `deleted` 评论 | 不返回正文；有可见回复时返回墓碑 | 同左 | 同左 | 可见 |

补充：

- 帖子被隐藏/删除后，其评论接口对普通用户返回 404；作者查看隐藏帖子时仍可读取评论。
- 顶层评论被隐藏/删除且仍有可见回复时，返回墓碑：

```json
{
  "id": 11,
  "is_tombstone": true,
  "body_md": "",
  "author": { "display_name": "已隐藏", "is_anonymous": false, "is_self": false },
  "replies": []
}
```

- 没有可见回复的隐藏/删除顶层评论直接从列表省略。
- 被隐藏/删除的回复直接省略，不做墓碑，因为不存在更深层级。

## 4. 信息架构与状态

### 4.1 标签

固定标签，前后端共用同一份常量：

| code | 中文 | 说明 | 权限 |
|---|---|---|---|
| `general` | 综合 | 日常讨论、校园墙内容 | 所有登录用户 |
| `help` | 求助 | 题目求助、调试问题 | 所有登录用户 |
| `solution` | 题解 | 解题思路、复杂度分析 | 所有登录用户 |
| `discussion` | 讨论 | 算法/课程/学习方式讨论 | 所有登录用户 |
| `announcement` | 公告 | 管理员公告 | 仅管理员 |

规则：

- 每帖 1–3 个标签，去重后校验。
- `announcement` 只能由管理员选择；普通用户提交返回 400。
- 公告帖自动允许管理员置顶，但不强制。
- 标签过滤使用数组包含：`$tag = ANY(tags)`。
- 不在数据库里做标签枚举约束，允许后续加标签而不改 CHECK；应用层校验白名单。

### 4.2 帖子状态

```text
published ──管理员隐藏/举报阈值──> hidden ──管理员恢复──> published
    │                                  │
    └────────作者/管理员删除───────────┴──> deleted
```

- `published`：正常可见。
- `hidden`：被管理员隐藏，或被举报阈值自动隐藏；公开不可见，作者可见。
- `deleted`：软删除；公开不可见，作者也不可见；管理端仍可审计。
- `hidden_reason`：`moderation`（管理员操作）或 `report_threshold`（系统自动）。
- `hidden_by`：管理员 id；系统自动隐藏时为 `NULL`。
- `is_pinned`：仅管理员可设；仅 `published` 帖参与置顶排序。
- 编辑不改变状态；`hidden` 帖作者不可编辑，只能删除或等待恢复。
- 恢复帖子时，同时把该帖所有 `pending` 举报置为 `rejected`，`pending_report_count = 0`。

### 4.3 评论状态

- `published`、`hidden`、`deleted`，规则与帖子类似，但没有置顶。
- 评论只能由作者编辑/删除；管理员可隐藏/恢复/删除。
- 顶层评论是 `parent_id IS NULL`；回复的 `parent_id` 始终指向顶层评论。
- 回复回复时：
  - `parent_id` 归一为根评论 id；
  - `reply_to_comment_id` 指向实际被回复的评论；
  - `reply_to_user_id` 记录实际被回复人，用于通知和“回复 @某人”。
- 顶层评论的 `reply_to_comment_id` 为 `NULL`。
- 评论计数 `forum_posts.comment_count` 只统计 `published` 评论，写入/状态变更后在同一事务内重算。

### 4.4 举报与禁言状态

举报：

```text
pending ──管理员 hide──> resolved（内容隐藏）
   └────管理员 keep──> rejected（内容保留；若因阈值隐藏且剩余举报低于阈值则恢复）
```

- 同一用户对同一目标只能举报一次：`UNIQUE(target_type, target_id, reporter_id)`。
- 举报人去重后计数，达到 `FORUM_REPORT_HIDE_THRESHOLD`（默认 3）自动隐藏。
- 自动隐藏时写一条 `moderation_actions`，`actor_id = NULL`，action 为 `auto_hide_post` / `auto_hide_comment`。
- 管理员处理举报时写审计；隐藏/恢复/删除内容也写审计。

禁言：

- `user_mutes` 支持按时长或永久禁言；`ends_at NULL` 表示永久。
- 有效禁言条件：`revoked_at IS NULL AND starts_at <= now() AND (ends_at IS NULL OR ends_at > now())`。
- 有效禁言期间禁止：发帖、编辑帖子、评论、回复、编辑评论。
- 仍允许：浏览、点赞、收藏、举报、删除自己的内容。
- 管理员不能禁言自己；所有禁言/解除写审计并通知被禁言用户。

## 5. 数据模型

### 5.1 ER 关系

```text
users ──< forum_posts >── problems
  │            │
  │            ├──< forum_comments >── users
  │            ├──< forum_post_likes
  │            ├──< forum_post_favorites
  │            └──< forum_reports (target_type='post')
  ├──< forum_comments
  ├──< forum_reports (reporter_id)
  ├──< user_mutes
  └──< notifications
```

### 5.2 迁移 SQL（`0004_forum.sql`）

```sql
-- Theseus forum MVP: single wall with tags, optional anonymity,
-- two-level comments, likes/favorites, reports, moderation and in-app notifications.

CREATE TABLE IF NOT EXISTS forum_posts (
    id BIGSERIAL PRIMARY KEY,
    author_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(120) NOT NULL,
    body_md TEXT NOT NULL,
    tags TEXT[] NOT NULL DEFAULT '{}'::text[],
    problem_id INTEGER REFERENCES problems(id) ON DELETE SET NULL,
    is_anonymous BOOLEAN NOT NULL DEFAULT FALSE,
    status VARCHAR(20) NOT NULL DEFAULT 'published'
        CHECK (status IN ('published', 'hidden', 'deleted')),
    hidden_reason VARCHAR(30)
        CHECK (hidden_reason IS NULL OR hidden_reason IN ('moderation', 'report_threshold')),
    hidden_by INTEGER REFERENCES users(id) ON DELETE SET NULL,
    hidden_at TIMESTAMPTZ,
    is_pinned BOOLEAN NOT NULL DEFAULT FALSE,
    pinned_at TIMESTAMPTZ,
    like_count INTEGER NOT NULL DEFAULT 0 CHECK (like_count >= 0),
    favorite_count INTEGER NOT NULL DEFAULT 0 CHECK (favorite_count >= 0),
    comment_count INTEGER NOT NULL DEFAULT 0 CHECK (comment_count >= 0),
    pending_report_count INTEGER NOT NULL DEFAULT 0 CHECK (pending_report_count >= 0),
    edited_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (char_length(title) BETWEEN 1 AND 120),
    CHECK (char_length(body_md) BETWEEN 1 AND 20000),
    CHECK (cardinality(tags) BETWEEN 1 AND 3)
);

CREATE INDEX IF NOT EXISTS idx_forum_posts_feed
    ON forum_posts (status, is_pinned DESC, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_forum_posts_author
    ON forum_posts (author_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_forum_posts_tags
    ON forum_posts USING GIN (tags);
CREATE INDEX IF NOT EXISTS idx_forum_posts_problem
    ON forum_posts (problem_id);

CREATE TABLE IF NOT EXISTS forum_comments (
    id BIGSERIAL PRIMARY KEY,
    post_id BIGINT NOT NULL REFERENCES forum_posts(id) ON DELETE CASCADE,
    author_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    parent_id BIGINT REFERENCES forum_comments(id) ON DELETE CASCADE,
    reply_to_comment_id BIGINT REFERENCES forum_comments(id) ON DELETE SET NULL,
    reply_to_user_id INTEGER REFERENCES users(id) ON DELETE SET NULL,
    body_md TEXT NOT NULL,
    is_anonymous BOOLEAN NOT NULL DEFAULT FALSE,
    status VARCHAR(20) NOT NULL DEFAULT 'published'
        CHECK (status IN ('published', 'hidden', 'deleted')),
    hidden_reason VARCHAR(30)
        CHECK (hidden_reason IS NULL OR hidden_reason IN ('moderation', 'report_threshold')),
    hidden_by INTEGER REFERENCES users(id) ON DELETE SET NULL,
    hidden_at TIMESTAMPTZ,
    pending_report_count INTEGER NOT NULL DEFAULT 0 CHECK (pending_report_count >= 0),
    edited_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (char_length(body_md) BETWEEN 1 AND 5000)
);

CREATE INDEX IF NOT EXISTS idx_forum_comments_post
    ON forum_comments (post_id, parent_id, created_at ASC);
CREATE INDEX IF NOT EXISTS idx_forum_comments_author
    ON forum_comments (author_id, created_at DESC);

CREATE TABLE IF NOT EXISTS forum_post_likes (
    post_id BIGINT NOT NULL REFERENCES forum_posts(id) ON DELETE CASCADE,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (post_id, user_id)
);

CREATE INDEX IF NOT EXISTS idx_forum_post_likes_user
    ON forum_post_likes (user_id, created_at DESC);

CREATE TABLE IF NOT EXISTS forum_post_favorites (
    post_id BIGINT NOT NULL REFERENCES forum_posts(id) ON DELETE CASCADE,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (post_id, user_id)
);

CREATE INDEX IF NOT EXISTS idx_forum_post_favorites_user
    ON forum_post_favorites (user_id, created_at DESC);

CREATE TABLE IF NOT EXISTS forum_reports (
    id BIGSERIAL PRIMARY KEY,
    target_type VARCHAR(10) NOT NULL CHECK (target_type IN ('post', 'comment')),
    target_id BIGINT NOT NULL,
    reporter_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    reason VARCHAR(20) NOT NULL
        CHECK (reason IN ('spam', 'abuse', 'spoiler', 'illegal', 'other')),
    detail VARCHAR(500),
    status VARCHAR(20) NOT NULL DEFAULT 'pending'
        CHECK (status IN ('pending', 'resolved', 'rejected')),
    handled_by INTEGER REFERENCES users(id) ON DELETE SET NULL,
    handled_at TIMESTAMPTZ,
    resolution_note VARCHAR(500),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (target_type, target_id, reporter_id)
);

CREATE INDEX IF NOT EXISTS idx_forum_reports_queue
    ON forum_reports (status, created_at ASC);
CREATE INDEX IF NOT EXISTS idx_forum_reports_target
    ON forum_reports (target_type, target_id);

CREATE TABLE IF NOT EXISTS user_mutes (
    id BIGSERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    muted_by INTEGER REFERENCES users(id) ON DELETE SET NULL,
    reason VARCHAR(500) NOT NULL,
    starts_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    ends_at TIMESTAMPTZ,
    revoked_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (ends_at IS NULL OR ends_at > starts_at)
);

CREATE INDEX IF NOT EXISTS idx_user_mutes_active
    ON user_mutes (user_id, ends_at)
    WHERE revoked_at IS NULL;

CREATE TABLE IF NOT EXISTS moderation_actions (
    id BIGSERIAL PRIMARY KEY,
    actor_id INTEGER REFERENCES users(id) ON DELETE SET NULL,
    action VARCHAR(40) NOT NULL,
    target_type VARCHAR(20) NOT NULL,
    target_id BIGINT,
    reason VARCHAR(500),
    metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_moderation_actions_target
    ON moderation_actions (target_type, target_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_moderation_actions_actor
    ON moderation_actions (actor_id, created_at DESC);

CREATE TABLE IF NOT EXISTS notifications (
    id BIGSERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    type VARCHAR(40) NOT NULL,
    actor_id INTEGER REFERENCES users(id) ON DELETE SET NULL,
    title VARCHAR(200) NOT NULL,
    body TEXT,
    link VARCHAR(500),
    related_type VARCHAR(30),
    related_id BIGINT,
    read_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_notifications_user
    ON notifications (user_id, read_at, created_at DESC);
```

### 5.3 与总体设计的命名差异

总体设计 §5.2 使用了 `posts` / `comments` / `post_reactions` / `post_reports`。本方案落地为更明确的：

| 总体设计 | 本方案 | 原因 |
|---|---|---|
| `posts` | `forum_posts` | 避免与未来其他业务帖子混淆 |
| `comments` | `forum_comments` | 同上 |
| `post_reactions` | `forum_post_likes` + `forum_post_favorites` | 首期只有点赞/收藏，语义清晰 |
| `post_reports` | `forum_reports` | 统一举报表，支持举报评论 |
| `moderation_actions` | `moderation_actions` | 保持通用命名 |
| `notifications` | `notifications` | 保持通用，后续作业/广播复用 |

后续更新总体设计时以本方案表名为准。

### 5.4 计数一致性

- `like_count` / `favorite_count`：只有插入/删除关联行成功时才 `+1/-1`，避免重复请求导致计数漂移。
- `comment_count`：评论新增、隐藏、恢复、删除后，在同一事务内重算：

```sql
UPDATE forum_posts
SET comment_count = (
    SELECT COUNT(*)
    FROM forum_comments
    WHERE post_id = $1 AND status = 'published'
), updated_at = CURRENT_TIMESTAMP
WHERE id = $1;
```

- `pending_report_count`：插入举报 `+1`，处理举报 `-1`（不低于 0），恢复/删除内容时清零。
- 所有计数变更与业务写入放在同一事务；后端提供一条维护 SQL，用于必要时重建计数：

```sql
UPDATE forum_posts fp
SET like_count = (SELECT COUNT(*) FROM forum_post_likes l WHERE l.post_id = fp.id),
    favorite_count = (SELECT COUNT(*) FROM forum_post_favorites f WHERE f.post_id = fp.id),
    comment_count = (
        SELECT COUNT(*) FROM forum_comments c
        WHERE c.post_id = fp.id AND c.status = 'published'
    );
```

### 5.5 索引与搜索

- 列表主索引：`(status, is_pinned DESC, created_at DESC)`。
- 热门排序在 SQL 中按公式计算，使用 `status + created_at` 索引缩小范围。
- 标签过滤使用 GIN。
- 首期搜索：

```sql
WHERE (fp.title ILIKE '%' || $q || '%' OR fp.body_md ILIKE '%' || $q || '%')
```

小规模校内数据可接受。数据量上来后再加可选迁移：

```sql
-- 可选，不在 0004 中执行，避免无扩展权限时迁移失败
-- CREATE EXTENSION IF NOT EXISTS pg_trgm;
-- CREATE INDEX idx_forum_posts_title_trgm ON forum_posts USING GIN (title gin_trgm_ops);
-- CREATE INDEX idx_forum_posts_body_trgm ON forum_posts USING GIN (body_md gin_trgm_ops);
```

中文分词、`zhparser`、独立搜索服务都留到后续。

### 6.9 发表评论/回复

```http
POST /api/forum/posts/{id}/comments
```

顶层评论：

```json
{
  "body_md": "空数组要单独判断。",
  "is_anonymous": false
}
```

回复顶层评论：

```json
{
  "body_md": "明白了，谢谢！",
  "parent_id": 31,
  "reply_to_comment_id": 31,
  "is_anonymous": true
}
```

回复某条回复：

```json
{
  "body_md": "我也遇到过这个问题。",
  "parent_id": 31,
  "reply_to_comment_id": 32,
  "is_anonymous": false
}
```

后端归一化：

1. 校验帖子存在且 `published`；
2. 若 `reply_to_comment_id` 存在，查出目标评论，必须属于同一帖子且为 `published`；
3. 根评论 = 目标的 `parent_id`，如果目标本身是顶层评论则根评论 = 目标 id；
4. 如果同时传了 `parent_id`，必须等于根评论 id，否则 400；
5. 写入 `parent_id = 根评论 id`、`reply_to_comment_id = 目标 id`、`reply_to_user_id = 目标作者`；
6. 顶层评论 `parent_id`、`reply_to_comment_id`、`reply_to_user_id` 全部为 `NULL`；
7. 禁言、频率限制、正文长度校验与发帖一致（评论上限 5000 字符）。

响应 201：返回创建后的评论对象（含 `id`、`created_at`、`author` 展示信息）。

- 删除/隐藏后在同一事务内重算 `forum_posts.comment_count`。
- 已删除评论不能编辑或恢复。

| type | 触发 | 收件人 |
|---|---|---|
| `forum_comment` | 有人评论你的帖子 | 帖子作者 |
| `forum_reply` | 有人回复你的评论 | 被回复评论作者 |
| `forum_mention` | 有人在帖子/评论中 @ 你 | 被 @ 用户 |

- `link` 只存站内相对路径；
- 通知写入与业务写入同事务，避免业务成功但通知丢失；
- 未读数是简单 `COUNT(*) WHERE read_at IS NULL`，首期数据量小，不需要缓存。

#### 内容状态修改

```http
PUT /api/admin/forum/posts/{id}/status
```

```json
{ "status": "hidden", "reason": "包含人身攻击" }
```

- `status`：`published` / `hidden` / `deleted`；
- `published` 表示恢复，只能从 `hidden` 恢复；`deleted` 为终态，不能通过该接口恢复；
- `hidden` 必须带 `reason`，写入 `hidden_reason='moderation'`、`hidden_by`、`hidden_at`；
- `deleted` 为软删除；
- 每次操作写 `moderation_actions`；
- 隐藏/删除时，将该目标所有 `pending` 举报置为 `resolved` 并清零 `pending_report_count`；
- 恢复时，将 `pending` 举报置为 `rejected` 并清零；
- 通知内容作者。

#### 举报处理

```http
PUT /api/admin/forum/reports/{id}
```

```json
{ "decision": "hide", "note": "确认是广告" }
```

- `decision = hide`：举报置为 `resolved`，隐藏目标内容（`hidden_reason='moderation'`）；
- `decision = keep`：举报置为 `rejected`；若目标仅因 `report_threshold` 被隐藏，且处理后 `pending_report_count < 阈值`，自动恢复为 `published`；
- `note` 可选，最长 500；
- 写审计；
- 若内容被隐藏/恢复，通知内容作者。

#### 禁言

```http
POST /api/admin/forum/users/{id}/mute
```

```json
{ "duration_hours": 24, "reason": "多次发布广告" }
```

- `duration_hours`：正整数；`null` 或省略表示永久；
- `reason` 必填，最长 500；
- 不能禁言自己；
- 插入 `user_mutes`，写审计，发 `forum_mute` 通知；
- 解除禁言：

```http
DELETE /api/admin/forum/users/{id}/mute
```

把当前有效禁言记录的 `revoked_at` 设为 `now()`，写审计并通知。

  "total": 3,
  "page": 1,

## 7. 关键流程

### 7.1 发帖流程

```text
POST /api/forum/posts
  → 认证（401）
  → 检查论坛开关（503）
  → 检查有效禁言（403）
  → 校验标题/正文/标签/题目引用
  → 频率限制（429）
  → 插入 forum_posts
  → 解析 @ 提及（可选，发通知）
  → 返回 id/status
```

事务边界：

- 帖子插入和 @ 通知同事务；
- @ 解析失败不应导致发帖失败：提及解析在事务内但单个用户不存在时跳过，不报错；
- 匿名标记只影响序列化，不影响写入。

### 7.2 评论/回复流程

```text
POST /api/forum/posts/{id}/comments
  → 认证、禁言、频率限制
  → 锁定帖子行，确认 published
  → 解析 parent/reply_to，归一化根评论
  → 插入 forum_comments
  → 重算 comment_count
  → 生成通知：
      1. 帖子作者（评论/回复都通知，若与操作者不同）
      2. 被回复评论作者（若与操作者和帖子作者不同）
      3. @ 提及用户（与以上去重）
  → 提交事务
  → 返回评论
```

通知去重顺序：回复目标 > 帖子作者 > @ 提及；同一用户只保留优先级最高的一条。

### 7.3 点赞/收藏流程

```text
POST /like
  → 认证
  → 帖子 published
  → INSERT ... ON CONFLICT DO NOTHING
  → 插入成功才 like_count + 1
  → 返回 liked=true + 最新计数
```

删除同理，使用 `DELETE ... RETURNING` 判断是否真的删除。

不产生通知，避免点赞刷屏。

### 7.4 举报与自动隐藏

```text
POST /api/forum/reports
  → 认证
  → 目标存在且 published，且不是自己的内容
  → 举报日限额
  → 事务开始
      → 锁定目标行
      → INSERT forum_reports（唯一约束防重复）
      → pending_report_count + 1
      → 若 >= 阈值 且仍 published：
          → status = hidden
          → hidden_reason = report_threshold
          → hidden_by = NULL
          → hidden_at = now()
          → 写 moderation_actions（system）
          → 通知作者
  → 提交
  → 返回 report_id + hidden
```

自动隐藏不处理举报本身，举报仍保持 `pending`，等待管理员复核。

### 7.5 管理员处理举报

```text
PUT /api/admin/forum/reports/{id}
  → require_admin
  → 锁定 pending 举报，404/409
  → 锁定目标行
  → decision = hide：
      → 举报 resolved
      → 目标 hidden（moderation）
      → 该目标所有 pending 举报 resolved
      → pending_report_count = 0
      → 审计 + 通知作者
  → decision = keep：
      → 举报 rejected
      → pending_report_count - 1
      → 若目标仅因阈值隐藏且剩余 < 阈值：
          → 恢复 published
          → 审计 + 通知作者
```

### 7.6 禁言流程

- 管理员在管理端内容页或举报页点击“禁言作者”。
- 选择时长（1 小时 / 24 小时 / 7 天 / 永久）并填写原因。
- 写入 `user_mutes`、审计、通知。
- 发帖/评论/编辑前统一调用 `ensure_not_muted(pool, user_id)`。
- 解除禁言：把当前有效记录 `revoked_at = now()`，审计、通知。

### 7.7 @ 提及

- 解析正则：`(?:^|\s)@([^\s@]{3,50})`。
- 去掉末尾常见标点：`, . : ; ! ? ，。：；！？、)】`。
- 按 `users.username` 精确匹配，最多处理 10 个提及。
- 不匹配、自己、重复提及都跳过。
- 匿名作者的通知文案用“匿名同学”。
- 提及只产生站内通知，不改变权限、不自动关注。

## 9. 安全、隐私与反滥用

### 9.1 XSS

- Markdown 原始 HTML 不可信；DOMPurify 白名单清洗。
- 禁止 `img`，避免 `<img onerror>`。
- 链接协议白名单。
- 代码块内容转义。
- 管理端预览同样清洗，不能因为管理员身份放宽。
- 通知正文只存纯文本摘要，不存 HTML。

### 9.2 越权与 IDOR

- 编辑/删除必须校验 `author_id = current_user.id` 或 `is_admin`。
- 匿名内容权限判断用 `author_id`，不能用展示名。
- 管理端全部走 `require_admin`。
- 举报目标必须真实存在；不能通过 `target_id` 探测隐藏内容（返回 404/409 不泄露正文）。
- 评论的 `parent_id` / `reply_to_comment_id` 必须同帖，防止跨帖串楼。

### 9.3 匿名隐私

- 公开序列化层统一处理匿名作者，禁止在 SQL 查询后忘记裁剪。
- 日志中不打印匿名帖子正文与作者映射。
- 管理端页面明确标注“仅管理员可见真实身份”。
- 导出/审计功能后续需单独授权。

### 9.4 频率限制

配置项：

| 配置 | 默认 | 说明 |
|---|---|---|
| `FORUM_ENABLED` | `true` | 论坛功能开关 |
| `FORUM_POST_COOLDOWN_SECS` | `60` | 两次发帖最小间隔 |
| `FORUM_POST_DAILY_LIMIT` | `20` | 每用户每日发帖上限 |
| `FORUM_COMMENT_COOLDOWN_SECS` | `10` | 两次评论最小间隔 |
| `FORUM_COMMENT_DAILY_LIMIT` | `200` | 每用户每日评论上限 |
| `FORUM_REPORT_DAILY_LIMIT` | `20` | 每用户每日举报上限 |
| `FORUM_REPORT_HIDE_THRESHOLD` | `3` | 自动隐藏阈值 |
| `FORUM_MAX_PINNED` | `5` | 最大置顶数 |

实现方式：按 `author_id + created_at` 查询计数；索引已覆盖。管理员是否绕过频率限制：默认不绕过，公告也需要遵守冷却；如需运营便利，可后续加 `admin` 豁免开关。

### 9.5 内容风险

- 首期不做敏感词库，但预留 `forum_service::check_content` 钩子。
- 举报 + 自动隐藏 + 人工复核是主要治理手段。
- 删帖软删除，保留审计；30–90 天后由运维清理（本期不做自动清理任务）。
- 不提供图片上传，减少内容安全与存储风险。
- 帖子/评论长度上限防止超长内容拖垮页面。

### 9.6 审计

`moderation_actions.action` 取值：

```text
hide_post
restore_post
delete_post
hide_comment
restore_comment
delete_comment
auto_hide_post
auto_hide_comment
pin_post
unpin_post
mute_user
unmute_user
resolve_report
reject_report
```

`metadata` 记录必要上下文：

```json
{
  "before_status": "published",
  "after_status": "hidden",
  "report_id": 9,
  "duration_hours": 24
}
```

### 11.2 集成/冒烟测试 `smoke_forum.sh`

前置：

- API、PostgreSQL 正常运行；
- 至少一道已审核题目（默认 1001）；
- 注册三个一次性账号：作者 A、评论者 B、管理员 C；
- 管理员通过 SQL 或已有管理员账号设置，脚本不修改真实管理员密码。

用例：

1. A 发匿名帖，引用题 1001，返回 201；
2. 游客列表能看到帖子，且无作者真实身份；
3. B 评论，A 收到 `forum_comment` 通知；
4. A 回复 B，B 收到 `forum_reply` 通知；
5. B 回复自己的回复，`parent_id` 仍为根评论；
6. B 点赞两次，计数只 +1；取消后 -1；收藏同理；
7. B 举报帖子，`hidden=false`；
8. B 用第二个账号再举报，达到阈值后 `hidden=true`，游客详情 404；
9. 管理员列表能看到真实作者，恢复帖子；
10. 管理员处理举报 `keep`，帖子保持 published；
11. 管理员禁言 B，B 评论返回 403；解除后可评论；
12. A 编辑帖子，`edited_at` 非空；
13. A 删除帖子，游客 404；
14. 匿名帖在通知文案中不出现 A 的用户名；
15. 清理测试账号、帖子、评论、通知、举报、禁言记录。

脚本默认清理数据；不默认回滚题目计数（论坛不涉及题目计数）。报告写 `.dev-logs/smoke-forum-<UTC>.log/.json`。

## 12. 待确认与后续演进

### 12.1 待确认

1. 论坛是否允许游客浏览？本方案默认允许；若学校要求全部登录后可见，只需在路由和接口加认证。
2. 匿名帖是否允许出现在热门/搜索？本方案默认允许，仅隐藏身份。
3. 教师是否需要论坛治理权？本方案默认仅管理员；若需要，后续加 `forum.moderate` 权限码并授予教师。
4. 是否需要帖子编辑历史？本方案不做，后续可加 `forum_post_revisions`。
5. 是否需要图片/附件？本方案不做，后续需对象存储与内容安全。
6. 邮件通知是否与论坛同时上线？本方案只做站内信；邮件等统一 outbox。
7. 举报自动隐藏阈值 3 是否合适？上线后按实际误伤率调整。
8. 禁言是否也阻止点赞/收藏？本方案不阻止，只阻止发帖/评论/编辑。

### 12.2 后续演进

- **通知统一化**：作业发布、成绩、系统广播复用 `notifications`，增加 `notification_preferences` 和 `email_outbox`。
- **论坛搜索**：`pg_trgm`、中文分词、独立搜索服务。
- **内容审核**：敏感词、链接黑名单、AI 辅助分类，仅作提示不自动定罪。
- **帖子增强**：编辑历史、投票、精华、关注作者、收藏夹。
- **管理端增强**：批量处理举报、用户禁言记录、审计导出、内容统计。
- **移动端**：底部导航、通知中心、发帖简化。
- **反滥用**：新账号发帖冷却、重复内容指纹、IP/设备风控（需隐私告知）。

### 13.1 后端模块职责

| 模块 | 职责 |
|---|---|
| `models/forum.rs` | 请求/响应结构、FromRow、序列化 |

### 13.2 关键错误文案

| 场景 | 状态码 | 文案 |
|---|---|---|
| 未登录写操作 | 401 | 请先登录 |
| 被禁言 | 403 | 你已被禁言，解除后可继续发言 |
| 编辑他人内容 | 403 | 没有执行该操作的权限 |
| 帖子不存在/不可见 | 404 | 帖子不存在或已被删除 |
| 评论不存在/不可见 | 404 | 评论不存在或已被删除 |
| 重复举报 | 409 | 你已举报过该内容 |

| 发帖过快 | 429 | 发帖过于频繁，请稍后再试 |
| 评论过快 | 429 | 评论过于频繁，请稍后再试 |
| 论坛关闭 | 503 | 论坛功能暂未开放 |

### 13.4 与总体设计的对应关系

| 总体设计条目 | 本方案落地 |
|---|---|
| 发帖、编辑、软删除 | `forum_posts.status` + `DELETE` 软删除 |
| 评论、回复、点赞 | 两级评论 + `forum_post_likes` |
| 引用题目 | `forum_posts.problem_id` + 题目卡片 |
| 标签、搜索、热门/最新 | 固定标签 + `ILIKE` + `latest/hot` |
| 匿名/昵称 | `is_anonymous` + 公开序列化裁剪 |
| 举报、屏蔽、禁言 | `forum_reports` + `user_mutes` |
| 题解/剧透标记 | 本期不做，标签 `solution` 先兜底 |
| 被回复/被引用/@/审核通知 | `notifications` |
| 敏感词/链接/频率限制 | 频率限制已做；敏感词预留钩子 |
| 管理员隐藏/删除/禁言/置顶 | 管理端接口齐全 |
| 审计 | `moderation_actions` |
| 软删除保留 30–90 天 | 本期只软删除，清理任务后续 |
