# 提交/运行示例会卡住原因

- 日期：2026-10-25
- 关联文档：[2610241_运行代码功能设计方案](./2610241_运行代码功能设计方案.md)
- 涉及代码：`backend-rust/src/services/run_service.rs`、`backend-rust/src/bin/judge_worker.rs`、`backend-rust/src/judge/queue.rs`

## 0. 结论速览

点击「运行」后提示「已有运行任务正在进行，请等待其结束」，并不是代码执行慢，而是：

1. `POST /api/runs` 会给用户加一个 **600 秒**的并发锁；
2. 任务被写入 Redis Stream 后，**Judge Worker 没有运行**，消息无人消费；
3. 这个锁只有 Worker 处理完任务才会主动释放，所以只能等 TTL 自然过期（10 分钟）。

属于「排队任务没有超时 / 不检测 Worker 是否在线」的设计缺口，详见第 4、5 节。

修复上述缺口之后，又暴露出**第二个独立的卡住原因**：

4. 沙箱启动时用 `docker cp` 注入代码，而容器同时启用了 `--read-only` 与 `--tmpfs /workspace`，Docker 的 `checkWritablePath` 不认 tmpfs，直接拒绝：`container rootfs is marked read-only`；
5. 该错误被 `AppError::Internal` 的 Display 掩盖成「内部服务错误」，任务每 ~120 秒被重试一次，直到达到最大投递次数才进入终态，期间并发锁一直被占用。

详见第 8 节。

## 1. 现象

- 在题目页点击「运行」，结果面板提示：`已有运行任务正在进行，请等待其结束`。
- 无论等待多久、刷新页面，再次运行仍然是同样的提示，直到约 10 分钟后才恢复。
- 数据库中该运行一直停留在 `queued`，`attempt_count = 0`。

## 2. 原因分析

### 2.1 调用链

```
前端 POST /api/runs
  └─ RunService::create
       ① enforce_rate()                      // 每分钟 10 次
       ② SET theseus:run:concurrency:{user_id} <token> NX EX 600
       ③ INSERT code_runs (status='queued')
       ④ SET theseus:run:concurrency:{user_id} = {run_id}   // swap_lock
       ⑤ XADD theseus:judge:runs {run_id}
       ⑥ 返回 run_id，前端开始轮询

Judge Worker
       ⑦ XREADGROUP 领取消息
       ⑧ UPDATE status='compiling' → 创建容器 → 编译 → 逐用例执行
       ⑨ UPDATE code_runs 写终态 + 写 Redis 状态缓存
       ⑩ release_user_lock()                // 删除并发锁
       ⑪ XACK
```

**第 ⑩ 步是唯一的正常释放点。** Worker 不运行，第 ⑦ 步就不会发生，锁只能等 600 秒 TTL 过期。

### 2.2 本次现场数据（实测）

| 项目 | 值 |
|---|---|
| `judge_worker` 进程 | 未运行 |
| Worker 心跳 `theseus:run:worker:*` | 无 |
| `code_runs` | `id=1, user_id=2, problem_id=1001, language=cpp, mode=examples, status=queued, attempt_count=0` |
| `theseus:judge:runs` 长度 | 1（消息无人消费） |
| `theseus:run:concurrency:2` | 存在，值为 `1`（即 run_id），TTL 剩余 462s |

### 2.3 为什么是 600 秒

**（修复前的代码）** `run_service.rs` 中：

```rust
const CONCURRENCY_TTL_SECONDS: u64 = 600;
```

锁的 TTL 是固定值，与任务是否真的在执行无关。它只是「兜底自动过期」，不是「任务超时」。

**（修复后）** 已改为按任务计算，见 5.3：

```rust
fn concurrency_ttl(queue_timeout_secs: u64, case_total: i32) -> u64 {
    queue_timeout_secs + RUN_TIMEOUT_SECONDS + case_total * CASE_TIMEOUT_SECONDS + LOCK_TTL_BUFFER_SECONDS
}
```

### 2.4 Worker 为什么没起来

Worker 需要访问 `/var/run/docker.sock` 创建沙箱容器。当前 shell 会话没有 docker 组权限（`usermod` 之后未重新登录），直接运行会报：

```
permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

正确启动方式：

```bash
cd backend-rust
sudo ./target/debug/judge_worker
# 或者：重新登录一个终端（docker 组生效后）直接运行
./target/debug/judge_worker
```

## 4. 设计缺口

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 创建任务前不检查 Worker 是否存活 | Worker 全部离线时仍然接收任务，必然卡住 |
| 2 | 排队任务没有超时回收 | 任务可以无限期 `queued`，占着用户并发锁 |
| 3 | 锁 TTL（600s）与实际执行时长无关 | 正常完成前锁一直占着；异常时最长卡 10 分钟 |
| 4 | 前端无法区分「自己的任务在跑」和「没有 Worker」 | 提示误导，用户只能等待 |

## 5. 超时与保护机制设计

建议 **5.1 + 5.2 组合**：前者快速失败，后者兜底回收。

### 5.1 提交前检查 Worker 心跳（快速失败）

Worker 已经在写心跳（`judge_worker.rs::heartbeat_loop`）：

- Key：`theseus:run:worker:{RUN_WORKER_NAME}`
- 每 10 秒 `SET key 1 EX 30`
- 退出时 `DEL key`

在 `RunService::create` 的限流之后、加锁之前增加检查：

```text
SCAN 0 MATCH theseus:run:worker:* COUNT 100
```

- 有结果 → 继续正常流程；
- 无结果 → 直接返回 `503 ServiceUnavailable("评测服务暂不可用，请稍后再试")`；
- **不创建数据库记录、不占用并发锁、不消耗限流次数**（或把限流放在检查之后）。

注意点：

- 心跳 TTL 30s，Worker 崩溃后最多 30s 内仍被视为在线，属于可接受误差；
- 目前心跳是「每个 Worker 一个 key」，用 Redis `SCAN` 即可；数量很少，成本可忽略；
- 如果以后 Worker 数量很大，可改用 `theseus:run:workers:alive` ZSET（score 为刷新时间）维护存活集合。

### 5.2 排队超时回收（兜底，核心）

**回收逻辑必须放在 API 侧**，不能放在 Worker 里 —— 因为要解决的正是「没有 Worker」的场景。建议在 API 进程启动一个后台任务，每 30 秒执行一次：

```text
① 选出超时任务：
   status = 'queued'  AND created_at < now() - RUN_QUEUE_TIMEOUT_SECS
   OR
   status IN ('compiling','running') AND started_at < now() - RUN_STALE_TIMEOUT_SECS

② 逐条处理（带条件更新，避免和 Worker 正常写入竞争）：
   UPDATE code_runs
      SET status='internal_error',
          error_message='排队超时：评测服务不可用',
          finished_at=CURRENT_TIMESTAMP
    WHERE id=$1
      AND status IN ('queued','compiling','running')

③ 更新/删除 Redis 状态缓存 theseus:run:status:{id}
④ release_user_lock(redis, user_id, run_id)   // Lua CAS，值为 run_id 才删除
⑤ 可选：死信/日志告警
```

关键细节：

- **锁释放必须 CAS**（现有 `release_user_lock` 已实现）：只删除值为 `run_id` 的锁，避免误删用户新任务的锁。
- **Stream 消息不需要 API 删除**：`process_run` 会先检查 `is_terminal_status`，终态记录会被直接 `XACK`（`judge_worker.rs:351`）。Worker 下次启动会清理掉这条消息。
- **条件更新很重要**：避免 Worker 刚好完成、API 又把它改成 `internal_error`。所有 UPDATE/终态写入都应带 `status NOT IN (终态)` 条件，现有 `finish_run` 已经这样做了。
- 建议状态文案区分原因：
  - `排队超时：评测服务不可用`（queued 超时）
  - `执行超时：Worker 可能已离线`（compiling/running 超时）
- 如果希望更精确，可新增 `expired` 状态；但为了少改前端和数据库枚举，先复用 `internal_error` + `error_message`。

### 5.3 用户并发锁 TTL 对齐

当前锁 TTL 固定 600 秒。建议改为：

```text
RUN_LOCK_TTL_SECS = RUN_QUEUE_TIMEOUT_SECS
                  + COMPILE_TIMEOUT(10s)
                  + 用例数 × CASE_TIMEOUT(2s)
                  + 缓冲(30s)
```

由于用例数在创建时已知（`case_total`），可以按任务计算；或者简化为固定 300 秒，并保留 5.2 的主动回收。

注意：**不能只靠缩短 TTL**。锁提前过期会导致同一用户同时跑两个任务，因此它只能作为兜底，不能替代 5.2。

### 5.4 前端提示

- 429（`AppError::RateLimited`）：`已有运行任务正在进行，请等待其结束`（现状，保留）；
- 503（Worker 离线）：`评测服务暂不可用，请稍后再试`；
- 超时回收后的运行记录：状态显示为 `internal_error`，详情/列表中展示 `error_message`；
- 可选优化：状态轮询超过 `RUN_QUEUE_TIMEOUT_SECS` 仍为 `queued` 时，前端提示「仍在排队，请确认 Worker 是否启动」。

### 5.5 新增配置项

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `RUN_QUEUE_TIMEOUT_SECS` | 90（下限 30） | `queued` 超过该时长视为排队超时 |
| `RUN_STALE_TIMEOUT_SECS` | 300 | `compiling/running` 无进展的兜底超时；实现上会 `.max(RUN_QUEUE_TIMEOUT_SECS)`，配得比排队超时小也会被抬高 |
| `RUN_REAPER_INTERVAL_SECS` | 30（下限 5） | 回收扫描间隔 |

> **修正**：初稿里的 `RUN_LOCK_TTL_SECS` **没有**落地为环境变量。锁 TTL 由 `concurrency_ttl(queue_timeout, case_total)` 在创建任务时按任务计算，不需要也不能单独配置。

## 8. 第二个卡住原因：沙箱启动失败（已修复）

### 8.1 现象

Worker 日志（2026-10-25 13:12–13:19，run 4，cpp）：

```
ERROR judge_worker: failed to start sandbox, leaving run pending run_id=4 error=内部服务错误
WARN  judge_worker: run left pending for retry after infrastructure error run_id=4
WARN  judge_worker: recovered stale run message run_id=4 attempt=1 / 2 / 3
```

现场特征：

| 观察 | 值 |
|---|---|
| `code_runs` | `id=4, status=compiling, attempt_count=3` |
| 重试节奏 | 每约 120 秒一次（claimer 的 `CLAIM_MIN_IDLE_MS = 120_000`） |
| 容器生命周期 | `theseus-run-4-*` 每次只存在约 100–200ms 就被清理 |
| 并发锁 | `theseus:run:concurrency:2 = 4` 一直被占用，用户再点运行仍是 429 |

也就是说：`docker run -d` 本身是成功的，失败发生在**随后的文件注入**阶段；失败后任务被「留待重试」，锁不会释放。重试到第 `RUN_MAX_DELIVERIES`（默认 3）次才进死信 + `internal_error`，所以用户看到的就是长时间卡住。

### 8.2 为什么日志只有「内部服务错误」

`AppError::Internal(String)` 的 `Display` 是固定的「内部服务错误」，真实原因在 payload 里：

```rust
#[error("内部服务错误")]
Internal(String),
```

而 Worker 日志用的是 `%error`（Display），detail 被直接丢掉；API 的 `IntoResponse` 也只是丢弃 detail 后返回通用文案，服务端没有任何记录。

修复（已落地）：

- `common/error.rs`：`IntoResponse` 的 `Internal(detail)` 分支增加 `tracing::error!(error = %detail, "internal server error")`，客户端文案保持通用（不外泄内部信息）；
- `bin/judge_worker.rs`、`services/run_service.rs`：所有 `AppError` 的日志从 `%error` 改为 `?error`（Debug 会带出 `Internal("...")`）；纯 Redis 错误保留 `%error`。

### 8.3 根因：`docker cp` 无法写入 `--read-only` + `--tmpfs` 容器

沙箱启动参数（`judge/runner.rs::start_container`）：

```
docker run -d --read-only \
  --tmpfs /workspace:rw,exec,size=128m,mode=1777 \
  --tmpfs /tmp:rw,exec,size=32m ...
```

原实现用 `docker cp` 把 `runner.py` / `main.cpp` / `case.json` 放进 `/workspace`，再从容器里 `cp` 出 `result.json`。Docker 28.5.2 源码（`daemon/archive_unix.go`）：

```go
// daemon/archive_unix.go:130 —— docker cp 解包前
if err := checkWritablePath(container, absPath); err != nil {
    return err
}

// daemon/archive_unix.go:161
func checkWritablePath(ctr *container.Container, absPath string) error {
    parser := volumemounts.NewParser()
    for _, mnt := range ctr.MountPoints {      // 只看 -v / --mount
        ...
    }
    if ctr.HostConfig.ReadonlyRootfs {         // HostConfig.Tmpfs 不参与判断
        return errdefs.InvalidParameter(errors.New("container rootfs is marked read-only"))
    }
    return nil
}
```

`HostConfig.Tmpfs` 不在 `MountPoints` 里，于是 `/workspace` 被当成只读根文件系统的一部分，cp 必然返回 `container rootfs is marked read-only`——与 `--tmpfs` 上的 `rw` 无关。

即使去掉 `--read-only` 也不行：Docker 28+ 的 cp 通过 `openContainerFS` 在**私有 mount namespace** 中操作，`daemon/containerfs_linux.go:34` 的注释写得很明确：

> Each view has its own private set of tmpfs mounts. Any files written under a tmpfs mount are not visible to processes inside the container nor any other view of the container's filesystem, and vice versa.

即 cp 写进去的是另一份空的 tmpfs，容器内的进程看不到。

**结论**：工作目录是 tmpfs 时，只能通过容器内进程读写文件（`docker exec`），不能用 `docker cp`。

### 8.4 修复

`judge/runner.rs`：

| 原实现 | 新实现 |
|---|---|
| `copy_to_container(ctr, src, dst)` | `write_to_container(workspace, ctr, file)`：`docker exec -i --user 65534:65534 <ctr> sh -c 'cat > /workspace/<file>'`，宿主机文件接 stdin |
| `copy_from_container(ctr, path)` | `read_from_container(ctr, file)`：`docker exec --user 65534:65534 <ctr> cat /workspace/<file>`，从 stdout 读回 |
| `read_result_file` / `read_output_file` 基于 cp | 改为基于 `read_from_container` |

安全边界不变：`--read-only`、`--network=none`、`--cap-drop=ALL`、`--security-opt=no-new-privileges`、`--user 65534:65534`、内存/CPU/PID/nofile 限制全部保留；只是把文件通道从 docker daemon 的 cp 换成容器内的 `cat`。

## 9. 对已落地修复的 review

### 9.1 结论：核心逻辑正确，保留

- **心跳检查位置正确**：`has_live_worker` 在 `enforce_rate` 之前，Worker 离线时不消耗限流额度、不建记录、不加锁，直接 503；
- **条件更新正确**：`expire_stale_runs` 的两条 `UPDATE ... RETURNING` 都只处理 `queued` / `compiling|running` 且带时间条件，不会覆盖 Worker 已写入的终态；
- **锁释放是 CAS**：`release_user_lock` 只在值等于 `run_id` 时删除，不会误删用户新任务的锁；
- **reaper 放在 API 进程是对的**：只有这样才能覆盖「所有 Worker 都挂了」的场景；
- **Stream 清理策略正确**：超时任务不删消息，Worker 恢复后看到终态直接 `XACK`。

### 9.2 与文档不一致、已修正的地方

1. `RUN_LOCK_TTL_SECS` 并未落地为环境变量，而是 `concurrency_ttl()` 在创建任务时按 `case_total` 计算（见 5.5 修正）；
2. `RUN_STALE_TIMEOUT_SECS` 有 `.max(RUN_QUEUE_TIMEOUT_SECS)` 下限，配得比排队超时小会被抬高；
3. 5.6 的改动点已按实际函数名与位置更新。

### 9.3 仍需注意的风险

1. **修复代码还没生效**：本次现场中 API 启动于 12:47、Worker 启动于 13:12，而修复后的 binary 编译于 13:18。reaper、心跳检查、`docker exec` 修复都还在旧进程之外，必须重启（第 10 节）。
2. **心跳只代表进程活着，不代表能跑**：Worker 启动时不会 ping docker，Docker 权限或镜像缺失时它仍会写心跳并领取任务，结果就是第 8 节的重复重试。建议后续在 Worker 启动时执行 `docker info` 并校验 4 个运行镜像，失败直接退出（不写心跳）。
3. **确定性错误也在走重试**：`failed to start sandbox` 这类错误每次必然失败，却仍按 120s 间隔重试最多 3 次，最坏拖约 6 分钟。可以区分「基础设施暂时性错误」（Redis/DB 断连）与「确定性错误」（镜像不存在、exec 失败），后者直接终态并释放锁。
4. **普通失败分支不立即释放锁**：死信分支会 `release_user_lock`，但 `process_run` 的 sandbox 启动失败分支只是「留待重试」，锁要等到重试终态或 reaper 才释放。若希望用户尽快重试，可在这里对齐死信分支的行为。

## 10. 生效步骤与验收

1. 停掉当前 `dev.sh`（Ctrl+C）；若 root Worker 没退出，补一刀：`sudo pkill -f judge_worker`；
2. 确认 3000 端口没有旧 API 进程（`ss -ltnp | grep :3000`），必要时结束它；
3. 重新启动：

   ```bash
   cd ~/LosAngelous/Theseus
   ./dev.sh
   ```

   `dev.sh` 会重新编译两个 binary，并用新代码启动 API 与 Worker；
4. 验收：
   - `redis-cli --scan --pattern 'theseus:run:worker:*'` 有心跳，Worker 日志出现 `judge worker started`；
