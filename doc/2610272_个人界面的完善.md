## 1. 目标与非目标

### 1.1 目标

1. 个人页不再重复显示“个人中心”大标题，信息层级更清楚。
2. 用户可以自助修改用户名、邮箱和密码，并看到邮箱验证状态。
3. 邮箱变更必须先验证新邮箱，避免写错邮箱或账号被盗后直接换绑。
4. 用户可以退出所有设备，并在注销后立即失去登录能力。
5. 注销账号保留教学记录，但用户名、邮箱等身份信息匿名化。
6. 个人页展示学习概览、快捷入口和近 30 天学习分析。
7. 支持头像上传、裁剪、替换和删除，适合单机服务器部署。
8. 用户可以查看和取消自己的论坛收藏。
9. 主题支持跟随系统，且不依赖服务端配置。

### 1.2 非目标

本轮明确不做：

- Plus 会员、积分、订单、支付、笔记本等商业化功能；
- 头像审核、敏感图片识别或对象存储；
- 多设备会话列表与单独踢出某个设备；
- 注销冷静期或管理员恢复已注销账号；
- 管理员替用户修改邮箱或密码；
- 学习分析的班级维度、教师视角或导出；
- 题目语言切换、国际化完整方案；
- 个人主页公开访问或他人主页；
- 自定义背景、主题色、字体大小。

## 4. 账号与安全

### 4.1 修改用户名

接口：`PUT /api/profile/username`

请求：

```json
{ "username": "new_name" }
```

规则：

- 去除首尾空白；
- 3–50 个字符，按 Unicode 字符数计算；
- 不允许空白字符、控制字符和 `@`；
- 唯一性冲突返回 409“用户名已存在”；
- 不能与当前用户名相同，返回 400；
- 修改成功后返回最新用户信息，前端同步 Pinia 和 localStorage；
- 不需要密码，这是已确认规则。

实现：

```sql
UPDATE users
SET username = $2, updated_at = CURRENT_TIMESTAMP
WHERE id = $1 AND status = 'active'
RETURNING id, username, email, role, email_verified_at, avatar_path, pending_email, created_at;
```

唯一冲突使用现有 `is_unique_violation` 判断。

### 4.2 修改邮箱

邮箱变更分为三步：

```text
提交新邮箱 → 新邮箱收到验证链接 → 点击验证后切换
```

接口：

```text
POST   /api/profile/email
DELETE /api/profile/email/pending
POST   /api/auth/verify-email
```

`POST /api/profile/email` 请求：

```json
{ "email": "new@example.com" }
```

规则：

- 邮箱格式校验，长度不超过 100；
- 统一转小写；
- 不能与当前邮箱相同；
- 不能与其他用户邮箱或待验证邮箱冲突；
- 写入 `users.pending_email`；
- 生成 purpose = `email_change` 的一次性 token，24 小时过期；
- 向新邮箱发送验证链接；
- 向旧邮箱发送安全提醒；
- 同一用户重复请求时，旧 token 失效或自然过期，只保留最新 pending_email。

验证：

- 复用 `POST /api/auth/verify-email`；
- `auth_tokens.purpose = 'email_change'` 时：
  1. 锁定用户行；
  2. 确认 `pending_email` 非空；
  3. 再次校验新邮箱唯一性；
  4. `email = pending_email`；
  5. `pending_email = NULL`；
  6. `email_verified_at = NOW()`；
  7. 标记 token 已使用；
  8. 提交事务。
- 验证成功后不需要重新登录。
- 验证前旧邮箱仍可登录和找回密码。

取消：

- `DELETE /api/profile/email/pending` 清空 `pending_email`；
- 同时使该用户所有 `email_change` token 失效；
- 返回当前用户信息。

### 4.3 修改密码

接口：`PUT /api/profile/password`

请求：

```json
{
  "current_password": "old-password",
  "new_password": "new-password"
}
```

规则：

- 当前密码必须正确，否则 401“当前密码错误”；
- 新密码 8–128 字符；
- 新密码不能与当前密码相同；
- 使用现有 Argon2 哈希；
- 更新密码后 `token_version = token_version + 1`；
- 用新 `token_version` 生成新 token 返回，当前浏览器保持登录；
- 其他设备旧 token 因版本不匹配立即失效；
- 向当前邮箱发送密码变更提醒。

响应：

```json
{
  "token": "new-jwt",
  "user": {
    "id": 7,
    "username": "alice",
    "email": "alice@example.com",
    "role": "student",
    "avatar_url": null,
    "pending_email": null,
    "email_verified": true,
    "created_at": "..."
  }
}
```

### 4.4 退出所有设备

接口：`POST /api/auth/logout-all`

规则：

- 递增 `token_version`；
- 当前 token 也失效；
- 前端收到成功后清除本地会话并跳转登录页；
- 返回 `{ "message": "已退出所有设备" }`。

### 4.5 注销账号

接口：`DELETE /api/profile`

请求：

```json
{
  "password": "current-password",
  "username": "current-name"
}
```

前置条件：

- 当前密码正确；
- 输入的用户名与当前用户名一致；
- 教师不能拥有未归档的自有班级，否则 409“请先归档你的班级”；
- 最后一个管理员不能注销，否则 409；
- 账号必须是 `active`。

事务步骤：

1. 使用 `pg_advisory_xact_lock` 保护管理员数量检查，避免并发注销最后一个管理员；
2. 锁定用户行；
3. 校验密码和用户名；
4. 教师检查未归档班级；
5. 学生 active 班级成员关系改为 `removed`，写 `removed_at`；
6. 生成匿名用户名和邮箱：
   - `deleted_{id}`；
   - `deleted_{id}@deleted.local`；
7. 清空 `avatar_path`、`pending_email`、`password_hash`；
8. 设置 `status = 'deleted'`、`deleted_at = NOW()`；
9. 递增 `token_version`；
10. 使该用户所有未使用 auth token 失效；
11. 提交事务；
12. 事务成功后删除头像文件。

保留数据：

- 提交、运行记录、成绩、论坛历史保留；
- 教师归档班级保留历史 owner；
- 学生已移除的班级关系保留历史；
- 不物理删除用户行，避免破坏外键和历史记录。

### 4.6 账号状态与认证

新增 `users.status`：

```text
active     正常
disabled   管理员禁用
deleted    用户已注销
```

规则：

- 登录只允许 `active`；
- 认证中间件每次读取 `status`，非 `active` 返回 401；
- `disabled` 由管理员操作，不在本期个人页面提供；
- 管理员用户列表可以展示状态，但本期不新增启用/禁用按钮；
- 注销后所有旧 token 因 `token_version` 和状态检查双重失效。

## 5. 头像

### 5.1 存储

- 数据库：`users.avatar_path VARCHAR(255)`，保存相对路径，例如 `avatars/7_a1b2c3.jpg`。
- 文件系统：`UPLOAD_DIR/avatars/`。
- 默认 `UPLOAD_DIR=./uploads`。
- 生产环境建议 `UPLOAD_DIR=/var/lib/theseus/uploads`，并挂载持久化卷。
- `uploads/` 加入 `.gitignore`。
- 部署文档说明：备份数据库时必须同时备份上传目录。

### 5.2 上传校验

- multipart 字段名：`file`；
- 最大 2MB；
- 只允许 JPG/PNG/WebP；
- 不只信任 `Content-Type`，必须用 `image` crate 解码验证；
- 解码失败返回 400“不支持的图片格式”；
- 图片尺寸过小（小于 64×64）返回 400；
- 文件名由后端生成，不使用用户文件名；
- 每个用户只保留一个头像文件。

### 5.3 处理

1. 读取上传字节；
2. 校验大小；
3. 解码图片；
4. 居中裁剪为正方形；
5. 缩放到 256×256；
6. 编码为 JPEG，质量 85；
7. 写入 `UPLOAD_DIR/avatars/{user_id}_{random}.jpg`；
8. 更新 `users.avatar_path`；
9. 事务提交后删除旧头像文件。

### 5.4 静态访问

- 后端挂载 `/uploads` 静态目录；
- 返回给前端的 `avatar_url` 为 `/uploads/avatars/...`；
- Vite 开发代理增加 `/uploads` → `http://127.0.0.1:3000`；
- 生产环境由 Nginx 直接提供静态文件，或由后端静态服务处理；
- 图片响应设置长期缓存，文件名随机化避免缓存击穿。

### 5.5 删除头像

`DELETE /api/profile/avatar`：

- 清空 `avatar_path`；
- 删除文件；
- 返回最新用户信息；
- 文件不存在时仍返回成功，保证幂等。

## 6. 学习分析

### 6.1 接口

`GET /api/profile/analytics?days=30`

- 仅登录用户本人可访问；
- `days` 范围 7–90，默认 30；
- 非法值返回 400；
- 不返回其他用户数据；
- 管理员只能看自己的个人统计。

### 6.2 响应

```json
{
  "days": 30,
  "summary": {
    "accepted_problems": 42,
    "attempted_problems": 60,
    "total_submissions": 180,
    "accepted_submissions": 95,
    "acceptance_rate": 52.8,
    "active_classes": 2,
    "streak_days": 5
  },
  "trend": [
    { "date": "2026-10-01", "submissions": 5, "accepted": 3 }
  ],
  "difficulty": [
    { "difficulty": "easy", "attempted": 20, "accepted": 15 },
    { "difficulty": "medium", "attempted": 25, "accepted": 12 },
    { "difficulty": "hard", "attempted": 15, "accepted": 4 }
  ],
  "tags": [
    { "tag": "数组", "attempted": 12, "accepted": 8 }
  ]
}
```

### 6.3 统计口径

- 范围：最近 `days` 天内的提交，趋势和难度/标签按该范围统计；
- 汇总中的“通过题目/已尝试题目”统计用户全部历史，不受 `days` 限制；
- 包含练习提交和带 `assignment_id` 的作业提交；
- 通过判断使用 `submissions.status = 'accepted'`；
- 通过率 = 通过提交数 / 总提交数 × 100，保留 1 位小数；
- 连续通过天数：从今天或昨天开始，向前连续存在至少一次 accepted 提交的天数；
- 标签来自 `problems.tags`，一个提交命中多个标签时分别计数；
- 题目被删除后历史提交仍保留，统计不依赖题目是否仍在题库。

### 6.4 查询策略

- 趋势：按 `DATE(submitted_at)` 聚合，Rust 中补齐缺失日期；
- 难度：`submissions JOIN problems` 按 difficulty 聚合；
- 标签：`unnest(problems.tags)` 后按标签聚合；
- 汇总：单独聚合查询；
- 活跃班级：学生统计 `class_members status='active'`，教师统计 `classes archived_at IS NULL`；
- 新增索引 `submissions(user_id, submitted_at DESC)`；
- 避免逐日或逐标签查询，全部使用聚合 SQL。

## 8. 数据模型

### 8.1 迁移 `0010_profile.sql`

```sql
ALTER TABLE users
    ADD COLUMN IF NOT EXISTS avatar_path VARCHAR(255),
    ADD COLUMN IF NOT EXISTS pending_email VARCHAR(100),
    ADD COLUMN IF NOT EXISTS status VARCHAR(20) NOT NULL DEFAULT 'active',
    ADD COLUMN IF NOT EXISTS deleted_at TIMESTAMPTZ;

ALTER TABLE users
    ADD CONSTRAINT users_status_check
    CHECK (status IN ('active', 'disabled', 'deleted'));

CREATE UNIQUE INDEX IF NOT EXISTS idx_users_pending_email
    ON users (LOWER(pending_email)) WHERE pending_email IS NOT NULL;

ALTER TABLE auth_tokens DROP CONSTRAINT IF EXISTS auth_tokens_purpose_check;
ALTER TABLE auth_tokens ADD CONSTRAINT auth_tokens_purpose_check
    CHECK (purpose IN ('email_verify', 'email_change', 'password_reset'));

CREATE INDEX IF NOT EXISTS idx_submissions_user_time
    ON submissions (user_id, submitted_at DESC);
```

说明：

- `avatar_path` 只存相对路径。
- `pending_email` 允许为空；部分唯一索引避免两个账号同时占用同一新邮箱。
- `status` 默认 `active`，现有用户无需回填。
- `auth_tokens` 的 purpose 增加 `email_change`。
- `forum_post_favorites` 已有 `(user_id, created_at DESC)` 索引，迁移无需重复创建。

### 8.2 `PublicUser` 扩展

```rust
pub struct PublicUser {
    pub id: i32,
    pub username: String,
    pub email: String,
    pub role: String,
    pub email_verified: bool,
    pub avatar_url: Option<String>,
    pub pending_email: Option<String>,
    pub created_at: DateTime<Utc>,
}
```

- `avatar_url` 由服务层根据 `avatar_path` 拼接 `/uploads/{path}`。
- `pending_email` 只对本人返回。
- `created_at` 用于资料卡展示加入时间。

## 12. 安全与并发

- 用户名/邮箱唯一性依赖数据库唯一约束，不只靠先查后写。
- 邮箱变更在事务内再次校验 pending_email 和邮箱唯一性。
- 密码修改与退出所有设备都递增 `token_version`。
- 注销使用 advisory lock 保护最后一个管理员。
- 注销事务提交后才删除头像文件；删除失败只记录日志，不影响账号状态。
- 认证中间件同时检查 status 和 token_version。
- 上传文件不使用原始文件名，避免路径穿越。
- 静态目录只暴露 `UPLOAD_DIR/uploads`，不暴露整个磁盘路径。
- 学习分析只查询当前 user_id，不接受任意用户参数。
- 收藏列表只查询当前 user_id。
- 所有个人资料接口都要求登录，管理员没有查看他人个人资料的额外权限。

## 15. 风险与取舍

| 风险 | 影响 | 应对 |
|---|---|---|
| 邮箱变更被会话盗用 | 攻击者换绑邮箱后重置密码 | 新邮箱验证 + 旧邮箱提醒；后续可加当前密码确认 |
| 注销破坏教学外键 | 班级/提交历史丢失 | 只匿名化不物理删除；教师先归档班级 |
| 最后一个管理员注销 | 平台失去管理员 | advisory lock + 409 |
| 头像文件占用磁盘 | 单机磁盘增长 | 2MB 限制、单文件覆盖、部署文档说明备份和清理 |
| 静态目录配置错误 | 头像 404 或路径穿越 | 只挂载 uploads 子目录，文件名后端生成 |
| 分析查询慢 | 个人页加载慢 | 聚合 SQL + 用户时间索引；不逐日查询 |
| 收藏列表泄露隐藏帖子 | 内容治理风险 | 只返回本人收藏；隐藏/删除状态前端禁止打开 |
| 主题跟随系统监听泄漏 | 内存/重复监听 | 统一 theme 工具，组件卸载时移除监听 |
| 用户名放开修改 | 冒充和纠纷 | 唯一约束；后续可加改名频率限制 |
| 个人页模块过多 | 首屏信息过载 | 资料卡+概览优先，分析和记录按区块折叠/滚动 |
