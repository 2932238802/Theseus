### 1. 项目链路

```text

→ 网关 / 负载均衡

→ 限流与配额

→ 下游服务或消息队列

```

每一层说明

- 输入输出

- 失败怎么处理

### 2. 鉴权怎么设计，为什么用 API Key 和 JWT

**API Key**

- 用来标识调用方，通常是第三方应用或服务
- 长期有效，适合服务端到服务端调用
- 服务端保存哈希，按前缀或 key id 查找
- 可以绑定权限范围、配额、过期时间和状态
- 泄露后可以禁用或轮换

**JWT**

- 用来标识用户身份和授权信息
- 由服务端签名，客户端携带
- 服务端验签即可，不必每次查会话
- 适合分布式系统和前后端分离
- 通常设置较短有效期，配合刷新令牌

**为什么两种都要**

- API Key 解决「是谁在调用」  
  JWT 解决「以谁的身份调用、能做什么」
- 第三方应用用 API Key 接入  
  用户登录态用 JWT 表达
- 两者的生命周期和泄露后的处理方式不同
- 把应用身份和用户身份分开，权限边界更清楚
- 可以先用 API Key 换取 JWT，减少长期凭证在浏览器中出现

**只用一种可以吗**

- 只有 API Key：缺少用户上下文和细粒度授权
- 只有 JWT：第三方客户端也要签发和轮换密钥，撤销成本高
- 具体要看调用方是应用、用户还是两者都有

### 3. JWT 和 Session 的区别

| 维度 | JWT | Session |
|---|---|---|
| 状态位置 | 客户端保存 token | 服务端保存会话 |
| 服务端查询 | 验签即可，通常不查库 | 每次按 session id 查存储 |
| 扩展性 | 天然适合多实例 | 需要共享存储或粘性会话 |
| 撤销 | 较难，需要黑名单或版本号 | 删除会话即可 |
| 大小 | 较大，放在请求头 | 只传 session id |
| 安全风险 | 存储位置不当会有 XSS 风险 | 需要防 CSRF |
| 跨域 / 移动端 | 较方便 | 依赖 Cookie，跨域更麻烦 |
| 数据新鲜度 | 签发后 claims 可能过期 | 每次可读到最新状态 |

**选择**

- 前后端分离、多服务、移动端：JWT 更常见
- 传统服务端渲染、需要强撤销：Session 更直接
- 实际项目常用混合方案
  短有效期 JWT + 刷新令牌，或 JWT + 服务端会话/黑名单

**JWT 注意点**

- payload 只是 Base64 编码，不是加密，不能放敏感信息
- 必须校验签名、过期时间、签发方和受众
- 不要接受 `alg: none`
- 撤销可以用短过期、版本号、黑名单
- 刷新令牌要单独存储和保护

### 4. 为什么数据库保存哈希后的 API Key

直接保存明文的风险

- 数据库泄露、备份泄露、只读副本泄露后，攻击者可以直接使用所有 key
- 内部人员或日志系统可能看到明文
- 不符合最小暴露原则

正确做法

- 只在创建时返回一次明文
- 数据库保存哈希值，不保存明文
- 查询时对传入的 key 做同样哈希，再按哈希或 key id 查找
- 使用固定时间比较，避免时序攻击
- 日志、监控和错误信息中不要打印完整 key

**用什么哈希**

- API Key 通常是高熵随机串，SHA-256 足够
- 加服务端 pepper 做 HMAC，数据库泄露后攻击者也不能离线穷举
- 如果 key 是人类可猜的短密码，使用 Argon2、bcrypt 等慢哈希
- 不要用可逆加密代替哈希

**怎么支持轮换**

- 一个应用可以同时有多个 key
- 新 key 生效后旧 key 设置过期时间
- 记录 `last_used_at`，清理长期不用的 key
- 支持禁用和删除

### 5. 防止额度超卖

核心是「判断和扣减必须原子」

**方案一：条件更新**

```sql
UPDATE api_keys
SET used = used + 1
WHERE id = $1
  AND used < quota;
```

检查受影响行数

- 1 行：扣减成功
- 0 行：额度不足

这是最直接的方式
单条 SQL 在数据库内是原子的

**方案二：行锁**

```sql
SELECT used, quota
FROM api_keys
WHERE id = $1
FOR UPDATE;
```

判断后再更新
适合扣减逻辑复杂、需要同时操作多张表的场景
缺点是热点行竞争严重

**方案三：乐观锁**

```sql
UPDATE api_keys
SET used = used + 1, version = version + 1
WHERE id = $1 AND version = $2 AND used < quota;
```

失败后重试
适合冲突不高的场景

**方案四：Redis 原子扣减**

用 Lua 脚本把「读取、判断、扣减」放在一次原子操作里
适合高并发限流和配额
再异步落库或定期对账

**方案五：预扣与回滚**

先预扣额度，业务成功后再确认
失败则回滚
需要幂等键避免重复扣减

### 6. `UPDATE` 一定安全吗，有什么缺陷

**单条条件更新本身是原子的**

```sql
UPDATE ... SET used = used + 1 WHERE id = ? AND used < quota;
```

在数据库层面，判断和更新在同一个语句里完成
不会出现两个请求都读到旧值再各自加一的情况

**但它不是完整方案**

- 如果先 `SELECT` 再 `UPDATE`，中间会有竞态
- 事务隔离级别不同，读到的数据可能不一致
- 热点行会被串行化，吞吐下降
- 主从延迟时，读到旧值
- 缓存与数据库不一致
- 扣减成功但业务失败，需要补偿
- 请求重试会重复扣减，需要幂等
- 进程崩溃可能留下中间状态
- 跨服务、跨库时，单条 SQL 无法保证全局一致性

**工程上还要补**

- 幂等键
- 失败回滚或补偿
- 对账任务
- 监控和告警
- 热点分片
- 缓存一致性策略

### 7. 每次鉴权都查数据库，性能怎么保证

- 按 key id 或哈希前缀建立唯一索引，避免全表扫描
- 只查鉴权需要的字段，不要 `SELECT *`
- 使用连接池，控制连接数
- 本地缓存 + Redis 缓存 key 元数据
- 缓存设置较短 TTL，撤销时主动删除
- 对不存在的 key 做负缓存，防止缓存穿透
- JWT 尽量本地验签，不查库
- 读多写少的场景可以用只读副本，但要考虑延迟
- 限流和熔断保护数据库
- 高频 key 可以单独做热点缓存

**缓存失效**

- 禁用或删除 key 时，先更新数据库，再删除缓存
- 多实例通过 Redis 发布订阅或消息广播失效
- 本地缓存 TTL 要短，避免长时间不一致
- 关键操作可以绕过缓存直接查库

### 8. 数据量大时缓存怎么做，知道哪些缓存

**缓存层次**

- 本地缓存：Caffeine、Guava Cache、进程内 LRU
- 分布式缓存：Redis、Memcached
- 数据库缓冲池
- CDN、HTTP 缓存
- 负缓存和布隆过滤器

**常见问题**

- 缓存穿透：查不存在的数据
  用空值缓存、布隆过滤器、参数校验
- 缓存击穿：热点 key 过期
  用互斥锁、逻辑过期、永不过期加异步刷新
- 缓存雪崩：大量 key 同时过期
  TTL 加随机值、多级缓存、限流降级
- 缓存一致性：数据库和缓存更新顺序
  cache-aside、删除缓存、延迟双删、binlog 订阅

**数据量很大**

- 按业务维度分库分表
- Redis Cluster 分片
- 冷热分离，历史数据归档
- 只缓存热点数据
- 大 key 拆分
- 监控命中率、内存、慢查询

### 9. 分布式场景缓存怎么做，怎么更新

**部署**

- Redis Cluster 或 Codis
- 一致性哈希或槽位分片
- 主从复制 + 哨兵/集群故障转移
- 本地缓存作为一级，Redis 作为二级

**更新策略**

- Cache Aside
  读时未命中查库并回填
  写时先更新数据库，再删除缓存
- 延迟双删
  更新数据库后删缓存，延迟再删一次
  降低并发读写导致旧值回填的概率
- 订阅 binlog
  通过 Canal 等组件监听数据库变更，异步删除缓存
- 消息队列广播
  多实例本地缓存通过消息失效
- 版本号
  缓存值带版本，读取时校验
- TTL 兜底
  最终一致性

**一致性取舍**

- 强一致通常要牺牲性能和可用性
- 大多数业务接受短暂不一致
- 金额、库存等关键数据不能只依赖缓存
- 更新缓存还是删除缓存要统一约定

### 10. 场景题：怎么设计联合索引

先问清楚查询模式，不要直接给索引

**设计原则**

- 最左前缀
- 等值条件放前面，范围条件放后面
- 区分度高的列优先
- 覆盖索引减少回表
- 避免冗余索引
- 考虑排序和分组
- 避免在索引列上做函数运算
- 控制索引长度

**例子**

```sql
SELECT id, status, created_at
FROM orders
WHERE tenant_id = ?
  AND status = ?
  AND created_at > ?
ORDER BY created_at DESC
LIMIT 20;
```

可以设计

```sql
CREATE INDEX idx_orders_tenant_status_created
ON orders (tenant_id, status, created_at);
```

- `tenant_id`、`status` 是等值条件
- `created_at` 是范围条件，放在最后
- 排序也能利用索引
- 如果查询只取这三列，可以考虑覆盖索引

**其他情况**

- 只有 `status` 和 `created_at`
  `(status, created_at)`
- 经常按 `tenant_id` 和 `created_at` 查
  `(tenant_id, created_at)`
- 低区分度列放前面通常收益不大
  除非它总是等值查询且能大幅缩小范围

**验证**

- 用 `EXPLAIN` 看执行计划
- 看是否命中索引、扫描行数、是否回表
- 上线后观察慢查询

### 11. 请求失败了怎么办

先分类

- 网络超时、连接失败：可以重试
- 5xx、429：通常可以退避重试
- 4xx：参数或权限问题，重试没有意义
- 业务失败：按业务规则处理，不要盲目重试

**处理手段**

- 设置合理超时
- 指数退避 + 随机抖动
- 限制最大重试次数
- 只重试幂等操作
- 熔断和降级
- 失败落库或进死信队列
- 补偿任务和对账
- 记录 trace id、日志和指标
- 告警

**写请求**

- 先查状态再决定是否重试
- 使用幂等键
- 避免重复扣款、重复下单

### 12. 幂等与重试策略

**幂等**

- 客户端为一次逻辑请求生成唯一幂等键
- 服务端用唯一索引或去重表保存「键 → 处理结果」
- 重复请求直接返回第一次的结果
- 状态机只允许合法跃迁
- Redis `SETNX` 可以做短期防重，但要有 TTL 和兜底
- 数据库唯一约束是最终防线

**重试**

- 只重试可恢复错误
- 指数退避，例如 100ms、200ms、400ms
- 加随机抖动，避免重试风暴
- 设置最大次数和总超时
- 熔断器避免持续打挂下游
- 异步任务失败进入死信队列
- 定时任务补偿
- 重试前先查业务状态

**组合**

```text
至少一次投递 + 幂等消费 = 业务上的恰好一次效果
```

不要承诺基础设施层面的 exactly once
