### 2. Momenta 实习与接口异步化改造

**最大产出**

先给结论，再讲背景和结果

```text
原来是什么流程
→ 瓶颈在哪里
→ 为什么改成异步
→ 你负责哪一部分
→ 改造后指标怎么变化
```

**接口异步化改造**

常见做法

- 接口只做参数校验和任务落库，立即返回任务 ID
- 通过消息队列把耗时任务交给消费者
- 前端轮询或通过推送获取结果
- 任务状态机：`pending → processing → success / failed`
- 失败重试、超时回收、死信队列
- 幂等键防止重复提交和重复消费

**为什么改**

- 同步接口响应时间长，容易超时
- 下游不稳定时会拖垮主流程
- 流量高峰时无法削峰
- 长任务占用连接和线程资源

**需要讲清楚的取舍**

- 异步后如何保证用户能看到最终结果
- 任务失败后怎么补偿
- 如何避免重复执行
- 如何监控积压和失败率

### 3. 消息队列的唯一性与准确性

**唯一性**

- 生产端为每条消息生成业务唯一键
- 消费端用唯一索引或去重表记录已处理消息
- 消费逻辑本身设计成幂等
  例如状态机只允许合法跃迁，或使用 `INSERT ... ON CONFLICT DO NOTHING`
- 消息 ID 只用于去重，不依赖它保证业务唯一
- 生产者重试时复用同一个业务键，不要每次生成新键

**准确性**

- 接受「至少一次」投递，通过消费端幂等实现业务上的「恰好一次」
- 本地事务与消息发送使用事务消息或本地消息表
  避免数据库已提交但消息没发出去
- 消费者处理成功并提交数据库后再 ACK
- 失败进入重试，超过次数进入死信队列
- 对账任务定期比对数据库和消息处理结果
- 关键链路记录消息状态和处理日志

**常见追问**

- 消息重复怎么办
  幂等键 + 唯一约束 + 状态机
- 消息丢失怎么办
  生产确认、持久化、消费 ACK、失败重试、对账
- 消息顺序怎么保证
  同一业务键路由到同一分区，或消费端按版本号处理
- 消息积压怎么办
  扩容消费者、批量消费、降级非核心逻辑、排查慢消费

### 4. Protobuf 数据结构改造与兼容

**改造前后**

讲清楚三件事

- 旧结构有哪些字段，分别被谁使用
- 新结构为什么这样拆或合并
- 迁移期间新旧版本如何共存

**兼容原则**

- 字段编号一旦使用就不要再改
- 删除字段时把编号和名称放入 `reserved`，避免以后复用
- 新增字段用新编号，旧版本会把它当作未知字段忽略
- 不要随意修改字段类型
  尤其是 `int32`、`int64`、`sint32` 之间的 wire type 差异
- 枚举新增值时，旧版本可能收到未知值，要有默认分支
- `optional`、`repeated` 的语义变化要考虑旧数据
- 旧版本反序列化再序列化时，未知字段是否保留取决于实现和配置
- proto3 的默认值不区分「未设置」和「设置为默认值」
  需要区分时使用 `optional` 或 `oneof`

**迁移方式**

- 双写或新旧字段并行一段时间
- 读取时优先新字段，回退旧字段
- 灰度发布，先升级消费者再升级生产者，或反过来按兼容性设计
- 保留旧字段直到确认没有旧客户端
- 用日志和指标观察解析失败和字段缺失

### 6. 用两个栈实现排序

**题目**

给定两个栈 a、b
设计一种移动方法，最终让其中一个栈里的数据有序

**思路**

把 a 当作输入栈，b 当作有序栈

1. 从 a 弹出栈顶元素 `value`
2. 如果 b 的栈顶比 `value` 大，把 b 的栈顶弹回 a
3. 直到 b 为空或 b 的栈顶不大于 `value`
4. 把 `value` 压入 b
5. 重复以上步骤，直到 a 为空
6. 最后把 b 的内容换回 a

这样 b 从栈顶到栈底是递减的
如果要求递增，把比较方向反过来

**复杂度**

时间 `O(n^2)`
空间 `O(n)`，只用了两个栈和一个临时变量

**代码**

```cpp
void sortStack(std::stack<int>& a, std::stack<int>& b) {
    while (!a.empty()) {
        int value = a.top();
        a.pop();

        while (!b.empty() && b.top() > value) {
            a.push(b.top());
            b.pop();
        }

        b.push(value);
    }

    a.swap(b);
}
```

**边界**

- 空栈直接返回
- 只有一个元素时不需要移动
- 有重复元素时用 `>` 或 `>=` 都可以，保证稳定与否要说明
- 调用前 b 应该为空
  如果 b 里已有数据，先明确这些数据是否参与排序

**追问**

- 能不能做到 `O(n log n)`
  两个栈没有随机访问，只能比较和移动
  这个模型下 `O(n^2)` 是常见答案
- 如果允许递归
  可以用系统栈辅助，但本质还是栈操作

### 7. 写一个会产生死锁的程序

**思路**

两个线程、两把互斥锁
加锁顺序相反

```cpp
#include <chrono>
#include <mutex>
#include <thread>

std::mutex m1;
std::mutex m2;

void thread1() {
    std::lock_guard<std::mutex> lock1(m1);
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::lock_guard<std::mutex> lock2(m2);
}

void thread2() {
    std::lock_guard<std::mutex> lock2(m2);
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::lock_guard<std::mutex> lock1(m1);
}

int main() {
    std::thread t1(thread1);
    std::thread t2(thread2);
    t1.join();
    t2.join();
}
```

**死锁的四个条件**

- 互斥
- 持有并等待
- 不可剥夺
- 循环等待

**怎么避免**

- 所有线程按同一顺序加锁
- 使用 `std::scoped_lock` 一次锁住多把锁
  C++17 会避免循环等待
- 使用 `std::lock` 加 `std::unique_lock`
- 设置超时，失败后释放已持有的锁
- 尽量减少锁的持有范围

**追问**

- 这个程序一定会死锁吗
  不保证每次都触发，取决于调度
  加 sleep 是为了提高触发概率
- 怎么检测死锁
  打印线程栈、使用调试器、分析锁顺序
  生产环境更依赖超时和监控

### 8. 生产者-消费者模式

**思路**

- 一个互斥锁保护队列
- 两个条件变量
  一个表示队列非空，一个表示队列未满
- 生产者等待「未满」，消费者等待「非空」
- 使用谓词等待，防止虚假唤醒
- 关闭时唤醒所有线程并退出

**代码**

```cpp
#include <condition_variable>
#include <mutex>
#include <queue>

class BoundedQueue {
public:
    explicit BoundedQueue(size_t capacity) : capacity_(capacity) {}

    void push(int value) {
        std::unique_lock<std::mutex> lock(mutex_);
        not_full_.wait(lock, [this] {
            return queue_.size() < capacity_ || stopped_;
        });
        if (stopped_) return;

        queue_.push(value);
        not_empty_.notify_one();
    }

    bool pop(int& value) {
        std::unique_lock<std::mutex> lock(mutex_);
        not_empty_.wait(lock, [this] {
            return !queue_.empty() || stopped_;
        });
        if (queue_.empty()) return false;

        value = queue_.front();
        queue_.pop();
        not_full_.notify_one();
        return true;
    }

    void stop() {
        std::lock_guard<std::mutex> lock(mutex_);
        stopped_ = true;
        not_empty_.notify_all();
        not_full_.notify_all();
    }

private:
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::condition_variable not_full_;
    std::queue<int> queue_;
    size_t capacity_;
    bool stopped_ = false;
};
```

**边界**

- 队列满时生产者阻塞
- 队列空时消费者阻塞
- 停止后所有等待线程都要被唤醒
- 虚假唤醒必须用谓词判断
- `notify_one` 和 `notify_all` 的选择
  关闭时用 `notify_all`

**追问**

- 为什么条件变量要和互斥锁一起用
  条件判断和等待之间需要原子性，避免丢失唤醒
- 能不能用信号量
  可以，信号量分别表示空位数和数据量
- 多生产者多消费者是否安全
  上面的实现可以，队列操作都在锁内
