# 实时推送（WebSocket v1）设计方案

> 日期：2026-10-29
> 状态：已实现（票据鉴权、进程内广播、站内信推送、匹配成功推送、前端单例连接；`cargo check`、`cargo test` 与 `npm run build` 通过）

## 1. 目标与范围

本版把「轮询发现变化」升级为「服务端主动推送」，但不替换任何权威数据接口：

- 新增一次性连接票据与 `GET /api/ws` 握手；
- 服务端推送 `notification.new`（站内信）与 `match.found`（匹配成局）；
- 前端使用单例连接，收到事件后更新铃铛或立即进入比赛页；
- 现有轮询、心跳与 REST 快照全部保留，作为兜底和重连恢复路径。

不在本版范围：

- 客户端通过 WebSocket 发送 `match.queue` / `match.cancel` / `match.ready`，匹配仍走 `POST|DELETE /api/contests/match`；
- `last_event_id` 断线重放与持久化事件日志，重连后由客户端重新拉取未读数和比赛详情；
- `match.opponent_update`、判题/运行状态流式推送（判题在独立 `judge_worker` 进程，跨进程推送留待后续）；
- Redis Pub/Sub 多实例广播。当前部署是单 API 实例，`RealtimeHub` 以按用户频道实现，后续替换发布端即可。

## 2. 连接与鉴权

浏览器 WebSocket 不能设置 `Authorization` 头，因此先通过普通接口换取票据：

1. `POST /api/ws/ticket`（`Authorization: Bearer <JWT>`）返回 `{ticket, expires_in_seconds}`；
2. 票据为 48 位随机串，60 秒有效且只能消费一次；
3. 客户端连接 `GET /api/ws?ticket=...`（开发环境经 Vite 代理，代理需开启 `ws: true`）；
4. 服务端消费票据后完成升级；票据无效返回 401。

退出登录或票据失效后，客户端重新走第 1 步。JWT 本身不会出现在 URL、代理日志或浏览器历史中。

## 3. 协议

### 3.1 客户端 → 服务端

```json
{"type":"hello"}
{"type":"pong"}
```

- `hello`：连接建立后发送，服务端返回 `ready`；
- `pong`：响应服务端每 30 秒一次的应用层 `ping`；
- 其他类型在 v1 中被忽略。

### 3.2 服务端 → 客户端

统一信封：

```json
{
  "id": 17,
  "type": "notification.new",
  "data": {},
  "server_time": "2026-10-29T12:00:00Z"
}
```

| 类型 | 触发 | `data` |
|---|---|---|
| `ready` | 收到 `hello` | `{user_id, server_time}` |
| `ping` | 每 30 秒 | `{}` |
| `notification.new` | 新增站内信 | 与 `GET /api/notifications` 列表项同构：`id/type/title/body/link/read/created_at/related_type/related_id` |
| `match.found` | 匹配成局 | `{contest_id, starts_at, ends_at, participant_count}` |
| `resync` | 广播积压导致事件被丢弃 | `{}`，客户端应重新拉取快照 |

`id` 为进程内单调递增的事件序号，可用于去重；它不是可重放的事件日志。

### 3.3 保活与重连

- 服务端每 30 秒发送 `ping`，客户端回 `pong`；90 秒没有任何客户端消息则关闭连接；
- 客户端断线后按 1s、2s、4s…最多 30s 指数退避重连，重连成功后重新拉取未读数；
- 浏览器标签页进入后台时连接可能被挂起，恢复后自动重连，不依赖额外保活定时器。

## 4. 服务端实现

### 4.1 广播 Hub

`backend-rust/src/realtime.rs`：

- `RealtimeHub` 保存在 `AppState`，内部为 `Mutex<HashMap<user_id, broadcast::Sender>>`；
- 每个连接持有自己的 `broadcast::Receiver`，只收到本用户事件；
- 无接收者的频道在连接结束时回收；
- 频道容量 64；接收端积压时返回 `Lagged`，服务端发送 `resync`。

### 4.2 站内信推送

通知写入分散在 `notification_service::create`、`send_custom`、班级群发和成绩发布等多条路径，且大多绑定在调用方的数据库事务中。为保证「事务提交后才推送」并覆盖全部路径，服务端使用表尾差量读取：

- 后台任务每 2 秒查询 `notifications WHERE id > cursor ORDER BY id`，单轮最多 200 条；
- 进程启动时游标取当前 `MAX(id)`，不补推历史通知；
- 每条通知按 `user_id` 发布到对应用户频道；
- 离线用户直接丢弃，站内信仍以数据库为准，下次登录或重连时由未读数接口补齐。

### 4.3 匹配成局推送

`try_match` 在调用者的 HTTP 请求内同步创建比赛，其他 2–3 名选手没有同步返回路径。`POST /api/contests/match` 成功后：

- 查询该比赛的全部 `contest_participants.user_id`；
- 向房内所有选手推送 `match.found`；
- 客户端收到后直接进入比赛页并调用 `GET /api/contests/{id}` 拉取题目与时间，不通过 WebSocket 传输题目内容。

结算与取消事件不单独推送：`contest_result`、`contest_cancelled` 等站内信会经 `notification.new` 到达客户端。

## 5. 前端实现

- `src/utils/realtime.ts`：单例连接，首次订阅时自动换取票据并连接；维护订阅表、指数退避重连、`hello/pong` 与 `ready` 处理；
- `src/store/notifications.ts`：订阅 `notification.new`，按 `id` 去重后插入列表并增加未读数；订阅 `ready`，重连后刷新未读数与已加载列表；
- `src/views/ContestsPage.vue`：排队状态下订阅 `match.found`，收到后停止轮询并跳转 `/contests/{id}`；
- `vite.config.ts`：`/api` 代理开启 `ws: true`；
- 60 秒未读数轮询、比赛页 5 秒详情轮询与 10 秒心跳保持不变。

## 6. 与总体设计的差异

`doc/总体设计.md` §6.3 描述的是完整协议。v1 的实现差异如下，接入后续能力时不需要改变连接与鉴权：

| 设计项 | v1 实现 |
|---|---|
| 客户端 `match.queue` / `match.cancel` / `match.ready` | 继续使用 REST 匹配接口 |
| `last_event_id` 重放 | 重连后通过 REST 快照与未读数恢复 |
| `match.started` / `match.finished` / `match.opponent_update` | 未推送；匹配直接以 `running` 创建，结果由站内信通知 |
| Redis Pub/Sub 多实例广播 | 单实例进程内广播，发布端已封装为 `RealtimeHub` |
| 站内信推送来源 | 通知表尾差量轮询（2 秒），而非每个业务事务直接发布 |

## 7. 验收

1. `POST /api/ws/ticket` 需要登录，票据 60 秒有效且只能使用一次；
2. 用票据连接 `/api/ws` 后发送 `hello`，收到 `ready` 与服务器时间；
3. 其他用户创建通知后，本连接在约 2 秒内收到 `notification.new`，铃铛未读数增加；
4. 四名用户匹配成局后，四人均收到 `match.found`；排队中的前端立即进入比赛页；
5. 断开网络后前端自动重连，重连后未读数与服务端一致；
6. 未建立连接或连接中断时，现有轮询仍能正常工作；
7. `cargo check`、`cargo test`、`npm run build` 通过。
