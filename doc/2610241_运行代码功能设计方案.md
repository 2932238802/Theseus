## 0. 摘要

“运行代码”是让用户在题目页执行当前代码并快速看到结果，**不进入正式判题、不计提交次数、不影响通过率**。它与“提交代码”共享语言与题目上下文，但使用独立的执行链路：

```text
Vue 题目页
  -> POST /api/runs
  -> PostgreSQL code_runs (queued)
  -> Redis Stream theseus:judge:runs
  -> Judge Worker (多实例消费组)
  -> gVisor 容器 (编译 + harness 执行)
  -> PostgreSQL 终态 + Redis 临时结果
  -> 前端轮询 GET /api/runs/:id/status
```

本方案采用**函数模式**：用户只实现 `Solution` 类/函数，平台根据题目 `run_config` 自动生成四种语言的 harness，负责参数反序列化、调用用户函数、序列化返回值。公开用例与自定义输入均使用 JSON 参数数组，不使用原始 stdin。

### 0.1 已确认决策

| 维度 | 决策 |

| 结果回传 | `POST /api/runs` 返回 `run_id`，前端轮询 |

| 镜像 | 仓库内 Dockerfile，CI 构建推送，固定 digest |
| 代码组织 | `backend-rust` 新增 `judge_worker` bin target |
| 提交判题 | 本次不迁移，继续使用现有 `tokio::spawn` 桩；运行使用独立队列 |

> 上表是**完整目标态**。P1 只实现其中一小部分，具体范围见 0.3 与 13.1；后续能力按 P2–P7 逐阶段交付，避免一次性修改过多代码。

### 0.2 时间语义修正

已选“标准档”中“编译 10s、单用例 2s、整次 10s”存在冲突。本方案明确为：

- 编译超时：60s（编译内存 1024MB，编译后降回运行限额）
- 单用例执行超时：2s
- 运行阶段合计超时：10s（示例最多 5 条，合计不超过 10s）
- 单次最坏执行约 70s（编译 60s + 运行 10s），排队等待不计入
- 前端轮询上限：60s；超时后提示“排队或执行超时”，任务仍可在历史中查看

- 示例运行与 `public_cases` 比较（P2）。
- JavaScript、C++、Java（P3/P4）。
- 二维数组、`ListNode`、`TreeNode`（P5）。
- 历史列表、详情页、删除接口、个人中心入口（P6）。

- 管理端题目编辑 UI（通过 API/种子配置 `run_config`）。
- 链表环、树的高级变体、原地修改、多返回值、自定义 checker。
- 运行取消、实时流式输出（SSE/WebSocket）。
- 排行榜、收藏、题解。
- 多租户计费。

### 1.3 关键限制

- 运行结果**不作为判题依据**。函数模式 harness 与用户代码同进程，恶意用户可以篡改结果文件；正式判题必须使用独立 supervisor/独立结果通道，后续迁移时另行设计。
- 现有题目没有 `run_config` 时，运行入口禁用并提示“该题暂未配置运行”。
- 现有前端模板会被 `run_config` 生成的模板替换；`code_template` 字段保留用于读取兼容。
- 提交判题仍为桩实现，运行功能上线不代表提交判题可用。

## 2. 用户流程

### 2.1 运行公开示例

```text
题目页
  -> 点击“运行”
  -> 弹窗选择“运行全部示例”
  -> 展示 3 条公开用例（来自 run_config.public_cases）
  -> 点击“运行”
  -> POST /api/runs { problem_id, language, mode:"examples", code }
  -> 返回 run_id
  -> 轮询 /api/runs/:id/status
  -> 完成：显示“通过 2/3”、每条用例的输入/期望/实际/stdout/stderr
```

### 2.2 自定义输入

```text
题目页
  -> 点击“运行”
  -> 弹窗选择“自定义输入”
  -> 输入 JSON 参数数组，例如 [[2,7,11,15], 9]
  -> 前端校验 JSON、参数个数、基础类型
  -> POST /api/runs { problem_id, language, mode:"custom", code, input }
  -> 轮询状态
  -> 完成：显示返回值、stdout、stderr、耗时、内存
```

### 2.3 查看历史

```text
个人中心
  -> “运行记录” Tab
  -> GET /api/runs?page=1&size=20
  -> 查看摘要、打开详情、删除单条
  -> 运行记录不进入提交记录、不影响通过率
```

### 2.4 异常流程

| 场景 | 行为 |
|---|---|
| 未登录 | 401，前端跳转登录 |
| 题目未配置 run_config | 运行按钮禁用，提示“该题暂未配置运行” |
| 题目未审核/不存在 | 404 |
| 语言不支持 | 400 |
| 代码为空/超过 64KB | 400 |
| 自定义输入不是 JSON 数组 | 400，返回具体字段错误 |
| 自定义参数个数/类型不匹配 | 400 |
| 公开用例为空 | 400 |
| 同时已有运行 | 429，提示等待当前运行结束 |
| 每分钟超过 10 次 | 429，`Retry-After` |
| 队列不可用 | 503；DB 记录标记 `internal_error`，释放并发锁 |
| 编译失败 | `compile_error`，返回编译输出 |
| 运行超时/OOM | 对应用例标记 `timeout` / `memory_limit_exceeded` |
| Worker 崩溃 | 消息 Pending，被其他 Worker `XAUTOCLAIM` 回收重试 |
| 前端离开页面 | 停止轮询；任务继续执行并进入历史 |
| 功能开关关闭 | 前端隐藏入口；后端 503 |

```text

│  - 历史/详情/删除     │

    │          │
    │          │ XADD theseus:judge:runs
    │          ▼
    │   ┌──────────────┐
    │   │ Redis Streams │
    │   │ consumer group│
    │   └──────┬───────┘
    │          │ XREADGROUP
    │   ┌──────▼───────┐
    │   │ Judge Worker  │ 多实例
```

### 3.1 组件职责

| 组件 | 职责 |
|---|---|
| Axum API | 鉴权、题目校验、run_config 校验、配额、创建运行、历史查询、删除、功能开关 |
| Redis | Stream 队列、消费组、PEL、死信、状态缓存、限流与并发锁 |
| Judge Worker | 消费任务、状态机、生成代码、启动沙箱、编译/执行、比较结果、写回 |
| PostgreSQL | `problems.run_config`、`code_runs` 永久历史 |
| gVisor/Docker | 一次性沙箱容器，限制网络、文件系统、CPU、内存、PID |
| 镜像仓库 | 四种语言运行时镜像，按 digest 固定 |

### 3.2 部署形态

- API 与 Worker 独立进程，可部署在不同机器。
- Worker 部署在专用评测机，安装 Docker + `runsc`，不与 API/数据库共享宿主机。
- 多 Worker 使用同一 Redis Stream 消费组，水平扩容。
- Worker 不暴露公网端口；仅访问 Redis、PostgreSQL、镜像仓库。
- Worker 需要 Docker socket 权限，等价于宿主机 root，必须是专用机器。
- 每个 Worker 默认并发 2 个容器，可通过 `RUN_WORKER_CONCURRENCY` 配置。

## 4. run_config 与 harness

### 4.1 run_config 结构

题目新增 `run_config JSONB`。示例：

```json
{
  "version": 1,
  "function_name": "twoSum",
  "params": [
    { "name": "nums", "type": "int[]" },
    { "name": "target", "type": "int" }
  ],
  "return_type": "int[]",
  "compare": { "mode": "exact" },
  "public_cases": [
    { "args": [[2, 7, 11, 15], 9], "expected": [0, 1] },
    { "args": [[3, 2, 4], 6], "expected": [1, 2] }
  ]
}
```

TreeNode/ListNode 示例：

```json
{
  "function_name": "reverseList",
  "params": [{ "name": "head", "type": "ListNode" }],
  "return_type": "ListNode",
  "compare": { "mode": "exact" },
  "public_cases": [
    { "args": [[1, 2, 3, 4, 5]], "expected": [5, 4, 3, 2, 1] }
  ]
}
```

```json
{
  "function_name": "invertTree",
  "params": [{ "name": "root", "type": "TreeNode" }],
  "return_type": "TreeNode",
  "compare": { "mode": "exact" },
  "public_cases": [
    { "args": [[4, 2, 7, 1, 3, 6, 9]], "expected": [4, 7, 2, 9, 6, 3, 1] }
  ]
}
```

### 4.2 支持类型

| 类型 | JSON 表示 | 说明 |
|---|---|---|
| `int` | number | 32 位整数 |
| `long` | number | 64 位整数；JS harness 注意精度，超出安全整数时建议改用字符串（首版不支持） |
| `double` | number | 浮点，比较可配容差 |
| `bool` | boolean | |
| `string` | string | UTF-8 |
| `int[]` / `long[]` / `double[]` / `bool[]` / `string[]` | array | 一维数组 |
| `int[][]` / `string[][]` | array of array | 二维数组 |
| `ListNode` | array | 值数组；**不支持环**；返回时序列化为数组 |
| `TreeNode` | array | LeetCode 层序数组，`null` 表示空节点；返回时序列化为层序数组并去掉末尾多余 `null` |

**不支持**：`void`、多返回值、原地修改、自定义 checker、链表环、带随机指针链表、图、并查集等特殊结构。遇到不支持题型时，题目不应配置 `run_config`。

### 4.3 比较规则

| 模式 | 规则 |
|---|---|
| `exact` | 深度相等；数组顺序敏感；`null` 与空数组不相等 |
| `double` | 数值绝对/相对误差 ≤ `epsilon`，默认 `1e-6`；数组中逐元素比较 |
| ListNode | 先序列化为值数组，再按 `exact` 比较 |
| TreeNode | 先序列化为层序数组（去掉末尾 `null`），再按 `exact` 比较 |

比较由 Worker 在 Rust 侧完成；harness 只负责返回 JSON 值，不负责判定。正式判题如需要特殊 checker，另行设计。

### 4.4 代码模板自动生成

`run_config` 是唯一事实来源，保存题目时生成 `code_template`：

- C++：`class Solution { public: <return> <function>(<params>) { } };`
- Java：`class Solution { public <return> <function>(<params>) { } }`（非 public class，便于与生成的 `Main.java` 同文件编译）
- Python：`class Solution:\n    def <function>(self, <params>) -> <return>:\n        pass`
- JavaScript：`var <function> = function(<params>) {\n};`

返回值默认占位：

| 类型 | 占位 |
|---|---|
| int/long | `0` |
| double | `0.0` |
| bool | `false` |
| string | `""` |
| 数组 | `[]` / `new int[]{}` / `new String[]{}` |
| ListNode/TreeNode | `null` / `nullptr` |

保存题目时：

1. 校验 `run_config`。
2. 生成四语言模板。
3. 写入 `code_template` 和 `run_config`。
4. 校验失败返回 400，不落库。

已有题目 `run_config` 为空时，`code_template` 保持现状，但运行入口禁用。

### 4.5 harness 生成

每种语言生成一个入口文件，读取 `/workspace/case.json`（参数数组），调用用户函数，将返回值写入 `/workspace/result.json`。用户 `stdout/stderr` 单独捕获。

#### C++

```text
/workspace/main.cpp =
  #include <bits/stdc++.h>
  #include "json.hpp"
  ListNode/TreeNode 定义
  用户代码（class Solution）
  int main() {
      读取 case.json -> 解析 args
      构造 ListNode/TreeNode
      Solution().<function>(args...)
      序列化返回值 -> result.json
  }
```

编译：

```bash
g++ -O2 -std=c++17 -pipe -o /workspace/program /workspace/main.cpp
```

#### Java

```text
/workspace/Main.java =
  import ...
  ListNode/TreeNode 定义
  class Main { main() { 解析 case.json -> 调用 new Solution().<fn> -> 写 result.json } }
  class Solution { 用户代码 }
```

编译/运行：

```bash
javac -encoding UTF-8 -cp /opt/harness/gson.jar -d /workspace/classes /workspace/Main.java
java -Xmx384m -cp /workspace/classes:/opt/harness/gson.jar Main
```

Java 容器内存 512MB，JVM 堆上限 384MB，预留元空间与本地内存。

#### Python

```text
/workspace/runner.py =
  读取用户代码文件 /workspace/solution.py
  exec 用户代码
  Solution().<fn>(*args)
  序列化 -> result.json
```

运行：`python3 /workspace/runner.py`

#### JavaScript

```text
/workspace/runner.js =
  读取用户代码 /workspace/solution.js
  eval/require 用户代码
  调用 <fn>(...args)
  JSON.stringify -> result.json
```

运行：`node /workspace/runner.js`

#### 结果文件与用户输出

- `result.json`：harness 写入的返回值，仅用于比较/展示“返回值”。
- `stdout`/`stderr`：捕获用户代码输出，单独展示；示例比较不使用 stdout。
- `result.json` 最大 64KB，超出截断并标记。
- 用户代码如果调用 `exit`/`System.exit`/`process.exit`，导致 `result.json` 未生成，标记 `runtime_error`。
- **限制**：用户代码与 harness 同进程，理论上可写 `result.json`。因此运行结果不可作为正式判题依据；正式判题迁移时必须使用独立 supervisor 或不可被用户代码写入的结果通道。

### 4.6 公开用例与展示示例

- `run_config.public_cases` 是运行用数据，最多 5 条。
- `problems.examples` 继续用于题目展示（人类可读格式），不参与执行。
- 管理员录入题目时应保证二者语义一致，但不强制格式一致。
- 前端“运行示例”显示 `public_cases` 的参数与期望返回值；题目描述区仍显示 `examples`。

## 6. 数据模型

### 6.1 `problems.run_config`

```sql
ALTER TABLE problems ADD COLUMN run_config JSONB;
```

- 为空表示该题未配置运行。
- 保存题目时校验并生成 `code_template`。
- 题目更新时同步更新；历史运行使用 `code_runs.run_config_snapshot`，不受后续修改影响。
- 管理员 API `POST/PUT /api/admin/problems` 请求体新增 `run_config` 字段。

### 6.2 `code_runs`

```sql
CREATE TABLE code_runs (
    id BIGSERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    problem_id INTEGER REFERENCES problems(id) ON DELETE SET NULL,
    problem_title VARCHAR(200) NOT NULL,
    language VARCHAR(20) NOT NULL CHECK (language IN ('cpp', 'java', 'python', 'javascript')),
    mode VARCHAR(20) NOT NULL CHECK (mode IN ('examples', 'custom')),
    code TEXT NOT NULL,
    input JSONB,
    run_config_snapshot JSONB NOT NULL,
    status VARCHAR(30) NOT NULL CHECK (status IN (
        'queued', 'compiling', 'running', 'completed',
        'compile_error', 'runtime_error', 'time_limit_exceeded',
        'memory_limit_exceeded', 'internal_error'
    )),
    cases JSONB NOT NULL DEFAULT '[]'::jsonb,
    case_total INTEGER NOT NULL DEFAULT 0,
    case_passed INTEGER NOT NULL DEFAULT 0,
    compile_output TEXT,
    error_message TEXT,
    runtime_ms INTEGER,
    memory_kb INTEGER,
    attempt_count INTEGER NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    started_at TIMESTAMPTZ,
    finished_at TIMESTAMPTZ
);

CREATE INDEX idx_code_runs_user_created ON code_runs(user_id, created_at DESC);
CREATE INDEX idx_code_runs_problem ON code_runs(problem_id);
CREATE INDEX idx_code_runs_status ON code_runs(status);
```

设计说明：

- `problem_id` 使用 `ON DELETE SET NULL`，但保留 `problem_title` 与 `run_config_snapshot`，题目删除后历史仍可读。
- `user_id` 使用 `ON DELETE CASCADE`，账号注销时运行历史一并删除。
- `cases` 存 JSONB，不单独建表；首版无按用例查询需求。
- `code`、`input` 永久保存；用户可单条删除；日志默认不打印完整内容。
- 不写入 `submissions`、不更新 `problems.submit_count`、`accept_count`、`acceptance_rate`、`user_problem_status`。

### 6.3 状态机

```text
queued
  -> compiling
  -> running
  -> completed
  -> compile_error
  -> runtime_error
  -> time_limit_exceeded
  -> memory_limit_exceeded
  -> internal_error
```

- `examples` 模式即使部分用例不匹配，状态仍为 `completed`，`case_passed/case_total` 表示通过数。
- `custom` 模式执行完成即 `completed`，不比较期望值。
- 终态不可被后续重复消息覆盖。

## 7. 队列与 Worker

> **P1 范围**：单 Worker、消费组、`XREADGROUP`/`XACK`、终态幂等。`XAUTOCLAIM`、重试计数、死信、多 Worker 扩容在 P7；P1 不需要它们即可交付。

### 7.1 Redis Streams

| 项 | 值 |
|---|---|
| Stream | `theseus:judge:runs` |
| Consumer Group | `judge-workers` |
| Dead Stream | `theseus:judge:runs:dead` |
| 消息体 | `{ "run_id": 123 }` |
| 读取 | `XREADGROUP GROUP judge-workers <worker-name> COUNT 1 BLOCK 5000 STREAMS theseus:judge:runs >` |
| 确认 | 终态写入 PostgreSQL 成功后 `XACK` |
| Pending 回收 | 每 30s `XAUTOCLAIM`，`min-idle-time` 120s，`COUNT 10` |
| 最大投递 | 3 次；超过后写死信并标记 `internal_error` |
| 并发 | 每 Worker 默认 2 个任务，可配置 |

### 7.2 创建任务流程

1. 校验用户、题目、`run_config`、代码、输入。
2. 检查功能开关。
3. 频率限制：`theseus:run:rate:{user_id}:{minute}` `INCR` + `EXPIRE 120`，超过 10 返回 429。
4. 并发限制：`SET theseus:run:concurrency:{user_id} {run_id} NX EX 600`，失败返回 429。
5. 插入 `code_runs`（`queued`），保存 `run_config_snapshot`。
6. `XADD` 消息。
7. `XADD` 失败：更新记录为 `internal_error`，释放并发锁，返回 503。
8. 返回 `run_id`。

并发锁释放：

- Worker 写终态后，使用 Lua 比较 `run_id` 后 `DEL`，避免误删下一次运行的锁。
- API 创建失败或队列失败时主动释放。
- Worker 崩溃时依赖 600s TTL 自动释放。

### 7.3 Worker 主循环

```text
启动
  -> 连接 Redis/PG，XGROUP CREATE MKSTREAM（幂等）
  -> 注册 SIGTERM
  -> 循环:
       XREADGROUP 拉取任务
       若无任务，继续阻塞读取
       若有任务:
         标记 compiling
         拉取 code_runs 记录
         生成 harness
         创建 gVisor 容器
         编译
         逐用例执行
         比较结果
         写 PostgreSQL 终态 + Redis 状态
         XACK
       并发槽位释放
  -> SIGTERM: 停止拉新任务，等待在途任务完成，XACK 后退出
```

### 7.4 幂等与重试

- Worker 写终态时使用条件更新：

```sql
UPDATE code_runs
SET status = $2, cases = $3, ...
WHERE id = $1 AND status NOT IN (
  'completed', 'compile_error', 'runtime_error',
  'time_limit_exceeded', 'memory_limit_exceeded', 'internal_error'
);
```

- 若影响行数为 0，说明已终态，直接 `XACK`，不重复写。
- 沙箱基础设施错误（Docker 启动失败、Redis 短暂异常）可重试；编译错误/用户运行错误是终态，不重试。
- 重试计数写入 `attempt_count`；超过 3 次进入死信并标记 `internal_error`。
- Worker 启动时创建消费组，忽略 `BUSYGROUP` 错误。
- 消费组名、Stream 名通过配置注入，避免环境间串数据。

### 7.5 Worker 健康检查

- 每 10s 写入 `theseus:run:worker:{name}`，TTL 30s。
- 监控系统检查活跃 worker 数；为 0 时告警。
- Worker 退出时删除心跳键。

## 8. 沙箱与执行

> **P1 范围**：仅 Python 运行器。C++/Java 在 P4，JavaScript 在 P3，二维数组/ListNode/TreeNode 在 P5。下文的通用沙箱策略从 P1 开始生效。

### 8.1 容器策略

每次运行创建一次性容器，执行结束立即删除：

```bash
docker run --rm \
  --runtime=runsc \
  --network=none \
  --read-only \
  --tmpfs /workspace:rw,exec,size=128m \
  --tmpfs /tmp:rw,exec,size=32m \
  --user 65534:65534 \
  --cap-drop=ALL \
  --security-opt=no-new-privileges \
  --pids-limit=64 \
  --memory=256m \
  --memory-swap=256m \
  --cpus=1 \
  --ulimit nofile=64:64 \
  --env HOME=/tmp \
  <image-digest> \
  <entrypoint>
```

Java 使用 `--memory=512m --memory-swap=512m`。

要求：

- `--runtime=runsc` 必须生效；启动后校验容器运行时，失败则任务 `internal_error`。
- 禁止 `--privileged`、宿主网络、宿主 PID、宿主 IPC、设备挂载。
- 不挂载宿主目录；代码和用例通过镜像内临时文件/`docker cp` 写入 `/workspace`。
- 根文件系统只读；`/workspace` 与 `/tmp` 为 tmpfs。
- 非 root 用户 65534。
- 丢弃全部 capabilities，`no-new-privileges`。
- 默认 seccomp；如镜像需要，使用最小白名单。
- 禁止出站网络、DNS、Unix socket 连接。
- 容器名带随机后缀，`finally` 中强制删除。

### 8.2 镜像

仓库内维护：

```text
backend-rust/docker/runners/
├── cpp.Dockerfile      # debian-slim + g++ + nlohmann-json
├── java.Dockerfile     # eclipse-temurin:21-jdk + gson
├── python.Dockerfile   # python:3.12-slim
└── node.Dockerfile     # node:22-slim
```

要求：

- 基础镜像固定版本 + digest。
- 不包含编译器以外的网络工具（curl/wget/nc 等）。
- 非 root 用户运行。
- CI 构建、扫描、推送；配置中使用 digest，不使用 `latest`。
- 镜像更新走单独发布流程，更新后跑完整 harness 回归。

### 8.3 编译与运行命令

| 语言 | 编译 | 运行 |
|---|---|---|
| C++ | `g++ -O2 -std=c++17 -pipe -o /workspace/program /workspace/main.cpp` | `/workspace/program` |
| Java | `javac -encoding UTF-8 -cp /opt/harness/gson.jar -d /workspace/classes /workspace/Main.java` | `java -Xmx384m -cp /workspace/classes:/opt/harness/gson.jar Main` |
| Python | 无 | `python3 /workspace/runner.py` |
| JavaScript | 无 | `node /workspace/runner.js` |

编译输出上限 64KB，超出截断并标记；编译非 0 退出码 → `compile_error`。

### 8.4 用例执行

示例模式：

1. 读取 `run_config.public_cases`（最多 5 条）。
2. 对每条用例写入 `/workspace/case.json`。
3. 启动 harness，执行用户函数。
4. 读取 `/workspace/result.json`，与 `expected` 比较。
5. 记录 `args/expected/actual/stdout/stderr/status/runtime/memory/truncated`。
6. 单条用例不匹配不影响后续用例执行（除非总超时）。

自定义模式：

1. 将用户 `input` 写入 `/workspace/case.json`。
2. 执行一次 harness。
3. 不比较期望值，展示 `actual/stdout/stderr`。

### 8.5 超时、内存与输出

| 项 | 限制 |
|---|---|
| 编译 | 60s（编译阶段内存 1024MB，编译完成后降回运行限额） |
| 单用例 | 2s |
| 运行阶段合计 | 10s |
| 内存 | 256MB（Java 512MB） |
| CPU | 1 核 |
| PID | 64 |
| 单条 stdout | 64KB |
| 单条 stderr | 64KB |
| result.json | 64KB |
| 自定义输入 | 64KB |
| 代码 | 64KB |
| 编译输出 | 64KB |

- 超时由 Worker 监控并强制停止容器；对应状态 `time_limit_exceeded`。
- OOM 由容器退出码/内存事件识别；对应状态 `memory_limit_exceeded`。
- 输出截断保留前 64KB，追加 `\n...[truncated]`，并设置 `truncated=true`。
- 运行阶段合计超时后停止剩余用例，已完成用例结果保留。

### 8.6 结果可信度

- 运行结果仅用于用户自查，不作为判题、排名、通过率依据。
- 用户代码与 harness 同容器同进程，可能篡改 `result.json`；正式判题必须另行设计独立 supervisor。
- Worker 记录镜像 digest、`run_config_snapshot`，便于复现和审计。

## 9. 配额与限流

### 9.1 规则

| 项 | 规则 |
|---|---|
| 运行权限 | 仅登录用户 |
| 并发 | 每用户同时 1 个运行 |
| 频率 | 每用户每分钟 10 次 |
| 每日 | 不设硬上限 |
| 计数范围 | 仅成功创建的任务；参数错误不计入 |
| 超限响应 | 429 + `Retry-After` |

### 9.2 Redis 键

```text
theseus:run:rate:{user_id}:{unix_minute}   INCR, EXPIRE 120
theseus:run:concurrency:{user_id}          run_id, EX 600
theseus:run:status:{run_id}                JSON, EX 3600
```

### 9.3 行为

- 频率限制采用固定分钟窗口，实现简单；后续可换滑动窗口。
- 并发锁 TTL 600s，覆盖正常排队与最坏执行时间（约 20s）；Worker 崩溃后自动释放。队列严重积压时应扩容 Worker，而不是依赖锁过期。
- 释放锁使用 Lua compare-and-delete，避免旧任务删除新任务的锁。
- Redis 不可用时**失败关闭**：返回 503，不绕过限流。
- 管理员同样受限；如需内测白名单，使用独立配置，不在首版实现。
- 无每日上限意味着需要监控单用户日调用量、异常账号和容器资源；后续可增加可配置日上限而不改接口。

## 10. 前端设计

> **P1 范围**：只实现自定义输入弹窗、Python 语言、运行结果展示、轮询。示例运行 Tab 在 P2，运行历史在 P6。

### 10.1 类型与 API

新增：

```text
src/api/runs.ts
src/store/runs.ts
src/types/run.ts
```

类型：

```ts
type RunMode = 'examples' | 'custom'
type RunStatus =
  | 'queued' | 'compiling' | 'running' | 'completed'
  | 'compile_error' | 'runtime_error' | 'time_limit_exceeded'
  | 'memory_limit_exceeded' | 'internal_error'

interface RunConfig {
  version: number
  function_name: string
  params: Array<{ name: string; type: string }>
  return_type: string
  compare: { mode: 'exact' | 'double'; epsilon?: number }
  public_cases: Array<{ args: unknown[]; expected: unknown }>
}

interface RunCase {
  index: number
  args: unknown[]
  expected?: unknown
  actual?: unknown
  stdout: string
  stderr: string
  status: 'passed' | 'failed' | 'runtime_error' | 'timeout' | 'memory_limit_exceeded' | 'internal_error'
  matched?: boolean
  runtime_ms?: number
  memory_kb?: number
  truncated: boolean
}
```

API 函数：

```ts
createRun(payload)
getRunStatus(id)
getRun(id)
listRuns(params)
deleteRun(id)
```

### 10.2 题目详情返回 run_config

`GET /api/problems/:id` 增加：

```json
{
  "run_config": {
    "version": 1,
    "function_name": "twoSum",
    "params": [
      { "name": "nums", "type": "int[]" },
      { "name": "target", "type": "int" }
    ],
    "return_type": "int[]",
    "compare": { "mode": "exact" },
    "public_cases": [...]
  }
}
```

- `public_cases` 是公开数据，可以返回。
- 不返回隐藏 `test_cases`。
- `run_config` 为空时，前端禁用运行按钮。

### 10.3 运行弹窗

一个“运行”按钮，点击打开弹窗：

```text
运行代码
[ 运行全部示例 ] [ 自定义输入 ]

运行全部示例：
  展示 N 条公开用例（只读）
  按钮：运行

自定义输入：
  参数提示：twoSum(nums: int[], target: int)
  textarea：[[2,7,11,15], 9]
  实时 JSON 校验
  按钮：运行
```

要求：

- 主按钮蓝色，取消为次按钮。
- 运行中禁用按钮，显示 `排队中/编译中/运行中`。
- 自定义输入预填第一条公开用例的参数，便于用户修改。
- JSON 解析失败、参数个数不符时前端提示，不发送请求。
- 运行弹窗关闭后，若任务仍在执行，结果仍进入“运行结果”Tab。

### 10.4 结果面板

同一结果面板分两个 Tab：

```text
[ 运行结果 ] [ 提交结果 ]
```

- 运行 Tab 顶部标注“运行不计入提交”。
- 示例模式：显示 `通过 2/3`，逐条展示 `args/expected/actual/stdout/stderr`。
- 自定义模式：显示 `返回值`、`stdout`、`stderr`、耗时、内存。
- `compile_error`：展示编译输出。
- 运行中：显示状态与已通过数（轮询）。
- 轮询间隔 800ms；终态停止；60s 超时提示；组件卸载/切换题目时停止。
- 运行 Tab 与提交 Tab 互不覆盖。

### 10.5 个人中心“运行记录”

- 新增 Tab 或独立区块“运行记录”。
- 列表字段：题目、语言、模式、状态、通过数、时间、操作。
- 详情：代码、输入、逐用例结果。
- 删除：二次确认；仅终态可删；删除后刷新列表。
- 空态与提交记录一致。
- 明确提示“运行记录永久保留，可手动删除；不计入通过率”。

### 10.6 功能开关

- 前端读取 `VITE_RUN_CODE_ENABLED`；为 `false` 时隐藏运行入口和运行记录。
- 后端 `RUN_CODE_ENABLED=false` 时返回 503；前端捕获并提示“运行功能暂未开放”。
- 题目未配置 `run_config` 时，运行按钮禁用并提示“该题暂未配置运行”。

## 11. 安全与数据治理

### 11.1 威胁模型

| 威胁 | 防护 |
|---|---|
| 任意代码执行逃逸 | gVisor、非 root、只读根、cap-drop、seccomp、no-new-privileges |
| 读取宿主文件/密钥 | 不挂载宿主目录；只读根；tmpfs；独立评测机 |
| 访问网络/内网 | `--network=none`；无代理环境变量 |
| 资源耗尽 | CPU/内存/PID/输出/时间限制；容器级隔离 |
| Fork 炸弹 | `--pids-limit=64`、超时强杀 |
| 读取隐藏测试 | 运行只使用 `run_config.public_cases`；不查询 `test_cases` |
| 篡改运行结果 | 运行不计分；正式判题需独立 supervisor（后续） |
| 队列投毒 | Redis 私网、鉴权、TLS；Stream 只接受 `run_id`；Worker 从 DB 读真实任务 |
| 盗用他人运行 | JWT + owner 校验；管理端只读审计 |
| 配额绕过 | 账号级限流；监控多账号；后续设备/IP 风控 |
| 历史数据泄露 | 仅本人可查；日志脱敏；账号注销级联删除 |
| 永久存储增长 | 监控表大小；后续归档/压缩；用户可删除 |

### 11.2 权限

- 创建/轮询/详情/删除：登录用户，且为记录所有者。
- 管理员可读取任意运行详情用于审计，但历史列表默认只查本人；如需全局查询，后续加 `user_id` 参数与审计日志。
- 运行接口不要求 admin。
- 题目必须 `approved` 才允许运行。

### 11.3 数据治理

- `code_runs` 永久保留代码、输入、输出、结果。
- 用户可删除单条；账号删除时 `ON DELETE CASCADE`。
- 题目删除时 `problem_id` 置空，保留 `problem_title` 和 `run_config_snapshot`。
- 日志默认只记录 `run_id/user_id/problem_id/language/mode/status/duration`，不记录完整代码与输入。
- Redis 状态键 TTL 1 小时；PostgreSQL 为唯一长期来源。
- 数据库备份包含运行历史，需按隐私要求管理。

### 11.4 供应链

- 镜像固定 digest，CI 构建并扫描。
- Worker 只拉取受信任镜像仓库。
- 不在镜像中存放数据库/Redis 凭证。
- Docker socket 权限仅授予 Worker 专用机器；该机器不承载 API/数据库。

## 12. 可观测性

### 12.1 日志

Worker 结构化日志字段：

```text
run_id, user_id, problem_id, language, mode, status,
queue_wait_ms, compile_ms, run_ms, total_ms,
memory_kb, image_digest, worker_name, attempt
```

禁止默认打印完整代码、输入、stdout/stderr。

### 12.2 指标

| 指标 | 说明 |
|---|---|
| `run_created_total` | 创建运行数 |
| `run_completed_total{status}` | 终态分布 |
| `run_queue_depth` | `XLEN theseus:judge:runs` |
| `run_pending_entries` | 消费组 PEL 数量 |
| `run_active_workers` | 心跳键数量 |
| `run_queue_wait_ms` | 排队时间 |
| `run_exec_ms` | 编译+执行耗时 |
| `run_sandbox_fail_total` | 容器启动/runsc 失败 |
| `run_timeout_total` | 超时 |
| `run_oom_total` | OOM |
| `run_rate_limited_total` | 429 |
| `run_db_error_total` | DB 写入失败 |

### 12.3 告警

- 队列深度持续 5 分钟超过阈值。
- PEL 持续超过 50 或最老 Pending 超过 5 分钟。
- 活跃 Worker 数为 0。
- 终态失败率（非用户错误）超过 5%。
- Redis/PostgreSQL/Redis Stream 写入失败。
- Docker/runsc 启动失败率异常。

## 13. 任务拆解（分阶段）

> P1 是当前交付范围；P2–P7 只保留阶段任务，不在本次执行。每个任务独立提交、独立验证。

### 13.1 P1 当前交付任务（Python + 自定义输入）

#### P1-01 `run_config` 最小模型与 Python 模板

- 新增 `problems.run_config JSONB` 迁移。
- 实现最小 `RunConfig` 校验：
  - `function_name`、`params`、`return_type`、`compare`。
  - 支持类型：`int`、`long`、`double`、`bool`、`string`、一维数组 `int[]/long[]/double[]/bool[]/string[]`。
  - 不支持二维数组、ListNode、TreeNode；遇到时返回 400。
- 仅生成 Python `code_template`；其余语言模板暂不生成。
- 管理端创建/更新题目支持 `run_config`；题目详情返回 `run_config`。
- 提供 1 道 Python 开发 seed 题目。
- 验证：合法配置生成 Python 模板；非法类型/参数 400；无 `run_config` 时运行入口禁用。

#### P1-02 `code_runs` 表与最小模型

- 新增 `0002_run_code.sql`，按目标态创建 `code_runs`。
- 实现状态枚举、插入、按 ID 查询、终态条件更新。
- P1 不实现历史列表与删除。
- 验证：迁移可重复执行；终态不可被旧消息覆盖；`user_id` 级联、`problem_id` SET NULL。

#### P1-03 Redis Streams 与基础配额

- 新增 Redis 连接与配置：`REDIS_URL`、`RUN_STREAM`、`RUN_CONSUMER_GROUP`、`RUN_CODE_ENABLED`。
- 实现：
  - 1 并发/用户：`SET NX EX 600` + compare-and-delete Lua。
  - 10 次/分钟：固定窗口 `INCR + EXPIRE`。
  - 状态缓存键 `theseus:run:status:{id}`，TTL 1 小时。
- P1 不实现 Pending 自动回收与死信。
- 验证：并发/频率边界；Redis 不可用返回 503；锁释放不误删。

#### P1-04 Judge Worker 骨架（单 Worker）

- 新增 `src/bin/judge_worker.rs`。
- 启动时 `XGROUP CREATE MKSTREAM`，忽略 `BUSYGROUP`。
- `XREADGROUP` 拉取任务、执行、写终态、`XACK`。
- 优雅停机；P1 只部署单 Worker。
- P1 不实现 `XAUTOCLAIM`、重试计数、死信。
- 验证：任务只消费一次；进程重启后可继续消费新增任务。

#### P1-05 gVisor Python Runner

- 新增 Python 运行时镜像 Dockerfile，固定 digest。
- 实现 Docker + `runsc` 容器创建、代码注入、执行、强制清理。
- 安全参数：`--network=none`、`--read-only`、`tmpfs /workspace`、非 root、cap-drop、no-new-privileges、PID/内存/CPU 限制。
- 超时强杀、OOM 识别、输出截断。
- 验证：无网络、非 root、只读根、死循环超时、内存炸弹、容器无残留。

#### P1-06 Python harness（基础类型）

- 生成 `runner.py`：读取 `case.json`，执行用户 `Solution` 方法，写 `result.json`。
- 支持标量 + 一维数组；用户 stdout/stderr 与返回值分离。
- 用户调用 `exit` 或未生成 `result.json` 时标记 `runtime_error`。
- 验证：每种基础类型跑通；参数个数/类型不符时报错；返回空数组/字符串正确。

#### P1-07 运行 API、配额与开关

- 实现：
  - `POST /api/runs`，P1 仅接受 `mode=custom`、`language=python`；使用 202。
  - `GET /api/runs/:id/status`。
  - `GET /api/runs/:id`（当前运行结果详情）。
- 校验题目已审核、`run_config` 存在、参数 JSON 数组合法、代码/输入 ≤64KB。
- 创建任务、XADD 失败回滚、功能开关、owner 校验。
- 不实现 `GET /api/runs` 历史列表与 `DELETE`。
- 验证：400/401/404/429/503 覆盖；运行不写 `submissions`；不影响通过率。

#### P1-08 前端自定义运行

- 新增 `src/api/runs.ts`、`src/store/runs.ts`、`src/types/run.ts`。
- 题目页运行按钮：仅当题目有 `run_config` 且当前语言为 Python 时可用。
- 弹窗只提供“自定义输入”，展示参数名/类型，JSON 校验。

- 队列深度、PEL、活跃 Worker、排队时间。
- 创建成功率、终态分布、编译/运行错误率。
- 沙箱启动失败、runsc 失败、超时、OOM。
- 429 比例、单用户调用量。
- API 5xx、DB/Redis 错误。

### 16.5 回滚

**一级回滚：关闭功能（最快）**

- API `RUN_CODE_ENABLED=false`：新运行返回 503。
- 前端 `VITE_RUN_CODE_ENABLED=false`：隐藏入口。
- Worker 可继续消费已入队任务，或停止拉取并等待在途完成。

**二级回滚：停止 Worker**

- 发送 SIGTERM，等待在途任务完成并 `XACK`。
- 未完成任务保留在 Pending/Stream，后续可恢复。
- 不删除 `code_runs` 与 Redis Stream，避免丢历史。

**三级回滚：代码/镜像**

- API/Worker 回滚到上一版本二进制。
- 镜像回滚到上一 digest。
- 数据库迁移为新增表和列，不回滚删除；保留数据。
- 前端回滚静态产物。

**安全事件回滚**

- 立即关闭开关并停止所有 Worker。
- 隔离评测机，保留容器/日志证据。
- 轮换 Redis/PostgreSQL/镜像仓库凭证。
- 审计 `code_runs` 与 Worker 日志。
- 修复后先内测再全量。

## 17. 风险与限制

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| 函数模式 harness 复杂度 | 高 | 四语言 × 多类型，编译/序列化差异大 | 先做类型矩阵测试；模板自动生成；固定镜像 |
| ListNode/TreeNode 边界 | 高 | 空值、单节点、层序 null、环 | 首版不支持环；补边界测试 |
| 结果可被用户代码篡改 | 中 | 运行不计分 | 文档明确；正式判题另设计 supervisor |
| 永久历史存储增长 | 中 | 代码/输入/输出永久保存 | 监控表大小；后续归档；用户可删除 |
| 无每日上限被滥用 | 中 | 仅 10 次/分钟、1 并发 | 监控异常账号；后续可配置日上限 |
| gVisor 兼容性/性能 | 中 | 启动慢、部分系统调用不支持 | 固定镜像；启动失败告警；不回退 runc |
| Docker socket 权限 | 高 | Worker 机器等价 root | 专用评测机；不部署 API/DB；限制访问 |
| 现有题目无 run_config | 中 | 上线后多数题不可运行 | seed 示例；管理员补配置；前端禁用提示 |
| 提交判题仍是桩 | 高 | 运行可用但提交全部 runtime_error | 明确不在本次范围；后续 CR 迁移 |
| 现有 test_cases 为 stdin 格式 | 中 | 与函数模式不一致 | 正式判题迁移时改为 args JSON；本次不读 |
| Java 内存/类名约定 | 中 | `public class Solution` 文件名校验 | 模板使用非 public class；文档说明；错误提示 |
| JS long 精度 | 低 | 超过安全整数丢精度 | 首版限制；后续用字符串 |
| 用户调用 exit | 低 | 不生成 result.json | 标记 runtime_error；明确提示 |
| 前端轮询泄漏 | 低 | 页面切换后仍请求 | 卸载停止；终态停止；AbortController |
| Redis 不可用 | 中 | 无法限流/排队 | 失败关闭；监控告警 |

### 17.1 P1 明确不做（后续阶段再实现）

- 运行取消。
- 实时流式输出。
- 原地修改/多返回值/自定义 checker。
- 链表环/随机指针/图。
- 管理员全局运行审计 UI。
- 运行计入提交统计。
- 提交判题迁移到 Worker。

### 17.2 后续演进

1. 提交判题迁移到同一 Worker，使用独立 `submit` Stream 与更强 supervisor。
2. 增加运行取消（Redis 标记 + 容器 kill）。
3. 增加 SSE 实时输出。
4. 增加每日上限、设备/IP 风控。
5. 增加链表环、树的高级题型、自定义 checker。
6. 运行历史归档/压缩/导出。
7. 管理端题目 `run_config` 可视化编辑。

### 18.3 状态与前端文案

| 状态 | 前端文案 | 是否终态 |
|---|---|---|
| `queued` | 排队中 | 否 |
| `compiling` | 编译中 | 否 |
| `running` | 运行中 | 否 |
| `completed` | 已完成 | 是 |
| `compile_error` | 编译错误 | 是 |
| `runtime_error` | 运行时错误 | 是 |
| `time_limit_exceeded` | 超出时间限制 | 是 |
| `memory_limit_exceeded` | 超出内存限制 | 是 |
| `internal_error` | 运行服务异常 | 是 |

示例模式完成但未全部通过时，文案为“已完成，通过 X/Y”，不使用“错误”描述用户答案。

### 18.4 待确认的假设

以下为写入方案时采用的默认假设，执行前如有不同意见需调整：

1. 现有题目通过 seed/管理端 API 补 `run_config`，不自动推导。
2. `ListNode` 首版不支持环；输入为值数组。
3. `TreeNode` 使用 LeetCode 层序数组，`null` 表示空节点。
4. JavaScript 的 `long` 使用 Number，超出安全整数范围的题目暂不配置。
5. Java 模板使用非 public `class Solution`，与生成的 `Main` 同文件编译。
6. 每个 Worker 默认并发 2 个容器，可配置。
7. 运行历史永久保留，不自动归档；后续按存储增长再评估。
8. 管理员可读取任意运行详情用于审计，但不在本次提供全局审计 UI。
9. 运行功能默认关闭，先管理员/内测，再全量。
10. 提交判题不迁移，运行时不会改变现有提交行为。
