# 冒烟测试实现（提交评测 P5）

## 0. 结论速览

- 新增一个可重复执行的端到端冒烟脚本：`backend-rust/scripts/smoke_submission.sh`。
- 脚本只操作**真实运行中的 API + judge_worker + PostgreSQL + Redis + Docker 沙箱**，不 mock 任何一层。
- 覆盖：登录、提交、排队/评测轮询、AC / WA / CE / TLE / RE 五种 verdict、首个失败用例、隐藏用例不泄露、计数只加一次、重复投递幂等。
- 使用开发种子题 `1001`（3 条公开 + 3 条隐藏用例），每次运行注册一个一次性哑账号，避免触发同一用户的限流。
- 技术栈：Bash + `curl` + `jq` + `psql` + `redis-cli`；不引入新的测试框架。
- 脚本默认清理测试用户，但**不默认回滚题目计数**；需要时用 `SMOKE_RESTORE_COUNTERS=1` 显式开启（仅当没有并发提交时）。
- 本文只描述实现方案，不包含代码改动。按 §10 的 S1–S4 顺序落地。

---

## 1. 目标与非目标

### 1.1 目标

1. 用一条命令验证「提交 → Redis Stream → Worker → 沙箱 → 终态 → 计数」整条链路。
2. 每条断言失败时能直接定位到 API、数据库或 Redis 的哪一项不符合预期。
3. 可在本地反复执行，不依赖人工点前端，也不依赖管理端 UI。
4. 把最容易回归的问题固化成断言：
   - 终态判定与 verdict 映射；
   - 首个失败用例的裁剪规则；
   - 隐藏用例不出现在用户接口；
   - 重复投递不重复计数；
   - 终态不可被覆盖。

### 1.2 非目标

- **不是**压力测试：串行执行，不测并发吞吐。
- **不是**安全测试：不验证 gVisor 逃逸、恶意代码、资源限制绕过。
- **不是**运行代码（`/api/runs`）的冒烟；后续可另写 `smoke_run.sh`。
- **不覆盖**需要停 Worker 的负向场景（无 Worker 503、排队回收、judging 卡死、死信），这些放在 §9 的手工清单。
- **不覆盖** MLE：容器 OOM 的触发在不同内核/运行时下差异较大，先不纳入自动断言。
- **不替代**单元测试与后续的 Rust 集成测试。

## 2. 被测链路与观测面

### 2.1 组件

```text
smoke_submission.sh
  ├─ HTTP  → API (127.0.0.1:3000)         创建/轮询/详情/权限
  ├─ SQL   → PostgreSQL                   状态、用例、计数、做题状态
  ├─ Redis → Redis Streams                入队、幂等、心跳、锁键
  └─ 间接  → judge_worker → Docker 沙箱    verdict
```

### 2.2 使用的 API

| 用途 | 方法/路径 | 成功状态码 | 认证 |
|---|---|---|---|
| 健康检查 | `GET /api/stats` | 200 | 否 |
| 注册 | `POST /api/auth/register` | 201 | 否 |
| 登录 | `POST /api/auth/login` | 200 | 否 |
| 创建提交 | `POST /api/submissions` | 201 | Bearer |
| 轮询状态 | `GET /api/submissions/{id}/status` | 200 | Bearer |
| 提交详情 | `GET /api/submissions/{id}` | 200 | Bearer |
| 提交列表 | `GET /api/submissions?page=1&size=50` | 200 | Bearer |

所有响应统一为：

```json
{"success": true, "data": {}, "error": null}
```

失败时 HTTP 状态码与 `error` 同时表达错误。

### 2.3 关键数据库字段

`submissions`：

| 字段 | 冒烟用途 |
|---|---|
| `status` | 终态 verdict |
| `test_cases_passed` / `total_test_cases` | 通过数、判题集合大小 |
| `cases` | 已执行 + 跳过用例（JSONB 数组） |
| `compile_output` | 编译错误输出 |
| `run_config_snapshot` / `judge_cases_snapshot` | 快照是否冻结 |
| `attempt_count` | 重复投递后是否变化 |
| `started_at` / `finished_at` | 时间范围 |

`problems`：`submit_count`、`accept_count`、`acceptance_rate`。

`user_problem_status`：`status`（`attempted` / `accepted`）、`last_submission_id`。

### 2.4 Redis 键与消息格式

| Key / Stream | 用途 |
|---|---|
| `SUBMIT_STREAM`（默认 `theseus:judge:submissions`） | 提交队列 |
| `SUBMIT_CONSUMER_GROUP`（默认 `judge-submit-workers`） | 消费组 |
| `theseus:submit:worker:{name}` | Worker 心跳，TTL 30s |
| `theseus:submission:status:{id}` | 状态缓存，TTL 3600s |
| `theseus:submit:concurrency:{user}` | 用户并发锁 |
| `theseus:submit:rate:{user}:{minute}` | 分钟桶限流 |

当前 `queue::enqueue` 是通用实现，消息字段名是 **`run_id`**，提交 id 也放在这个字段里：

```text
XADD theseus:judge:submissions * run_id <submission_id>
```

> 注意：`doc/2610254` 中写的是「消息体只有 submission_id」，与当前实现存在命名差异。冒烟脚本必须按**实际实现**发送 `run_id`。后续如把字段改成通用 `id`，需要同步本脚本与设计文档。

## 3. 环境与前置条件

### 3.1 必须运行的服务

1. PostgreSQL：可连接，已执行 `migrations/0001–0003`（API 启动会自动迁移）。
2. Redis：可连接，且与 API/Worker 使用同一个 `REDIS_URL`（含 db 编号）。
3. API：`backend-rust`，监听 `BIND_ADDRESS`（默认 `127.0.0.1:3000`）。
4. judge_worker：已启动，且 `SUBMIT_JUDGE_ENABLED=true`。
5. Docker：Worker 能创建沙箱；至少构建了 Python 与 C++ 运行镜像。

### 3.2 环境变量

脚本默认从 `backend-rust/.env` 读取 `DATABASE_URL`、`REDIS_URL`、`SUBMIT_STREAM`、`SUBMIT_CONSUMER_GROUP` 等；已存在的同名环境变量优先，便于 CI 覆盖。

| 变量 | 默认值 | 说明 |
|---|---|---|
| `SMOKE_API_BASE` | `http://127.0.0.1:3000` | 不含 `/api` |
| `SMOKE_PROBLEM_ID` | `1001` | 两数之和种子题 |
| `SMOKE_TIMEOUT_SECS` | `240` | 单次提交等待终态上限 |
| `SMOKE_POLL_INTERVAL_MS` | `500` | 状态轮询间隔 |
| `SMOKE_KEEP_DATA` | `0` | `1` 时保留测试用户与提交 |
| `SMOKE_RESTORE_COUNTERS` | `0` | `1` 时回滚 `problems` 计数（需无并发提交） |
| `SMOKE_SKIP_CPP` | `0` | `1` 时跳过 C++ 编译错误用例 |
| `SMOKE_BACKEND_ENV` | `<repo>/backend-rust/.env` | 配置文件路径 |
| `SMOKE_REPORT_DIR` | `<repo>/.dev-logs` | 报告目录 |
| `SMOKE_PASSWORD` | 随机生成 | 仅测试哑账号使用 |

### 3.3 种子数据要求

题 `1001` 必须满足：

- `review_status = 'approved'`；
- `run_config` 非空，`public_cases` 长度 > 0；
- `judge_cases` 为 JSON 数组且长度 > 0（当前种子为 3 + 3 = 6 条）；
- `run_config.function_name = twoSum`，参数为 `int[] nums, int target`，返回 `int[]`。

前置 SQL：

```sql
SELECT review_status,
       run_config IS NOT NULL AS has_run_config,
       COALESCE(jsonb_array_length(run_config->'public_cases'), 0) AS public_cases,
       COALESCE(jsonb_array_length(judge_cases), 0) AS hidden_cases
FROM problems
WHERE id = 1001;
```

不满足时退出码 `2`，提示：

```bash
psql "$DATABASE_URL" -f backend-rust/scripts/seed_dev.sql
```

### 3.4 工具与权限

必需：`bash >= 4.2`、`curl`、`jq`、`psql`、`redis-cli`。

可选：`shellcheck`、`docker`（用于预检镜像；没有 Docker CLI 权限时只告警）。

脚本不调用 `sudo`。Worker/Docker 权限由用户提前准备好。

### 3.5 安全约定

- 只使用脚本随机生成的哑账号；**不得**使用真实账号或真实密码。
- Token、密码、`DATABASE_URL`、`REDIS_URL` 不写入报告，也不在 `set -x` 下运行。
- 报告与日志只记录 `user_id`、`submission_id`、状态、耗时，不记录完整代码与隐藏用例内容。
- 脚本只允许在本地/测试数据库执行；开头打印目标 API 与数据库 host（隐藏密码）供确认。

## 4. 测试用例设计

所有用例串行执行；每个提交都等待终态后再进入下一条，避免撞上「每用户 1 并发」锁。

### 4.1 T0 预检与登录

步骤：

1. 检查工具是否存在；
2. `GET /api/stats` 返回 200；
3. 检查 `theseus:submit:worker:*` 至少有一个心跳；
4. 校验题 1001 的种子数据；
5. 注册哑账号并登录，保存 `user_id` 与 Bearer token；
6. 记录题 1001 的初始 `submit_count` / `accept_count` 与脚本开始时间。

失败处理：

- API 不可达 → 退出码 `3`；
- 无 Worker 心跳 → 退出码 `2`，提示检查 `SUBMIT_JUDGE_ENABLED` 与 Worker 日志；
- 种子数据不完整 → 退出码 `2`。

### 4.2 T1 accepted

代码（Python）：

```python
class Solution:
    def twoSum(self, nums, target):
        seen = {}
        for index, value in enumerate(nums):
            if target - value in seen:
                return [seen[target - value], index]
            seen[value] = index
        return []
```

断言：

- `POST /api/submissions` → 201，`data.status == "pending"`；
- 创建后立刻查 `/status`，`status ∈ {pending, judging}`，`total_test_cases == 6`，且响应中不含 `code` / `cases`；
- 轮询到 `accepted`，耗时 < `SMOKE_TIMEOUT_SECS`；
- 详情 `test_cases_passed == total_test_cases == 6`；
- `failed_case == null`，`compile_output` 为空（null 或空字符串）；
- DB `cases` 长度为 6，所有 `status == "passed"`；
- DB `run_config_snapshot` 与 `judge_cases_snapshot` 均非空；
- `user_problem_status.status == "accepted"`。

### 4.3 T2 wrong_answer 与首错裁剪

代码：

```python
class Solution:
    def twoSum(self, nums, target):
        return []
```

断言：

- 终态 `wrong_answer`；
- `test_cases_passed == 0`，`total_test_cases == 6`；
- `error_message` 包含「第 1 个用例」；
- `failed_case` 非空，且：
  - `index == 0`；
  - `status == "failed"`；
  - `expected` 存在（按设计，WA 才暴露期望）；
  - `args` 等于第一条公开用例参数；
- API 响应中**没有** `cases`、`judge_cases`、`judge_cases_snapshot` 字段；
- DB `cases` 长度为 6：1 条 `failed` + 5 条 `skipped`；
- DB 中没有第二条隐藏用例出现在任何用户可读响应里。

### 4.4 T3 compile_error

代码（C++，故意缺分号）：

```cpp
class Solution {
public:
    vector<int> twoSum(vector<int>& nums, int target) {
        return {}
    }
};
```

前置：`SMOKE_SKIP_CPP=0` 且 C++ 镜像存在；否则标记 `SKIP`，不计入失败，但最终摘要必须显示跳过原因。

断言：

- 终态 `compile_error`；
- `compile_output` 非空，且包含编译器错误关键字（`error`，忽略大小写）；
- `test_cases_passed == 0`，`total_test_cases == 6`；
- `failed_case == null`；
- DB `cases` 为空数组；
- `user_problem_status` 不因本次 CE 降级（若此前已 AC，仍为 `accepted`）。

### 4.5 T4 time_limit_exceeded

代码：

```python
class Solution:
    def twoSum(self, nums, target):
        while True:
            pass
```

断言：

- 终态 `time_limit_exceeded`；
- `error_message` 包含「超过 2 秒」或「总时长」；
- `failed_case` 非空，`status == "timeout"`；
- `failed_case.expected` **不存在**（TLE 不暴露期望）；
- DB `cases` 长度为 6：1 条 `timeout` + 5 条 `skipped`。

### 4.6 T5 runtime_error

代码：

```python
class Solution:
    def twoSum(self, nums, target):
        raise RuntimeError("smoke boom")
```

断言：

- 终态 `runtime_error`；
- `error_message` 非空；
- `failed_case` 非空，`status == "runtime_error"`；
- `failed_case.expected` 不存在；
- `stderr` 或 `error_message` 包含 `boom`（若沙箱未回传 traceback，则只要求非空）。

### 4.7 T6 权限与列表裁剪

前置：再注册一个哑账号 B。

断言：

- B 访问 A 的提交详情 → 403；
- B 访问 A 的提交状态 → 403；
- 访问不存在的提交 id → 404；
- A 的 `GET /api/submissions`：
  - 返回条数 > 0；
  - 每条记录都没有 `code` 字段；
  - 没有 `cases` / `judge_cases` / `judge_cases_snapshot` 字段；
  - `test_cases_passed`、`total_test_cases` 与详情一致。

### 4.8 T7 重复投递幂等

步骤：

1. 取 T1 的 `submission_id`（已 `accepted`）；
2. 记录该提交的 `attempt_count`、题 1001 的计数；
3. 直接向提交流补发一条相同 id 的消息：

```bash
redis-cli -u "$REDIS_URL" XADD "$SUBMIT_STREAM" '*' run_id "$submission_id"
```

4. 等待 3 秒（Worker 读取到终态后会直接 ACK）。

断言：

- 提交 `status` 仍为 `accepted`；
- `attempt_count` 不变；
- `submit_count` / `accept_count` 不变；
- 消费组 Pending 不因这条消息持续增长（可只做趋势检查，不做绝对断言）。

### 4.9 T8 计数与做题状态

在所有 verdict 完成后统一断言：

- `problems.submit_count` 增量 == 用户可见终态提交数（未 SKIP 的 AC + WA + CE + TLE + RE）；
- `problems.accept_count` 增量 == 1（AC 未被 SKIP 时）；
- `acceptance_rate` 与「新 accept / 新 submit」一致（误差 < 0.01）；
- `user_problem_status.status == "accepted"` 且不会被后续 WA / CE / TLE / RE 降级；
- `last_submission_id` 等于本次最后一条提交（RE）的 id；T7 的重复投递不改变它。

并发保护：若脚本期间检测到**其他用户**对题 1001 的新提交，则跳过计数类断言并输出 `SKIP`，避免误报。

## 5. 脚本结构

### 5.1 文件与调用方式

```text
backend-rust/scripts/smoke_submission.sh
```

调用：

```bash
# 仓库根目录
./backend-rust/scripts/smoke_submission.sh

# 常用选项
SMOKE_KEEP_DATA=1 ./backend-rust/scripts/smoke_submission.sh
SMOKE_SKIP_CPP=1 ./backend-rust/scripts/smoke_submission.sh
SMOKE_VERBOSE=1 ./backend-rust/scripts/smoke_submission.sh
```

脚本从自身路径推导仓库根目录，不依赖当前工作目录。

### 5.2 内部辅助函数

| 函数 | 职责 |
|---|---|
| `say/warn/fail` | 统一输出；`fail` 记录失败但继续跑完可继续的用例 |
| `require_cmd` | 预检工具 |
| `load_env` | 读取 `backend-rust/.env`，已有环境变量优先 |
| `api_call` | 封装 curl：返回 body + HTTP 状态码，自动带 Bearer |
| `api_json` | 调 API 并用 `jq` 取字段 |
| `assert_eq` / `assert_ne` / `assert_contains` / `assert_json_has` | 断言与计数 |
| `register_and_login` | 注册 + 登录，输出 `user_id` 与 token |
| `create_submission` | POST 并返回 `submission_id` |
| `wait_terminal` | 轮询 `/status` 直到终态或超时 |
| `fetch_detail` | 拉详情并缓存 JSON |
| `db_scalar` / `db_json` | `psql -At` 查询 |
| `redis_cmd` | `redis-cli -u "$REDIS_URL" --raw` |
| `record_check` | 写入检查结果（供摘要与 JSON 报告） |

### 5.3 主流程伪代码

```text
main:
  parse_args
  load_env
  preflight          # 工具/API/心跳/种子
  register A
  baseline = db_problem_counters(1001)
  token_a = login A

  ac  = run_case("accepted",      python_ac_code)
  wa  = run_case("wrong_answer",  python_wa_code)
  ce  = run_case("compile_error", cpp_ce_code)   # 可 SKIP
  tle = run_case("tle",           python_tle_code)
  re  = run_case("runtime_error", python_re_code)

  check_privacy(ac, wa)
  check_idempotency(ac)
  check_counters(baseline)

  write_report
  cleanup
  exit summary.failed == 0 ? 0 : 1
```

`run_case`：

```text
run_case(expected_status, code, language):
  submit = POST /api/submissions
  assert 201 and pending
  assert status_shape immediately
  final = wait_terminal(submit.id)
  detail = GET /api/submissions/{id}
  assert final.status == expected
  assert detail fields per test
  assert db row per test
  record pass/fail
```

### 5.4 轮询实现约定

- 间隔取 `SMOKE_POLL_INTERVAL_MS`；
- 每次请求都检查 HTTP 状态与 `success`；
- 终态集合固定为：

```text
accepted, wrong_answer, time_limit_exceeded, memory_limit_exceeded,
runtime_error, compile_error, internal_error
```

- 超时后仍继续尝试读取一次详情，便于报告里带出当前状态；
- 遇到 429：读取 `Retry-After`，等待后重试创建（同一用户不应发生，兜底用）；
- 遇到 503：立即失败并提示检查 `SUBMIT_JUDGE_ENABLED` / Worker 心跳。

### 5.5 测试代码存放

建议把五段代码放在脚本内 heredoc 变量中，避免额外文件与路径问题；代码不写入报告。

```bash
read -r -d '' PY_AC <<'PY' || true
class Solution:
    def twoSum(self, nums, target):
        seen = {}
        for index, value in enumerate(nums):
            if target - value in seen:
                return [seen[target - value], index]
            seen[value] = index
        return []
PY
```

JSON 请求体用 `jq -n --arg` 构造，避免手写转义。

## 6. 断言矩阵

| 检查项 | API | DB | Redis |
|---|---|---|---|
| 创建成功 | 201、`status=pending` | `status=pending`、快照非空 | 队列长度 +1（可选） |
| AC | `accepted`、6/6、无 failed_case | `cases` 全 passed、`finished_at` 非空 | 状态缓存为 accepted |
| WA | `wrong_answer`、首错 index=0、expected 存在 | `cases` = 1 failed + 5 skipped | — |
| CE | `compile_error`、compile_output 非空 | `cases=[]` | — |
| TLE | `time_limit_exceeded`、expected 缺失 | `cases` = 1 timeout + 5 skipped | — |
| RE | `runtime_error`、expected 缺失 | `cases` 首条 runtime_error | — |
| 隐私 | 列表无 `code`；他人 403；不存在 404 | — | 状态缓存含 user_id |
| 幂等 | 状态不变 | 计数与 attempt 不变 | 重复消息被 ACK |
| 计数 | — | submit/accept 增量正确 | — |

说明：

- 首错裁剪只允许出现**一个** `failed_case`；
- `expected` 仅在 `wrong_answer` 时出现；
- `accepted` / `compile_error` / `pending` / `judging` 时 `failed_case` 为 null；
- `internal_error` 不参与计数断言。

### 7.2 文件产物

- `SMOKE_REPORT_DIR/smoke-submission-<UTC>.log`：完整输出；
- `SMOKE_REPORT_DIR/smoke-submission-<UTC>.json`：

```json
{
  "started_at": "2026-10-25T06:00:00Z",
  "api_base": "http://127.0.0.1:3000",
  "problem_id": 1001,
  "user_id": 42,
  "git_commit": "e62a735",
  "checks": [
    {"id": "accepted", "status": "passed", "duration_ms": 1420, "submission_id": 123}
  ],
  "summary": {"passed": 10, "failed": 0, "skipped": 1, "duration_ms": 7000}
}
```

禁止写入：token、密码、完整源码、隐藏用例内容、数据库连接串。

### 7.3 退出码

| 码 | 含义 |
|---|---|
| `0` | 全部通过或仅有 `SKIP` |
| `1` | 存在断言失败 |
| `2` | 前置条件不满足（工具/种子/Worker 心跳/开关） |
| `3` | API/数据库/Redis 不可达 |

## 8. 数据清理与隔离

### 8.1 默认行为

- 删除测试用户 A、B：`DELETE FROM users WHERE id IN (...)`；
- 级联删除其 `submissions`、`user_problem_status`；
- **不回滚** `problems.submit_count/accept_count`；
- 输出提示：本地开发库计数会增长，可重跑 `clean_dev.sql` 或使用 `SMOKE_RESTORE_COUNTERS=1`。

### 8.2 可选计数回滚

`SMOKE_RESTORE_COUNTERS=1` 时：

1. 检查脚本开始后是否存在其他用户对题 1001 的提交；
2. 不存在时，按基线恢复 `submit_count`、`accept_count`、`acceptance_rate`；
3. 存在则跳过并告警，避免把真实提交的计数抹掉。

### 8.3 保留数据

`SMOKE_KEEP_DATA=1` 时不删除用户，打印测试账号、提交 id 与清理 SQL，便于排障。

## 9. 手工负向场景（不纳入脚本）

以下场景需要停 Worker 或改配置，放在发布前手工执行：

### 9.1 无存活 Worker → 503

1. 停 Worker；
2. 等心跳 TTL（30s）过期；
3. `POST /api/submissions` → 503；
4. 确认没有新增 `submissions` 行，也没有占用限流/并发锁。

### 9.2 排队超时回收

1. 让 Worker 停止消费但保留最近一次心跳：`kill -STOP <judge_worker_pid>`，并在 30 秒心跳 TTL 内提交；
2. 提交成功后不要恢复 Worker，等待 `SUBMIT_QUEUE_TIMEOUT_SECS`（默认 90s）；
3. 断言 `status=internal_error`、`error_message` 包含「排队超时」、并发锁 key 已删除。

也可直接在隔离库插入一条带合法快照的 `pending` 提交并等待回收，避免与真实 Worker 抢时序。

### 9.3 judging 卡死回收

1. 在隔离环境让 Worker 领取后崩溃；
2. 等待 `SUBMIT_STALE_TIMEOUT_SECS`（默认 300s）；
3. 断言 `internal_error` 且锁释放。

### 9.4 死信

1. 构造重复投递超过 `SUBMIT_MAX_DELIVERIES`；
2. 断言 `SUBMIT_DEAD_STREAM` 有记录、提交为 `internal_error`。

### 9.5 MLE

用 Java/Python 主动分配大内存，确认 `memory_limit_exceeded`；不同环境差异大，仅人工验证。

## 11. 验收标准

- [ ] 按 §3 准备环境后，脚本单次运行退出码为 `0`，耗时 < 60 秒；
