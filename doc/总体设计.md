## 0. 一页结论

| 项目 | 结论 |
|---|---|
| 产品定位 | 面向校内教学与训练的在线算法服务平台：刷题、判题、组织作业、4 人匹配、段位、论坛、通知与防作弊 |
| 核心用户 | 学生、教师、管理员三个**互斥**角色，不叠加、不继承；题库练习、论坛、通知对所有登录角色开放 |
| 架构选择 | 前端 Vue 3 SPA + 后端 Axum 模块化单体 + PostgreSQL + Redis Streams + 独立 Worker + Docker/gVisor 沙箱 |
| 实时能力 | 通知与匹配成局使用 WebSocket 推送；判题、邮件、防作弊扫描走异步队列 |
| 数据原则 | PostgreSQL 是唯一事实来源；Redis 只承载队列、缓存、限流、匹配池和实时广播 |
| 防作弊 | 作为一等子系统设计：预防、检测、证据、人工复核、申诉、审计，不以单一模型自动定罪 |
| 交付策略 | 先打通「教学闭环」，再做 4 人匹配与段位，最后做 AI 辅助；每阶段都可独立演示 |
| 当前状态 | 刷题、提交判题、隐藏用例、论坛/通知、排行榜、三角色互斥、组织/作业/批改/邀请、作业策略、个人中心（资料/邮箱/密码/注销/头像/学习分析/收藏/我的作业）、首页学习工作台、教师出题与管理员题目审核、邮箱验证与密码找回、4 人匹配与段位分、限时赛事报名与赛事闭环、竞赛断线重连、实时推送（通知与匹配成局）、疑似粘贴人工复核与信誉分处罚已完成；防作弊相似度、赛季未开始 |
| 最大风险 | 范围过大、4 人匹配冷启动、防作弊误判与隐私边界、邮件可达性、单机运维 |

**一句话总结：** 保持「模块化单体 + 异步 Worker」的简单形态，学生只学、教师只教、管理员只管平台，以教学作业闭环为第一优先级，把匹配、论坛、防作弊做成可独立演进的能力，而不是一开始就拆微服务。

### 1.2 目标用户与场景

**学生**

- 浏览题库、按标签/难度筛选、搜索；
- 在线写代码、运行示例、提交判题；
- 查看通过数、失败用例、历史提交、收藏与学习进度；
- 加入组织、完成作业、查看教师评分与评语；
- 参加 4 人匹配，获得段位与赛季排名；教师和管理员不进入匹配池；
- 在校园墙讨论题目、引用题目、接收回复与系统通知。

**教师**

- 管理自己的组织与学生名单，不加入其他组织、不提交组织作业；
- 从题库组合作业，设置截止时间、重交次数、迟交策略；
- 查看自己组织的完成度、题目通过率、常见错误；
- 批改作业、写评语、发布成绩、处理申诉；
- 创建题目并提交管理员审核，不参与审核自己的题目；
- 使用题库练习、论坛和通知；这些是平台公共能力，不代表教师拥有学生身份。

**管理员**

- 审核教师创建的题目与隐藏用例，管理题库；
- 管理用户与角色；不创建组织、不导入学生、不分配教师；
- 管理论坛内容、举报、禁言；
- 配置匹配参数、赛季、题目池；
- 发布系统广播、维护公告；
- 查看判题队列、Worker 心跳、死信、异常率；
- 查看审计日志，处理数据导出/删除请求；
- 不进入组织、作业、提交、成绩数据；如果确实需要授课，必须先转为教师角色。

### 1.3 成功标准

毕业设计阶段建议用可量化的指标验收：

- 教学闭环：教师创建组织 → 布置作业 → 学生提交 → 自动判题 → 教师批改 → 学生收到通知，全流程可演示；
- 判题：常规提交 P95 在 15 秒内出终态；隐藏用例零泄露；重复投递不重复计数；
- 匹配：4 人房间可稳定创建、开始、结算；断线可重连；评分与段位可解释；
- 防作弊：相似代码与异常行为可生成待复核报告，管理员可确认/驳回，学生可申诉；
- 论坛：发帖、引用题目、评论、举报、审核闭环；
- 通知：站内信即时可见，邮件可送达（开发环境可用 MailHog）；
- 运维：单机部署可重启恢复；数据库每日备份；关键队列有监控；
- 体验：桌面端完整可用，移动端可完成刷题与查看作业。

### 1.4 范围与非目标

**本期范围**

- 校内单租户部署（一个学校/一个部署实例）；
- Web 端优先，响应式适配手机浏览器；
- 函数式判题（沿用现有 `run_config`），支持 C++/Java/Python/JavaScript；
- 4 人匹配；正式 ACM 赛制比赛暂不做；
- 站内论坛；不做即时私聊；
- 防作弊以代码相似度 + 行为信号 + 人工复核为主；
- 邮件通知；不做短信/微信推送。

**明确不做**

- 多学校 SaaS 与跨校排行榜；
- 支付、课程购买、证书；
- 摄像头监考、屏幕录制、人脸识别；
- AI 自动评分或自动判定作弊；
- 移动原生 App；
- 任意语言插件市场；
- 微服务拆分与多云多活。

### 1.5 设计原则

1. **简单但完整**：一个模块化单体 + 少量 Worker，优先保证闭环，不为未来过度设计。
2. **PostgreSQL 是事实来源**：Redis 中的数据必须可从数据库重建；队列消息丢失可恢复。
3. **重任务异步化**：判题、邮件、相似度扫描、统计聚合不阻塞 API。
4. **最小权限与资源归属**：教师只能看自己的组织；管理员只看平台数据、不进入教学数据；学生只能看自己的提交和成绩。
5. **防作弊重证据**：信号只用于生成报告，处罚必须经过人工复核与申诉。
6. **默认可运维**：每个异步链路都有重试、死信、幂等、监控和手工恢复手段。
7. **渐进式演进**：先单体，后按瓶颈拆 Worker；先 REST，实时需求再上 WebSocket。

## 2. 角色、权限与数据边界

### 2.1 角色模型

采用三个**互斥**角色，每个账号只能有一个角色：

| 角色 | 定位 | 直接能力 |
|---|---|---|
| `student` | 学习者 | 题库练习、4 人匹配、加入组织、提交作业、查看自己的成绩、论坛、通知 |
| `teacher` | 授课者 | 题库练习、创建和管理自己的组织、布置作业、批改、发布成绩、创建题目并提交审核、论坛、通知 |
| `admin` | 平台管理者 | 题库练习、用户/角色管理、题目审核、论坛管理、匹配配置、广播、审计、系统配置、论坛发帖/评论、通知 |

互斥规则：

- 角色之间**没有继承、没有兼任**：`student` 不具备教师能力，`teacher` 不具备学生组织身份，`admin` 不参与教学。
- 题库练习、运行、论坛、通知是所有登录角色可用的平台公共功能，不代表学生身份；只有带 `assignment_id` 的组织作业提交才要求 `student`。
- 教师不能加入组织、不能提交组织作业；管理员不能创建组织、批改、查看组织/作业/提交/成绩数据。
- 4 人匹配和段位是学生活动，只有 `student` 可以排队；教师和管理员可以使用题库练习，但不进入匹配池。
- 一个账号不能同时是教师和学生。若某人既要授课又要学习，本轮使用两个独立账号；后续可讨论“关联账号”，不做单账号双角色。
- 管理员如果确实需要授课，必须先转为教师；转成教师后不再拥有管理员权限。

**数据库只保留 `users.role` 单值**，不建 `roles` / `user_roles`，不做权限并集：

```sql
role VARCHAR(20) NOT NULL DEFAULT 'student'
CHECK (role IN ('student', 'teacher', 'admin'))
```

迁移时把现有 `user` 回填为 `student`，现有 `admin` 保持 `admin`；新增 `role_changed_at` 和 `idx_users_role`。完整 SQL 与清理条件见 `doc/2610259_班级与作业设计方案.md` 的 §3.2、§5.2。

**认证与授权：**

- JWT 只用于确认用户 id；`AuthUser.role` 每次请求从 `users.role` 读取，不信任 token 中的旧角色。
- 角色变更立即生效；前端刷新 `/me` 即可更新导航，不要求重新登录。
- 授权顺序：先判断角色是否具备该能力，再判断资源归属。角色不具备能力返回 403；资源对调用者不可见返回 404，避免泄露组织/作业是否存在。
- 管理员不是教学超级用户：`/api/classes/*`、`/api/assignments/*`、教学提交/成绩接口对管理员一律 403。

**角色变更：**

- 只有 `admin` 可以修改他人角色；不能修改自己的角色。
- `student → teacher`：必须没有 `active` 组织成员关系，否则返回 409。
- `teacher → student/admin`：必须没有未归档的自有组织；可带 `archive_owned_classes=true`，在同一事务内归档后变更。
- `admin → teacher/student`：同样不能保留未归档组织或 active 成员关系。
- 最后一个管理员不能降级；所有角色变更在事务内加 advisory lock，写 `role_changed_at`，并记录操作者、目标、前后角色。
- 归档组织可以保留被降级的历史 owner，但组织冻结，不再有管理入口；这是唯一允许“组织 owner 不是教师”的例外，且只发生在归档组织。

### 2.2 权限矩阵

| 能力 | `student` | `teacher` | `admin` |
|---|---:|---:|---:|
| 题库浏览、运行、练习提交 | ✓ | ✓ | ✓ |
| 论坛发帖/评论/举报 | ✓ | ✓ | ✓ |
| 站内通知 | ✓ | ✓ | ✓ |
| 4 人匹配、段位、匹配榜 | ✓ | — | — |
| 加入组织、提交作业、查看自己的成绩 | ✓ | — | — |
| 创建/管理自己的组织与成员 | — | ✓ | — |
| 创建/发布/归档作业 | — | ✓（自己的组织） | — |
| 批改、发布成绩、查看自己组织统计 | — | ✓（自己的组织） | — |
| 创建题目并提交审核 | — | ✓ | — |
| 审核题目/隐藏用例 | — | — | ✓ |
| 导入/维护官方题库 | — | — | ✓ |
| 查看全局统计 | — | — | ✓ |
| 论坛审核/禁言 | — | — | ✓ |
| 用户/角色管理 | — | — | ✓ |
| 匹配/赛季配置 | — | — | ✓ |
| 系统广播 | — | — | ✓ |
| 系统配置/审计导出 | — | — | ✓（敏感操作二次确认） |

说明：

- 表格列的是每个角色的**直接能力**，不存在 `student ⊂ teacher ⊂ admin` 的继承关系。
- 管理员拥有平台管理能力，但不自动拥有教学能力；不能因为 `role = admin` 就创建组织、批改或查看成绩。
- 教师只能操作自己的组织；其他教师访问返回 404。学生只能操作自己的数据。
- 题库练习、论坛、通知是平台公共功能，不是“学生身份”的一部分。

实现上建议保留显式的「角色 → 权限码」映射，但每个角色只拿到自己的权限码，不做继承：

```text
problem.create      teacher
problem.review      admin
problem.import      admin
class.manage        teacher（仅自己的组织）
assignment.manage   teacher（仅自己的组织）
assignment.grade    teacher（仅自己的组织）
match.participate   student
match.configure     admin
forum.moderate      admin
broadcast.send      admin
user.manage         admin
system.manage       admin
system.audit        admin
```

资源级校验（是否组织 owner、是否作业所属学生、是否提交者本人）在权限码之后执行。

### 2.3 资源归属与数据范围

- 组织：`classes.owner_id` 必须指向 `teacher`；active 组织不得由非教师拥有。归档组织允许保留历史 owner，但已冻结。
- 组织成员：`class_members` 只包含 `student`，不存教师、不存管理员，也不设 `member_role`；第一版不做协同教师/助教。
- 作业：归属于组织，`created_by` 固定为组织 owner 教师；管理员和其他教师不能代建。
- 题目：`created_by` 记录创建者；教师只能编辑自己创建的未审核/被驳回题目；管理员审核并维护官方题库；不允许审核自己创建的题目。
- 提交：所有角色可以查看自己的练习提交；学生查看自己的作业提交；组织 owner 教师查看自己组织作业范围内的提交；管理员不能查看其他人的提交（包括练习提交），非 owner 教师/非成员学生返回 404。
- 匹配：只有学生进入匹配池；教师和管理员不能参加排位匹配。
- 论坛：所有登录角色可发帖/评论/举报；作者可编辑/删除自己的内容；管理员可隐藏、删除、禁言、置顶。
- 审计：管理员可查平台管理操作；教师只能查与自己组织相关的操作；管理员不能借审计接口读取教学数据；所有敏感操作留痕。
- 角色变更：学生升教师前必须退出所有组织；教师降级前必须没有未归档的自有组织，或在同一事务内归档。历史提交和成绩保留，但降级后不能再以学生视图访问。

### 2.4 账号生命周期

```text
注册（校园邮箱） → 邮箱验证 → 完善学号/姓名 → 正常
        ↓ 未验证                  ↓ 违规/离校
      限制功能                 禁用/归档
```

- 校园邮箱域名白名单可配置；开发环境允许任意邮箱；
- 学号、真实姓名可选但建议采集，用于作业与成绩；
- 毕业/离校：归档账号，保留历史提交与成绩，禁止登录；
- 角色变更：注册默认 `student`，只有管理员可以调整。学生升教师前必须退出所有组织；教师降级前必须没有未归档的自有组织，或在同一事务内归档。最后一个管理员不能降级，角色变更立即生效；
- 删除账号：先匿名化/保留统计，再按学校数据政策处理；不直接物理删除教学记录。

### 3.2 为什么是模块化单体

- 毕业设计团队规模小，拆微服务会带来部署、调试、事务、链路追踪成本；
- 当前判题 Worker 已经与 API 分离，天然形成「同步 API + 异步执行」边界；
- 模块化单体可以通过 crate/module 边界保持清晰，后续按瓶颈拆出匹配服务或通知服务；
- 匹配、通知、防作弊都可以先以 Worker/后台任务实现，不需要独立服务。

### 3.5 同步与异步边界

| 场景 | 方式 | 原因 |
|---|---|---|
| 登录、题库、提交创建 | 同步 REST | 需要立即反馈 |
| 判题状态轮询 | 同步 REST + Redis 缓存 | 现有实现，简单可靠 |
| 匹配状态/房间事件 | WebSocket | 低延迟、多端同步 |
| 判题执行 | Redis Stream | 耗时、需重试/死信 |
| 邮件发送 | 数据库 outbox + Worker | 避免 SMTP 阻塞请求、可重试 |
| 站内信扇出 | 异步任务 | 广播可能涉及大量用户 |
| 相似度扫描 | 异步任务 | CPU 密集、可延后 |
| 截止提醒 | Scheduler | 定时任务 |
| 排行榜刷新 | 定时聚合/物化视图 | 避免实时重查询 |

### 3.6 关键状态机

**题目审核**

```text
draft → pending → approved → archived
          │  ↑
          └→ rejected → draft
```

- 教师创建题目默认为 `pending`，管理员导入的官方题目可直接发布并留审计；学生不能创建题目；
- 管理员审核通过后进入题库；
- 已通过题目的修改建议走「新版本/重新审核」，避免线上用例被悄悄替换；
- 删除优先归档，硬删除仅限无提交或管理员显式确认。

**作业**

```text
draft → scheduled → active → closed → archived
```

- `scheduled` 到开始时间自动转 `active`；
- `closed` 后默认禁止提交，可配置迟交；
- `archived` 只读，保留成绩与统计。

**匹配**

```text
queued → matched → ready → running → finished
   │        │         │        │
   └────────┴─────────┴────────┴→ cancelled
```

- 匹配成功后进入房间，倒计时结束自动开始；
- 全员断线超时则取消；单人断线有重连宽限期；
- 结算后写评分历史与段位。

**防作弊报告**

```text
open → reviewing → confirmed → appealed → upheld
  │        │            │           └→ overturned
  │        └→ dismissed └→ closed
  └→ auto_closed（低风险/证据不足）
```

**提交**

沿用现有：

```text
pending → judging → accepted / wrong_answer / time_limit_exceeded /
                     memory_limit_exceeded / runtime_error / compile_error /
                     internal_error
```

## 4. 核心业务设计

### 4.1 身份与账号

**功能**

- 校园邮箱注册 + 邮箱验证；
- 登录/登出、刷新令牌、密码找回；
- 学号/姓名/组织信息；
- 管理员禁用/归档账号；
- 管理员重置密码、强制下线；
- 管理员可选开启 2FA（TOTP）。

**设计要点**

- 密码使用 Argon2（当前已使用）；
- 访问令牌短有效期（如 15–30 分钟），刷新令牌 7–14 天，刷新令牌只存哈希；
- 邮箱验证 token 与重置 token 一次性、带过期时间、只存哈希；
- 登录/注册/找回密码按 IP + 账号限流，失败次数过多临时锁定；
- 校园邮箱域名白名单可配置；开发环境允许 `@example.test`；
- JWT 只放用户 id 和会话信息；角色每次请求从数据库读取，不信任 token 中的旧角色，避免角色变更后旧 token 长期有效；
- 管理员 2FA 建议在正式部署时启用，毕业演示可先留接口。

> **个人界面完善（2026-10-27）：** 个人页仪表盘、用户名/邮箱/密码自助修改、邮箱变更验证、退出所有设备、注销匿名化、头像上传、近 30 天学习分析、论坛收藏页和跟随系统主题已按 `doc/2610272_个人界面的完善.md` 完成。头像文件默认写入 `UPLOAD_DIR=./uploads`，生产环境需使用持久化目录。

### 4.2 题库与题目生命周期

**题目来源**

- 教师创建并提交审核；
- 管理员导入/维护官方题目；
- 从现有题库复制并修改（教师复制后生成待审版本）；
- 批量导入 JSON/CSV（仅管理员）。

**题目字段建议**

在现有 `problems` 基础上新增：

- `visibility`：`public` / `class` / `private`；
- `problem_type`：`function` / `stdio`（本期以 function 为主，stdio 作为扩展）；
- `owner_id`：创建者（现有 `created_by` 可复用）；
- `review_status`：现有 `pending/approved/rejected`，增加 `archived`；
- `reviewed_by`、`reviewed_at`、`review_note`；
- `version`：题目内容/用例版本；
- `archived_at`；
- `source`：`official` / `teacher` / `imported`；
- `difficulty`、`tags`、`time_limit`、`memory_limit` 沿用。

**审核规则**

- 教师创建的题目默认 `pending`，管理员统一审核；
- 管理员导入的官方题目可直接发布，但必须记录导入人、`reviewed_at` 和审计日志；这是系统导入，不进入教师投稿审核流；
- 教师投稿不允许审核自己创建的题目（四眼原则）；如确需紧急处理，由另一名管理员操作并审计；
- 审核必须能查看完整题面、公开用例、隐藏用例、运行配置；
- 拒绝必须填写理由，通知创建者；
- 已通过题目的修改：默认生成待审版本，审核通过后替换；紧急修正可由管理员直接改并记录审计。

**用例与判题配置**

- 继续使用 `run_config`（函数名、参数、返回类型、比较方式、公开用例）与 `judge_cases`（隐藏用例）；
- 用例上限、总字节数、参数个数、类型校验沿用现有实现；
- 隐藏用例只对题目作者、管理员审核者和判题 Worker 可见；其他教师不可见；
- 支持「按学生随机参数」的扩展：同一逻辑用例生成不同输入，降低硬编码/抄袭（P2）；
- 未来支持 special judge / 浮点误差 / 多答案。

**版本与重判**

- 题目修改后，旧提交保留当时快照；
- 管理员可发起重判批次（例如修复用例错误），重判结果写新记录或标记版本，不覆盖历史；
- 重判必须审计，避免成绩争议。

**删除策略**

- 默认归档，保留提交与成绩；
- 硬删除仅用于无提交的草稿，或管理员显式确认并先导出；
- 当前数据库对 `submissions.problem_id` 使用级联删除；建议后续改为「归档 + 可选硬删除」，避免误删教学记录。

### 4.3 判题与代码运行

复用现有链路，补齐教学场景：

```text
POST /api/submissions
  → 校验题目/开关/Worker 心跳/限流/并发锁
  → 写入 submissions（冻结 run_config + judge_cases 快照）
  → XADD 提交队列
  → judge_worker 消费/认领
  → 沙箱编译 + 逐用例执行
  → 终态 + 计数 + 做题状态 + 状态缓存
```

需要补充：

- `submissions.assignment_id`、`submissions.match_id` 可空外键，用于作业/匹配归属；
- 作业/匹配提交的配额与普通练习分开计算；
- 重判批次与 `rejudge_of`；
- 判题结果对教师可见的范围控制；
- 判题队列健康检查：XLEN、PEL、最老 Pending、Worker 心跳、死信数；
- 语言版本固定并展示（避免“本地能过、线上不过”）；
- 编译/运行超时、输出截断 64KB、内存限制的提示文案统一；
- 资源公平：运行与提交共享沙箱信号量，匹配/作业高峰期限流。

### 4.4 练习与学习进度

练习是平台公共能力，`student` / `teacher` / `admin` 都可以做题、运行和提交不带 `assignment_id` 的练习记录；练习提交不计入任何组织成绩，也不代表学生身份。

- 题目状态：未开始 / 尝试过 / 已通过（现有 `user_problem_status`）；
- 收藏（现有 `favorites` 表，前端可接入）；
- 答题草稿：按「用户 + 题目 + 语言」保存到 `problem_drafts`，编辑器停止输入约 1 秒后同步；本机草稿即时写入 localStorage，进入题目时本机有编辑则保留本机内容，本机为空才采用云端草稿；代码恢复为模板时删除云端草稿；
- 提交历史、代码详情、失败用例；
- 学习统计：通过题数、按难度/标签分布、连续打卡（可选）；
- 每日一题/推荐（P2）：按标签掌握度推荐，不做复杂推荐系统；
- 错题本（P2）：记录失败原因，支持重做；
- 隐私：默认只本人可见，排行榜可选匿名。

### 4.5 在线匹配与段位

**目标**

4 名学生进入同一房间，在固定时间内做同一套题，按成绩排名并获得评分变化；支持段位与赛季。

参与范围：只有 `student` 可以排队；`teacher` / `admin` 可以使用题库练习，但不进入匹配池、不产生段位分。

**匹配流程**

```text
学生点击“开始匹配”
  → 写入 Redis ZSET: matchmaking:{mode}  score=rating  member=user_id
  → 匹配器每 1–2 秒扫描，按评分窗口凑 4 人
  → 原子移除 4 人，创建 matches + match_players
  → 通过 WebSocket 推送 match.found
  → 房间倒计时（如 15 秒）→ match.started
  → 学生提交代码（携带 match_id）→ 正常判题
  → 时间到/全部完成 → 结算 → 评分/段位 → 通知
```

**匹配参数（建议默认）**

| 参数 | 默认值 | 说明 |
|---|---|---|
| 人数 | 4 | 可配置 2/4；不足 4 人时超时降级为 2 人或取消 |
| 题目数 | 3 | 难度混合：易/中/难 |
| 时长 | 60 分钟 | 服务端计时 |
| 评分窗口 | ±150 | 每 10 秒扩大 50 |
| 最长等待 | 180 秒 | 超时提示降级/取消 |
| 重连宽限 | 120 秒 | 断线可回到房间 |
| 段位 | 青铜/白银/黄金/铂金/钻石 | 按 rating 区间 |
| 定级赛 | 5 场 | 新用户先定级 |

**计分与排名**

建议采用 ICPC 风格，便于解释和实现：

- 每题有分值（或统一 1 分）；
- 排名依次比较：通过题数降序 → 罚时升序 → 最后通过时间升序；
- 罚时 = 首次通过时间 + 每次错误提交 20 分钟；
- 未通过题目不计罚时；
- 并列时以最后通过时间早者优先；仍并列则按赛前 rating 高者优先（仅用于展示，不改变评分计算）。

**评分算法**

- 推荐 Glicko-2 或多人 Elo 变体；毕业设计可用简化 Elo：
  - 每名玩家的实际得分 `S = (击败人数) / (N-1)`；
  - 期望得分 `E = 平均(1 / (1 + 10^((R_opp - R_self)/400)))`；
  - `R' = R + K * (S - E)`，K 取 24–32；新用户 K 更大；
- 评分变化写入 `rating_history`，禁止原地修改；
- 赛季结束软重置（向平均值收敛），保留历史最高段位；
- 防止刷分：同对手短时间重复匹配降低收益；异常对局进入复核。

**断线与异常**

- 单人断线：房间继续，保留 120 秒重连；超时按当前成绩结算；
- 全员断线/服务异常：取消对局，不扣分；
- 学生主动退出：视为放弃，按失败结算；频繁退出有冷却；
- 匹配取消：在 `ready` 前可取消，不扣分；
- 服务端时钟为准，客户端只展示。

> **当前实现（2026-10-29）：** 比赛页用 5 秒轮询并按 10 秒上报心跳，匹配成局后额外通过 WebSocket 推送 `match.found`。`contest_participants` 记录 `last_seen_at`、`disconnected_at`、`timed_out_at`：30 秒无心跳为 `disconnected`，距最后一次心跳 120 秒变为 `timed_out` 并冻结成绩；排位赛全员 `timed_out` 时取消比赛、不写段位分，赛事比赛保持固定结束时间。详见 `doc/2610294_短线重连实现方案.md` 与 `doc/2610295_实时推送设计方案.md`。

**WebSocket 事件（目标；v1 已实现 `match.found` 与 `notification.new`）**

```text
match.queued
match.found          { contest_id, starts_at, ends_at, participant_count }
match.started        { match_id, problems, ends_at }   // v1 未推送
match.submission     { submission_id, problem_id, status }   // v1 未推送
match.opponent_update{ user_id, solved_count }   // v1 未推送，注意隐私
match.finished       { rank, rating_delta, results }   // v1 由结果站内信覆盖
match.cancelled      { reason }   // v1 由取消站内信覆盖
```

### 4.6 组织、作业与批改

> **当前实现（2026-10-27）：** 已实现组织创建/归档、邀请码与批量邀请、成员管理；作业草稿/组题/开始与截止时间/发布/归档；学生作业提交、自动判题、教师批改台、单题手动分/评语、整体评语、截止后发布成绩，以及作业/成绩站内通知。`classes` 当前用 `course_name`、`term` 字段承载课程与学期信息，尚未拆出独立 `terms` 表；CSV 导入、统计导出、申诉、邮件通知仍未实现。作业策略（迟交、重交、计分、可见性、补交/免修、解析、统计与审计）已按 `doc/2610271_作业策略的实现.md` 完成。

**组织模型**

- 学期 `terms`：名称、起止时间；
- 组织 `classes`：学期、课程名、组织名、owner 教师；active 组织的 owner 必须是 `teacher`；
- 成员 `class_members`：只包含 `student`，不存教师/管理员，不设 `member_role`；
- 第一版不做协同教师/助教；教师之间按 owner 隔离，非 owner 教师访问返回 404；
- 后续支持 CSV 导入学号/邮箱、批量邀请；被添加者必须是学生；
- 学生可加入多个组织；教师不能加入组织，也不能提交组织作业；
- 归档组织冻结，可保留被降级的历史 owner，但不再有管理入口；管理员不可查看。

**作业模型**

- 作业归属于组织；
- 从题库选择题目，设置分值、顺序、是否必做；
- 开始/截止时间、时区；
- 迟交策略：禁止 / 扣分 / 允许但标记；
- 重交策略：不限 / 限定次数 / 只取最后一次 / 取最高分；
- 评分策略：自动判题分 + 教师人工分；
- 提交权限：只有组织 active `student` 可以提交作业；教师/管理员只能用题目页“运行”预览，不能产生作业提交；
- 可见性：截止前是否显示得分、是否显示答案/解析；
- 状态：草稿 → 定时 → 进行中 → 已截止 → 归档。

**提交流程**

```text
学生打开作业 → 看到题目与截止时间
  → 提交代码（submissions.assignment_id）
  → 自动判题
  → 作业面板显示每题状态/得分
  → 教师批改（可选人工分/评语）
  → 发布成绩 → 站内信 + 邮件
```

**批改与反馈**

- 教师可对每道题给分、写评语；
- 支持整体评语、评分 rubric（可选）；
- 支持批量发布/撤回；
- 成绩修改必须填写原因并写审计；
- 学生可对成绩提出申诉，教师处理；
- 导出 CSV 成绩单。

**统计**

- 组织完成率、平均分、每题通过率、常见错误类型；
- 未提交名单、迟交名单；
- 题目难度校准（实际通过率 vs 标称难度）；
- 防作弊报告入口。

### 4.7 防作弊系统

这是平台的必备能力，建议作为独立子系统设计，而不是只依赖隐藏用例。

#### 4.7.1 威胁模型

| 威胁 | 例子 | 主要检测/预防 |
|---|---|---|
| 代码抄袭 | 同学间复制、往届答案 | 代码相似度、提交历史、跨作业比对 |
| AI 生成 | 直接粘贴 AI 代码 | 行为信号 + 相似度 + 人工复核（不依赖单一 AI 检测） |
| 账号共享/代做 | 一人多号、他人登录 | 设备/IP/登录行为、异常通过速度、邮箱/学号核验 |
| 匹配串通 | 4 人房间互相放水 | 对局异常、重复对手、评分异常、代码相似 |
| 答案泄露 | 隐藏用例/题解外流 | 隐藏用例隔离、访问控制、日志审计 |
| 沙箱逃逸 | 读取宿主/网络 | gVisor、无网络、非 root、只读、资源限制 |
| 作业抄袭链 | 组织内雷同 | 组织范围相似度图、团伙聚类 |

#### 4.7.2 分层设计

**第一层：预防**

- 隐藏用例 + 随机参数变体（P2）；
- 沙箱无网络、只读、非 root、资源限制；
- 提交/匹配频率限制、账号邮箱验证；
- 匹配房间开始前提示诚信规则；
- 作业可设置“仅限课堂时间/机房 IP”；
- 关键操作审计，教师改分必须填写原因；管理员不参与改分，也不能无痕查看教学数据。

**第二层：检测**

| 信号 | 来源 | 可靠性 | 处理 |
|---|---|---|---|
| 代码相似度 | 判题后异步扫描 | 中高 | 生成报告，人工复核 |
| 提交时间异常 | 服务端时间 | 中 | 结合题目难度/通过率 |
| 粘贴/焦点/全屏事件 | 前端采集（需告知） | 中低 | 仅作辅助证据 |
| IP/设备变化 | 请求元数据 | 中 | 账号共享/代做线索 |
| 匹配同步提交 | 房间事件 | 中高 | 串通线索 |
| 不可能的解速 | 历史分布 | 中 | 人工复核 |
| 重复对手/互送分 | 对局历史 | 中 | 评分异常检测 |

**第三层：证据与处置**

- 所有信号写入 `submission_signals` / `similarity_pairs`；
- 达到阈值生成 `cheat_reports`，附带证据（相似片段、时间线、对局记录）；
- 教师在批改台复核自己组织的报告：确认、驳回、要求说明；管理员不进入具体教学报告和成绩数据；
- 处罚分级：提醒 → 该次作业零分 → 作业重做 → 课程纪律流程；
- 学生可申诉，申诉记录与证据保留；
- **不得仅凭单一低可靠信号自动处分**；
- 所有操作写审计。

#### 4.7.3 代码相似度

- 预处理：去注释、统一空白、可选标识符重命名；
- 分词/AST 指纹 + winnowing 或 shingle；
- 同语言优先；跨语言可先用结构特征，不作为主要证据；
- 比对范围：同题、同作业、同组织、同匹配、最近 N 天；
- 输出相似度分数、匹配片段、双方提交 id；
- 阈值分级：低（仅记录）、中（报告）、高（优先复核）；
- 性能：异步批量，限制单次扫描量，避免拖垮判题 Worker。

#### 4.7.4 行为信号

前端可采集（必须在作业/匹配开始前明确告知）：

- 粘贴事件次数/长度；
- 页面失焦、切屏、退出全屏；
- 编辑器内容突变；
- 输入节奏异常（仅聚合，不记录按键内容）；
- 提交间隔、首次通过时间。

原则：

- 只采集与诚信相关的聚合信号，不记录完整键盘内容；
- 不默认开启摄像头/麦克风/屏幕录制；
- 信号仅用于生成报告，不作为唯一处罚依据；
- 学生可查看自己的信号摘要，保障知情权。

#### 4.7.5 架构

```text
submission.created
  → anti_cheat stream
  → anticheat_worker:
      1. 规范化代码
      2. 与范围内历史提交比对
      3. 聚合行为信号
      4. 写 similarity_pairs / submission_signals
      5. 超阈值生成 cheat_reports
  → 管理端复核队列
  → 决定 + 通知 + 申诉
```

#### 4.7.6 指标

- 报告数量、确认率、驳回率、申诉翻案率；
- 人工复核平均耗时；
- 相似度阈值与误报率校准；
- 按组织/题目的异常分布；
- 不把“检测数量”当作唯一成功指标，误伤率同样重要。

### 4.8 论坛 / 校园墙

**功能**

- 发帖、编辑、删除（软删除）；
- 评论、回复、点赞；
- 引用题目：结构化 `problem_id`，展示题目标题/难度卡片；
- 标签、搜索、热门/最新排序；
- 匿名/昵称显示（后台仍记录真实作者，供审核）；
- 举报、屏蔽、禁言；
- 题解/剧透标记：默认折叠，用户点击展开；可设置为“通过该题后可见”；
- 通知：被回复、被引用、被 @、帖子被审核。

**内容与审核**

- 仅验证过的校园邮箱可发帖；
- 敏感词/链接/频率限制；
- 举报进入审核队列；
- 管理员可隐藏、删除、禁言、置顶；
- 所有审核动作写审计；
- 保留数据策略：软删除保留 30–90 天，之后物理清理。

**技术要点**

- Markdown 渲染必须 sanitize，禁止任意 HTML/脚本；
- 代码块高亮，限制单帖长度；
- 图片/附件本期不做，避免存储与内容安全成本；
- 搜索先用 PostgreSQL `pg_trgm` + 标签；中文分词后续可接 `zhparser`；
- 帖子引用题目使用外键 `ON DELETE SET NULL`，题目归档后仍保留讨论；
- 反滥用：新账号发帖冷却、重复内容检测、举报阈值自动隐藏（待人工确认）。

### 4.9 通知与邮件

**通知类型**

| 事件 | 站内信 | 邮件 | 说明 |
|---|---:|---:|---|

| 作业发布/即将截止 | ✓ | ✓ | 可配置 |

| 论坛回复/引用/审核 | ✓ | 可选 | 偏好设置 |

| 防作弊报告/申诉结果 | ✓ | ✓ | 仅相关人员 |
| 账号安全 | ✓ | ✓ | 登录异常/密码变更 |

**邮件架构**

```text
业务事务
  → 写 notifications（站内信）
  → 写 email_outbox（同一事务或可靠事件）
  → notify_worker 读取 outbox
  → SMTP 发送
  → 成功标记 sent；失败指数退避重试；超过上限 dead
```

要点：

- outbox 表带 `idempotency_key`，避免重复发送；
- 开发环境用 MailHog/Mailpit，不真实外发；
- 生产配置 SPF、DKIM、DMARC，使用校内 SMTP 或可信服务商；
- 处理退信/投诉；事务邮件不提供退订，营销/广播提供退订；
- 广播邮件分批发送，避免瞬时压力；
- 站内信通过 WebSocket 推送，离线用户下次登录拉取；
- 用户可配置通知偏好（类型 × 渠道），但成绩/安全类不可关闭。

**当前实现（2026-10-29）：** 通知写入 `notifications` 时带 `email_state='pending'`；后台邮件循环按 `notification_preferences`（类别 × `email` 渠道）把待处理通知转入 `email_outbox` 再投递，批量插入的通知入口因此无需单独处理邮件。偏好接口为 `GET|PUT /api/profile/notification-preferences`，类别为组织、作业与成绩、论坛互动、账号处理、竞赛结果、系统公告；论坛互动与系统公告默认关闭邮件，其余默认开启；站内信始终接收，未验证邮箱只保留站内信。数据库迁移为 `0023_notification_preferences.sql`。

### 4.10 排行榜与统计

**榜单类型**

- 全局：通过题数、rating、连续打卡；
- 组织：作业完成率、平均分、题目通过数；
- 作业：分数排名仅 owner 教师可见，不向学生公开组织排名；
- 匹配：赛季 rating、段位、胜场；
- 题目：通过率、尝试次数、平均耗时。

**实现**

- 先用 SQL 聚合 + 缓存/物化视图，按分钟或事件刷新；
- 数据量大时再引入 `daily_user_stats` 预聚合；
- 并列规则明确并展示；
- 防刷：同一题重复 AC 只计一次；匹配异常对局不计分；频繁换号检测；
- 隐私：允许学生在公共榜匿名，管理员仍可看真实身份；非本组织教师不能查看其他组织学生身份。

### 4.11 管理端

**页面**

- 仪表盘：用户、平台提交量、判题队列、Worker、异常、待办审核；
- 用户与角色：搜索、禁用、重置密码、调整角色；学生升教师/教师降级前展示清理条件；
- 题目审核：待审列表、完整题面/用例、通过/拒绝/备注；
- 题目管理：编辑 `run_config` / `judge_cases`、重判、归档；
- 论坛审核：举报、隐藏、禁言；
- 匹配配置：人数、时长、题目池、赛季、段位阈值；
- 广播：按角色发送站内信和邮件；组织通知由 owner 教师在组织内触发；
- 系统设置：开关、限额、邮箱域名白名单；
- 审计日志：操作者、动作、对象、前后值、时间、IP；
- 数据导出/删除请求。

**原则**

- 管理端所有写操作审计；
- 敏感操作二次确认（删除题目、授予管理员、归档组织后降级）；
- 管理员不能查看或修改教学成绩、评语和组织数据；
- 授予管理员、系统配置、审计导出使用独立权限码（如 `system.manage`），敏感操作二次确认并审计；
- 角色互斥，不设 `student ⊂ teacher ⊂ admin` 层级，也不提供角色叠加；
- 关键配置变更记录变更人。

### 4.12 AI 能力（远期）

暂不进入 MVP。后续可做：

- 做题风格分析：根据提交历史、错误类型、耗时给出建议；
- 代码 review：命名、复杂度、边界条件；
- 个性化练习推荐；
- 教师辅助：批量生成题目草稿、相似题推荐；
- 防作弊辅助：AI 生成代码检测（仅作信号，不作唯一证据）。

架构建议：

- 独立的 AI Gateway，不把模型调用散落在业务代码；
- 只发送必要数据，去除学号/姓名等 PII；
- 结果标注“AI 生成，仅供参考”；
- 人工复核与可关闭开关；
- 成本/速率限制与缓存；
- 评测集与效果评估，避免“看起来智能”。

### 5.3 关键约束与索引

- `users.email` 唯一；`users.student_no` 可空但唯一；
- `users.role` CHECK 只允许 `student` / `teacher` / `admin`；`idx_users_role` 支持按角色筛选；
- `class_members` 唯一 `(class_id, user_id)`，服务层校验成员必须是 `student`；
- `assignments` 索引 `(class_id, status, due_at)`；
- `submissions` 索引 `(user_id, submitted_at)`、`(problem_id, submitted_at)`、`(assignment_id)`、`(match_id)`；
- `matches` 索引 `(status, started_at)`；`match_players` 唯一 `(match_id, user_id)`；
- `contests.official_event_id` 唯一（`WHERE official_event_id IS NOT NULL`），一个赛事最多生成一场比赛；`official_event_problems` 唯一 `(event_id, problem_id)` 与 `(event_id, position)`；
- `similarity_pairs` 唯一 `(submission_a, submission_b, algorithm)`，避免重复扫描；
- `notifications` 索引 `(user_id, read_at, created_at)`；
- `email_outbox` 索引 `(status, next_attempt_at)`；
- `audit_logs` 索引 `(actor_id, created_at)`、`(target_type, target_id)`；
- 论坛搜索：`pg_trgm` 索引或 `tsvector`（中文分词后续接入）。

### 5.4 数据生命周期

- 提交代码与成绩：教学周期内保留；毕业/课程结束后归档；
- 审计日志：至少保留 1 年；
- 邮件 outbox：发送成功后保留 30 天，失败/dead 保留 90 天；
- 行为信号：保留 1 个学期，申诉/报告相关延长；
- 论坛软删除：保留 30–90 天；
- 账号删除：匿名化统计，保留必要教学记录；
- 备份：每日全量 + 关键表增量；定期恢复演练。

## 6. 接口与事件

### 6.1 REST 约定

- 统一响应：`{"success": true, "data": {}, "error": null}`；
- 创建成功 201，删除成功 204 或 200；
- 分页：`page`、`size`、`total`，`size` 上限 100；
- 排序白名单，禁止任意字段拼接；
- 错误码：`VALIDATION_ERROR`、`UNAUTHORIZED`、`FORBIDDEN`、`NOT_FOUND`、`RATE_LIMITED`、`SERVICE_UNAVAILABLE`、`INTERNAL_ERROR`；
- 关键写接口支持 `Idempotency-Key`（提交、作业提交、广播）；
- 时间统一 UTC 存储，前端按用户时区展示；
- 所有列表接口按权限裁剪字段。

### 6.3 WebSocket

**当前实现（2026-10-29，v1）**

- `POST /api/ws/ticket`（Bearer JWT）返回 60 秒有效的一次性票据；`GET /api/ws?ticket=...` 完成升级，JWT 不进入 URL 或日志；
- 客户端发送 `hello`，服务端返回 `ready` 与服务器时间；
- 服务端每 30 秒发送应用层 `ping`，客户端回 `pong`；90 秒无客户端消息断开；
- 服务端按用户广播事件，统一信封为 `{id, type, data, server_time}`：
  - `notification.new`：站内信写入后由通知表尾差量任务在约 2 秒内推送，payload 与通知列表项同构；
  - `match.found`：匹配成局后推送给房间内全部选手，payload 为 `{contest_id, starts_at, ends_at, participant_count}`，题目仍由 `GET /api/contests/{id}` 拉取；
  - `resync`：广播积压被丢弃，客户端应重新拉取快照；
- 重连不使用 `last_event_id`，客户端重连后重新拉取未读数与比赛详情；
- 单 API 实例使用进程内 `RealtimeHub`（按用户 `tokio::sync::broadcast`）；多实例时替换为 Redis Pub/Sub。

**后续目标（尚未实现）**

- 客户端 → 服务端 `match.queue` / `match.cancel` / `match.ready`，匹配仍走现有 REST 接口；
- `match.started` / `match.finished` / `match.opponent_update` 与判题状态流式推送；
- `last_event_id` 断线重放、多实例 Redis Pub/Sub 广播。

**多实例（目标）**

- WebSocket 连接可能落在不同 API 实例；使用 Redis Pub/Sub 广播房间事件；
- 房间权威状态在 PostgreSQL/Redis，WebSocket 只做传输；
- 客户端重连必须能通过 `GET /api/contests/{id}` 恢复快照。

### 6.5 限流与幂等

- 登录/注册：IP + 账号双维度；
- 提交/运行：每用户每分钟、每用户并发 1；
- 匹配：队列中只能有一个；
- 论坛：新账号发帖冷却、每用户每日上限；
- 邮件：同一用户同类事件去重；
- 作业提交/广播：`Idempotency-Key`；
- 判题：提交 id 作为幂等键，终态条件更新；
- 所有异步任务至少一次投递，业务处理必须幂等。

## 7. 安全、隐私与合规

### 7.1 账户与权限

- Argon2 密码哈希；密码强度与泄露密码库检查（可选）；
- 访问令牌短期 + 刷新令牌轮换；登出/禁用即时失效；
- 管理员 2FA（TOTP）建议上线；
- 权限检查在服务层统一实现，避免只靠前端隐藏；
- 角色互斥：`student` / `teacher` / `admin` 不继承、不兼任；管理员没有教学权限；
- 资源级鉴权（组织/作业/提交归属）必须测试；
- 防止越权：教师不能看其他组织成绩，学生不能看他人代码，管理员不能看他人提交/成绩。

### 7.2 应用安全

- CORS 限制为前端域名（当前为 permissive，需要收紧）；
- 安全响应头：CSP、HSTS、X-Content-Type-Options、Referrer-Policy；
- 所有输入服务端校验；SQLx 参数绑定；
- Vue 默认转义；论坛 Markdown 必须 sanitize，禁止原始 HTML；
- 文件上传（若后续支持）：类型/大小校验、病毒扫描、对象存储隔离；
- 限流与防爆破；登录失败锁定；
- 依赖审计与定期升级；
- 密钥不入库、不进日志；环境变量/密钥管理；
- 备份加密；数据库不暴露公网。

### 7.3 沙箱与代码执行

- 生产使用 gVisor（`runsc`），本地允许 `runc` 但显式警告；
- 容器非 root、只读根文件系统、无网络、独立 tmpfs；
- CPU、内存、PID、时间、输出大小限制；
- 每种语言固定镜像 digest，构建可复现；
- 判题容器不注入数据库/Redis 凭据；
- 隐藏用例只通过受控 harness 传入，日志不打印完整输入/输出；
- 资源耗尽、超时、崩溃都要有明确终态；
- 定期做沙箱逃逸与资源限制测试。

### 7.4 防作弊的伦理边界

- 明确告知学生采集哪些信号、用于什么目的；
- 不默认开启摄像头/麦克风/屏幕录制；
- 信号不是判决，必须人工复核；
- 提供申诉渠道与证据查阅；
- 误判可撤销并恢复成绩；
- 数据保留期限与访问范围明确；
- 教师只能查看自己组织的敏感报告，且查询留痕；管理员不进入具体教学报告。

### 7.5 数据隐私与合规

- 最小化采集：只收集教学必需信息；
- 学号/姓名/邮箱等 PII 加密或脱敏展示；
- 学生之间默认看不到彼此邮箱/学号；
- 数据导出/删除请求有流程；
- 遵守学校数据管理规定与《个人信息保护法》相关要求；
- 第三方邮件/日志/监控服务需评估数据出境与保密；
- 论文/演示使用脱敏数据。

### 7.6 审计与应急

- 审计：登录、角色变更、题目审核、成绩修改、广播、论坛处罚、配置变更；
- 审计日志只追加，定期归档；
- 安全事件预案：账号泄露、沙箱逃逸、数据泄露、邮件滥发；
- 备份与恢复演练；

## 8. 非功能设计

### 8.1 容量目标（毕业设计/单校规模）

| 指标 | 目标 |
|---|---|
| 注册用户 | 5,000 |
| 同时在线 | 300–500 |
| 提交峰值 | 60–100 次/分钟 |
| 同时匹配房间 | 20–50 |
| 判题 Worker | 2–4 并发（可水平扩展） |
| 单次判题 P95 | < 15 秒（常规题目） |
| API P95 | < 300 ms（不含判题） |
| 可用性 | 学期内 99.5% |
| 备份 | 每日全量，RPO 24h，RTO 4h |

### 8.2 性能

- 数据库：关键查询建索引；列表分页；避免 N+1；
- Redis：状态缓存、限流、匹配池、队列；
- 判题：共享信号量、队列深度监控、必要时增加 Worker；
- 邮件/防作弊：独立 Worker，避免挤占判题；
- 排行榜：预聚合/物化视图；
- 前端：路由懒加载、代码分割、编辑器按需加载；
- 压测：k6/Locust 覆盖登录、题库、提交、轮询、匹配。

### 8.3 可用性与容灾

- PostgreSQL 单机 + 每日备份；条件允许做主从/流复制；
- Redis 不作为事实来源，丢失后从数据库恢复队列（需要补偿任务）；
- Worker 崩溃后 Pending 消息由 XAUTOCLAIM 回收；
- 判题超时/卡死由 reaper 回收；
- 邮件 outbox 可重放；
- 匹配房间状态持久化，API 重启后可恢复；
- 升级采用向后兼容迁移，先加列/表，再切读写，最后清理。

### 8.4 可观测性

**结构化日志字段**

```text
request_id, user_id, role, route, status, latency_ms
submission_id, problem_id, assignment_id, match_id, language,
queue_wait_ms, compile_ms, run_ms, total_ms, case_passed, case_total,
worker_name, attempt, verdict
```

**指标**

- 请求量/错误率/延迟；
- 提交创建数、终态分布、判题时长；
- 队列深度、PEL、最老 Pending、死信数；
- 活跃 Worker 数、心跳；
- `internal_error` 比例；
- 邮件发送成功/失败/退信；
- 防作弊报告数/复核时长；
- 匹配排队时长、房间数、取消率；
- 数据库连接池、Redis 延迟、磁盘。

**告警**

- 无存活判题 Worker；
- PEL > 50 或最老 Pending > 5 分钟；
- `internal_error` 比例 > 1%；
- 邮件失败率突增；
- 磁盘/数据库连接耗尽；
- 匹配队列等待 > 5 分钟。

### 8.5 测试策略

|---|---|
| 单元测试 | 校验、状态机、评分、权限、相似度算法 |
| 集成测试 | PostgreSQL + Redis + 假 Worker，覆盖队列/终态/回收 |
| 冒烟测试 | 已有 `smoke_submission.sh`、`smoke_forum.sh`、`smoke_teaching.sh`、`smoke_problem_review.sh`、`smoke_auth_email.sh`；补 `smoke_run.sh` |
| E2E | 浏览器：登录→刷题→提交→作业→批改→通知 |

| 防作弊测试 | 已知抄袭/独立实现样本，评估误报/漏报 |
| 性能测试 | 登录、题库、提交、轮询、匹配 |
| 安全测试 | 越权、注入、XSS、限流、沙箱 |
| 可访问性 | 键盘操作、对比度、屏幕阅读器基础检查 |

### 8.6 部署拓扑

**开发环境**

```text
docker compose:
  postgres + redis + api + judge_worker + mailhog
  + vite dev server / nginx
  + runner 镜像（python/node/cpp/java）
```

**生产环境（单机起步）**

```text
Nginx (TLS)
  ├─ 静态前端
  ├─ /api → backend-rust
  └─ /api/ws → backend-rust
PostgreSQL（本地/独立）
Redis
judge_worker × N（runsc）
notify_worker
anticheat_worker
scheduler
备份脚本 + 日志轮转
```

- 生产禁止 `runc`；`RUN_SANDBOX_ALLOW_RUNC=false`；
- Docker daemon 权限仅授予 Worker 运行用户；
- 数据库/Redis 不暴露公网；
- 配置通过环境变量/密钥文件注入；
- 迁移在发布前执行，保留回滚方案。

### 8.7 CI/CD

- GitHub Actions：`cargo fmt --check`、`cargo clippy -D warnings`、`cargo test`、前端 `npm run build`、迁移检查；
- 冒烟测试需要 Docker/gVisor，可放在 self-hosted runner 或 nightly；
- 镜像构建与扫描；
- 发布：构建 → 备份 → 迁移 → 启动 → 健康检查 → 冒烟；
- 回滚：保留上一版本二进制/镜像与迁移回滚说明。

## 10. 风险与取舍

| 风险 | 影响 | 应对 |
|---|---|---|
| 范围过大 | 毕业前做不完 | MoSCoW + 每阶段可演示；AI/竞赛延后 |
| 4 人匹配冷启动 | 匹配等待过久 | 超时降级 2 人/取消；课内约定匹配时段 |
| 防作弊误判 | 学生申诉、信任受损 | 证据链 + 人工复核 + 申诉 + 阈值校准 |
| 行为监控隐私 | 合规/抵触 | 明确告知授权用途与记录范围；只记录摄像头授权状态及切屏/粘贴事件，不采集视频、不默认上传 |
| 邮件可达性 | 成绩通知失败 | 校内 SMTP、SPF/DKIM/DMARC、outbox 重试、站内信兜底 |
| 沙箱运维 | 判题不可用/逃逸 | gVisor、镜像固定、资源限制、健康检查 |
| 单机故障 | 教学中断 | 每日备份、快速恢复、Redis 可重建 |
| 评分争议 | 匹配不公平 | 公开规则、重放对局、异常对局不计分 |
| 论坛滥用 | 内容风险 | 邮箱验证、限流、举报、审核、软删除 |
| 角色互斥过于刚性 | 教师/管理员无法用同一账号学习或授课 | 使用独立账号；后续评估关联账号，不恢复角色叠加 |
| 数据丢失 | 成绩/提交丢失 | 备份、软删除、审计、导出 |
| 时间不足 | 论文/答辩 | 先闭环后亮点；用冒烟和演示脚本保证稳定 |

## 11. 还可以补充的设计点

以下是对原始需求的补充建议，按优先级排列。

### 11.1 教学与组织

1. **学期/课程/组织三层模型**：避免每年复制数据；支持课程代码、组织名称、学期归档。
2. **学生名单导入**：CSV（学号、姓名、邮箱），失败行返回原因；支持批量邀请。
3. **协同教师/助教（后续）**：一个组织有多名教师时，他们仍是 `teacher`，不获得学生身份；第一版只支持 owner 教师，不做协同教师/助教。
4. **作业策略**：迟交扣分、重交次数、取最高/最后一次、补交、免修。
5. **成绩申诉与改分审计**：教师改分必须填原因；学生可申诉；历史可追溯。
6. **成绩导出**：CSV/Excel，包含每题得分、总分、迟交标记。
7. **教学统计**：完成率、平均分、题目通过率、常见错误、未提交名单。
8. **课程归档**：学期结束后只读，保留数据，支持复制到新学期。

### 11.2 题库与判题

9. **题目版本化**：已通过题目的修改走新版本/重新审核，避免线上用例被悄悄替换。
10. **重判机制**：修复用例/编译器版本后批量重判，保留历史，不覆盖旧成绩。
11. **归档优先于删除**：教学记录不应因误删题目而消失；硬删除需显式确认与导出。
12. **标准输入/输出题型**：除函数式外，支持 `stdio`，便于通用算法题与课程作业。
13. **特殊判题**：浮点误差、多答案、交互题（后续）；先设计接口，不急于实现。
14. **按学生随机用例**：同逻辑不同参数，降低硬编码与抄袭；需保证可复现。
15. **语言版本固定**：展示编译器/运行时版本，避免环境差异争议。
16. **判题配额与公平**：作业/匹配/练习分池或分权重，防止高峰互相挤占。

### 11.3 匹配与段位

17. **匹配降级**：4 人等待超时后允许 2 人开局或取消，避免永远匹配不到。
18. **断线重连**：120 秒宽限；服务端计时；全员断线取消不扣分。
19. **赛季与定级**：新用户 5 场定级；赛季软重置；历史最高段位保留。
20. **评分规则公开**：展示 rating 变化、对手平均分、排名依据，减少争议。
21. **反串通**：重复对手降收益、异常对局复核、同步提交检测。
22. **对局重放**：保存题目、提交时间线、排名，供申诉/复盘。
23. **匹配题目池**：按难度/标签配置，避免同一题反复出现；可设置本周题池。

### 11.4 防作弊

24. **证据链**：每个报告包含相似片段、时间线、行为信号、对局记录，而不是一个分数。
25. **分级处置**：提醒/本次零分/重做/纪律流程；避免一上来就重罚。
26. **申诉与恢复**：学生可提交说明；误判可撤销并恢复成绩。
27. **隐私告知**：作业/匹配开始前明确采集哪些信号；提供摘要查看。
28. **误报评估**：用已知独立实现样本校准阈值；记录确认率/翻案率。
29. **跨作业/跨组织比对**：防止往届答案复用；注意数据范围与隐私。
30. **AI 代码检测只作辅助**：不把不可解释的模型分数作为处分依据。

### 11.5 论坛与通知

31. **匿名与实名分离**：前台匿名，后台保留作者；仅管理员可见真实作者。
32. **剧透控制**：题解默认折叠；可设置“通过后可见”。
33. **题目引用卡片**：结构化引用，展示标题/难度/通过率，点击跳转。
34. **举报与审核队列**：自动隐藏阈值 + 人工确认；审核动作审计。
35. **搜索**：先用 `pg_trgm`/标签，中文分词后续升级；避免一开始引入复杂搜索引擎。
36. **通知偏好**：类型 × 渠道；成绩/安全类不可关闭。
37. **邮件可达性**：SPF/DKIM/DMARC、退信处理、开发环境 MailHog。
38. **广播分批**：管理员按角色广播；组织通知由 owner 教师在组织内触发。异步扇出，避免阻塞和邮件风暴。
39. **站内信兜底**：邮件失败不影响站内信；用户下次登录能看到。

### 11.6 管理与运维

40. **管理员内部分权**：授予管理员、系统配置、审计导出使用 `system.manage` / `system.audit` 权限码并二次确认；角色仍然互斥，不设层级继承。
41. **审计日志**：登录、角色、审核、改分、广播、论坛处罚、配置变更。
42. **管理端二次确认**：删除题目、授予管理员、归档组织后降级。
43. **判题健康面板**：队列深度、PEL、Worker、死信、异常率。
44. **备份与恢复演练**：每日全量；每学期至少一次恢复演练。
45. **CI**：fmt/clippy/test/build/migration；冒烟在 self-hosted/nightly。
46. **压测**：提交峰值、匹配并发、通知扇出。
47. **功能开关**：提交评测、匹配、论坛、邮件、防作弊可独立开关，便于演示/降级。
48. **数据导出/删除流程**：满足学校隐私要求。
49. **可访问性**：键盘操作、对比度、错误提示；移动端至少可刷题/看作业。
50. **文档**：部署手册、教师手册、学生手册、答辩演示脚本。

### 11.7 AI 与论文

51. **AI 数据治理**：脱敏、最小化、可关闭、人工复核、成本上限。
52. **论文指标**：判题延迟、作业完成率、防作弊确认率/翻案率、匹配等待时长、系统可用性。
53. **演示脚本**：一条主线覆盖学生做题、匹配、作业、教师批改、管理员审核、防作弊报告、通知。
54. **创新点表述**：4 人匹配评分 + 教学作业闭环 + 证据化防作弊，而不是“又一个 OJ”。
