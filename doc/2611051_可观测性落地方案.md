# 可观测性落地方案

> 日期：2026-11-05
> 状态：v1 已实现
> 关联：`2611012_架构与性能收口.md`、`2611031_服务器部署方案.md`、`AGENTS.md`

## 1. 目标

`/metrics` 已经提供 HTTP、连接池、判题队列与 Worker 心跳指标，但此前没有采集、存储、展示与告警。本方案把指标接口补成一条可运行的单机可观测性链路：

- Prometheus 定时抓取 `backend:3000/metrics` 并保存 15 天；
- Alertmanager 对告警分组、抑制并投递到邮件或通用 webhook；
- Grafana 预置 Prometheus 数据源与「Theseus 运行概览」仪表盘；
- 三个组件放在 Compose 的可选 `observability` profile 中，不启用时不影响现有部署。

不引入日志聚合与链路追踪，日志仍使用 `docker compose logs` 与 `.dev-logs/`。

## 2. 拓扑

```text
                    ┌─────────────────────────────┐
                    │ Prometheus :9090            │
                    │  抓取 backend:3000/metrics  │
                    └───────┬─────────────┬───────┘
                            │             │
                   告警规则 │             │ PromQL
                            ▼             ▼
                    ┌──────────────┐  ┌──────────────┐
                    │ Alertmanager │  │ Grafana :3000│
                    │ :9093        │  │ 预置仪表盘    │
                    └──────┬───────┘  └──────────────┘
                           │
                邮件 / 通用 webhook

所有观测端口只绑定宿主机 127.0.0.1，不经过前端 Nginx。
```

| 服务 | 镜像 | 宿主机端口 | 数据卷 |
|---|---|---|---|
| `prometheus` | `prom/prometheus:v2.55.1` | `127.0.0.1:9090` | `prometheus-data` |
| `alertmanager` | `prom/alertmanager:v0.27.0` | `127.0.0.1:9093` | `alertmanager-data` |
| `grafana` | `grafana/grafana:11.2.0` | `127.0.0.1:3001` | `grafana-data` |

Prometheus 不依赖 backend 健康状态启动，否则 API 故障时反而采集不到 `up` 指标，无法触发 `TheseusBackendDown`。

## 4. 启用方式

```bash
cd /opt/theseus/deploy
# 1. 合并新增配置（或手工编辑 .env）
./scripts/merge_env.sh --dry-run
./scripts/merge_env.sh
# 2. 在 .env 中设置
#    COMPOSE_PROFILES=observability
#    GRAFANA_ADMIN_PASSWORD=<强密码>
#    ALERT_EMAIL_TO=ops@example.com   # 可选，留空则只在 Alertmanager UI 查看
# 3. 启动
docker compose up -d
```

`.env` 中的 `COMPOSE_PROFILES` 会被 Docker Compose 自动读取，因此 `update.sh` 里的 `docker compose up -d` 也会一并启用观测组件，升级后不需要额外命令；`update.sh` 结束时还会检查 Prometheus 与 Grafana 的本地健康端点。若只用过 `docker compose --profile observability up -d` 临时启用，建议补上 `COMPOSE_PROFILES`，避免后续命令遗漏该 profile。

公网查看使用 SSH 隧道，不要把 9090/9093/3001 直接暴露：

```bash
ssh -L 3001:127.0.0.1:3001 -L 9090:127.0.0.1:9090 -L 9093:127.0.0.1:9093 user@server
# 浏览器打开 http://127.0.0.1:3001，账号见 GRAFANA_ADMIN_USER
```

Grafana 首次启动会自动创建 `Theseus` 文件夹与 `Theseus 运行概览` 仪表盘，数据源已配置为 Prometheus。

## 5. 指标

HTTP、连接池、判题队列、Worker 心跳与匹配指标沿用 `2611012` 的定义，本方案新增：

| 指标 | 类型 | 标签 | 说明 |
|---|---|---|---|
| `theseus_judge_queue_enabled` | gauge | `queue`=run / submit / anticheat | 队列开关本身，即使 Redis 不可用也会输出 |

该指标的用途：当 `theseus_judge_stream_length` 缺失时，无法区分「队列本来就没启用」和「Redis 连接失败」。告警规则通过 `theseus_judge_queue_enabled == 1 unless on(queue) theseus_judge_stream_length` 只在后者触发。

### 5.1 队列长度口径

落地告警时发现原实现只 `XACK` 不删除 Stream 条目，`XLEN` 会随历史任务单调增长：积压告警在累计 50 个任务后必然误报，Stream 也会长期占用内存。本次同步修改 `judge/queue.rs`：

- `ack` 在 `XACK` 成功后执行 `XDEL`，每个 Stream 只有一个消费组，删除不影响其他消费者；
- 顺序保持先确认后删除：即使删除失败，任务也不会被重复投递，只在极端情况下留下已确认条目；
- 无数字 ID 的无效消息在丢弃时同样删除。

调整后 `theseus_judge_stream_length` 表示未确认与处理中的任务量，积压阈值才有实际意义。

从旧版本升级时，Stream 中已有的历史条目不会自动消失。可在低峰期按最小 pending ID 做一次安全裁剪（只删除已确认的旧条目）：

```bash
cd deploy
S=theseus:judge:submissions
G=judge-submit-workers
MIN=$(docker compose exec -T redis redis-cli --raw XPENDING "$S" "$G" - + 1 | head -n1)
[ -n "$MIN" ] && docker compose exec -T redis redis-cli XTRIM "$S" MINID "$MIN"
# run 与 anticheat 队列同理，替换 S / G 后执行
```

没有 pending 时可跳过，或先停止 Worker、确认队列为空后直接重建 Stream。裁剪前先看 `XINFO GROUPS` 的 `pending` 与 `lag`，不要在判题高峰期操作。

## 6. 告警规则

| 告警 | 条件 | 持续 | 级别 |
|---|---|---|---|
| `TheseusBackendDown` | `up{job="theseus-backend"} == 0` | 1m | critical |
| `TheseusAlertmanagerDown` | `up{job="alertmanager"} == 0` | 2m | warning |
| `TheseusHigh5xxRate` | 5xx 请求占比 > 1% | 5m | critical |
| `TheseusHighP95Latency` | 全局 P95 > 1s | 10m | warning |
| `TheseusJudgeWorkerDown` | `theseus_judge_worker_up == 0` | 2m | critical |
| `TheseusJudgeMetricsMissing` | 队列启用但无 Stream 指标 | 5m | warning |
| `TheseusJudgeBacklog` | Stream 长度 > 50 | 10m | warning |
| `TheseusJudgePendingHigh` | 已投递未 ACK > 20 | 10m | warning |
| `TheseusJudgeDeadLetters` | 死信数 > 0 | 5m | warning |
| `TheseusDbPoolSaturated` | 连接池使用率 > 90% | 10m | warning |
| `TheseusMatchmakingErrors` | 10 分钟内匹配批次出错 | 立即 | warning |

critical 告警会抑制同名 warning（Alertmanager `inhibit_rules`），避免同一故障重复通知。

阈值按单机默认配置给出。判题并发或 `DB_MAX_CONNECTIONS` 调整后，应同步复核积压与连接池阈值。

## 7. 通知渠道

Alertmanager 启动脚本按环境变量生成接收器：

- 设置 `ALERT_EMAIL_TO` 时生成 `email_configs`，SMTP 复用后端已有的 `EMAIL_SMTP_HOST`、`EMAIL_SMTP_PORT`、`EMAIL_SMTP_USERNAME`、`EMAIL_SMTP_PASSWORD`、`EMAIL_FROM` 与 `EMAIL_SMTP_TLS`；
- 设置 `ALERT_WEBHOOK_URL` 时追加通用 `webhook_configs`，适合接入自建告警网关；
- 两者都未设置时仍启动，告警只在 Alertmanager UI 中查看，不产生外部投递。

没有直接内置飞书、钉钉等机器人格式。这类平台需要签名与消息体转换，建议先用一个转发服务接收 Alertmanager 的通用 JSON，再转成目标格式，避免把平台特定逻辑写进 Compose。

告警分组为 `alertname + severity`，首次等待 30 秒、组内间隔 5 分钟、未恢复每 4 小时重复。

## 8. 仪表盘

`Theseus 运行概览` 包含：

- 请求速率、5xx 比例、接口 P95 延迟、判题 Worker 心跳（stat）；
- 按状态码分组的请求速率、最慢 5 条路由的 P95；
- 判题队列长度、待确认与死信、数据库连接池、排位匹配队列与成局速率。

默认时间范围为最近 6 小时，30 秒刷新。仪表盘允许在 UI 中修改；重启 Grafana 后以 provisioning 文件为准（`allowUiUpdates: true`，但文件更新会覆盖同名仪表盘）。

## 9. 数据保留与资源

- Prometheus 默认保留 15 天，可用 `PROMETHEUS_RETENTION` 调整；单机低配环境建议 7–15 天。
- 三个组件常驻内存约 100–300 MB，主要取决于序列基数。`route` 使用 `MatchedPath` 模板，不会因路径参数增长。
- 卷 `prometheus-data`、`alertmanager-data`、`grafana-data` 随项目保留；不启用观测时不会创建。
- 备份脚本只备份数据库与 uploads，观测数据视为可丢失的运行期数据，不纳入恢复流程。

## 10. 安全

- `/metrics` 继续只在 Compose 内部网络暴露，未在前端 Nginx 放行；
- Prometheus、Alertmanager、Grafana 端口全部绑定 `127.0.0.1`，公网访问走 SSH 隧道或额外反代；
- Grafana 关闭注册与匿名访问，管理员密码通过 `.env` 注入；
- 告警内容只包含指标值、队列名与路由模板，不含用户数据、源码或隐藏用例；
- Alertmanager 的 SMTP 密码只存在于容器环境变量中，不写入挂载的配置文件。

## 11. 已知限制

- 单机部署：Prometheus 与 Alertmanager 均为单实例，没有 HA 与跨机聚合；
- 没有日志聚合与链路追踪，排障仍依赖 `docker compose logs`；
- 观测三件套不参与 `update.sh` 的镜像构建，升级时只跟随镜像标签；
- 没有长期存储（Thanos/VictoriaMetrics）与告警静默管理 UI 之外的策略；
- 多实例后 `theseus_http_*` 等进程内指标需要按实例抓取并在 PromQL 中聚合，当前单实例无需额外配置。
